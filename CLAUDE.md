# Hearth — Engineering Contract

Hearth is an internal work suite (chat, drop-in voice rooms, meetings, calendar, tasks, and a Drive holding docs and wiki, sheets, slides and files) where AI agents are teammates, built over a permission-aware Org Brain. Its first customer is our own organisation, moving its work communication off WhatsApp. It is not an email client, a guest or cross-org tool, an integrations hub, a full Excel or PowerPoint replacement, or an assistant that acts on anyone's behalf. Spec: `docs/PRD.md`, where a decision (`Dn`) beats a requirement that disagrees with it. Keep each module at the depth its P0 rows set (D18).

- Build → simplify → automate. Start with manual input.
- Scope guard: do NOT build email, external guests or shared channels, third-party integrations, native apps, agent computers, macros, pivot tables or other full Office parity, an assistant that sends or edits for a user (D16), WhatsApp import (D17), billing or self-serve sign-up, or AI scoring of what people say or voiceprints (D34). The full list is PRD §3.2.
- Stack (D37): TypeScript strict end to end in an npm-workspaces monorepo (`apps/web`, `apps/server`, `packages/shared`, `packages/access`, `infra/`; `demo/` stays as the reference UI). Node 24 LTS. Web: Vite + React 19 + Tailwind v4 as an installable PWA, with TanStack Router and Query (T21). Server: Fastify + `ws`. PostgreSQL 17 (RDS; pgvector later), Valkey, S3, LiveKit Cloud. AWS CDK in ap-southeast-1. Vitest, Playwright, Biome. Not Next.js, Supabase or Vercel: hosting is AWS ap-southeast-1 (D37, B.6), and the server runs long-lived WebSocket, Yjs and recorder processes that serverless hosts don't. LiveKit Cloud metadata, Twilio Verify (the number of each roster member who asks for a sign-in or re-authentication code, and the codes it makes, sends and checks, processed in the United States; D46, T20) and OpenAI transcription still leave Singapore and are recorded in PDPA-10. Technical decisions (T1–T12, and T13 onwards as they're made) are recorded with their status in `docs/TECH-SPEC.md`. The database layer is Kysely: typed SQL queries and plain SQL migrations (T3).

## Build order
- Core first, AI second (D41). Stages C0–C6 make no model calls: no LLMs, no speech-to-text, no embeddings, no local ML models such as speech detection or noise suppression, and no AI-generated content. Check a requirement's stage in `docs/BUILD-PLAN.md` Part 2 before building it.
- Build the seams in `docs/BUILD-PLAN.md` Part 1D instead, so AI plugs in later without migrations: every content write appends an outbox event with an ACL snapshot; every other write appends its catalogue event or is listed as exempt, with a reason, in `apps/server/src/outbox/coverage.ts` (CI checks both ways: `apps/server/scripts/check-catalogues.ts` against the database's grants and functions, and every integration suite but the roles one against the writes it commits); principals have a kind (human, agent, assistant, system); messages can carry an author kind and sources; transcript fields exist, nullable, with a status; AI feature flags exist and are off.
- CI enforces it with `scripts/guards/ai-free.test.ts`. It fails on a package in its banned list (model SDKs, speech-to-text and speech detection, on-device ML and noise suppression, OCR) in any `package.json` (by name, npm alias or override) or any npm lockfile (dependencies of dependencies too; other package managers' lockfiles are refused because it can't read them), or imported by a script or an HTML page. It also reads every script and page with comments stripped (a page whole, attributes included) and fails on use of the browser's speech recognition or built-in AI (`SpeechRecognition`, `LanguageModel`, `Summarizer`, `LanguageDetector`, `Rewriter` and `Proofreader` by name; `Translator` and `Writer` through `window`, `globalThis` or `self`, a cast, an `in` check or their `create()` entry point), and on any request for the `voiceIsolation` constraint. Only a property read (`settings.voiceIsolation`), setting it to `false`, or declaring it as an optional property in a type (`voiceIsolation?: boolean`, which strict TypeScript needs because the DOM types lack it) passes; destructuring, a bracket read or an `in` check naming it fails. It also fails on any URL on the public npm CDNs it lists, comments and strings included, because loading code from them would bypass every npm check. Biome (`biome.json`) also refuses those browser globals in plain JavaScript. livekit-client asks for voice isolation by default and the guard can't see library defaults, so C2 passes `voiceIsolation: false` on every capture path: the Room's `audioCaptureDefaults` and every standalone `createLocalTracks`, `createLocalAudioTrack` or `usePreviewTracks` call. The stock components-react PreJoin can't turn it off, so C2 doesn't use it. A newly found package goes in the banned list in `scripts/guards/ai-free.ts`. From A0, `packages/model` is the one place a model SDK may live, and the guard gets an exception for it then.

## Product rules that never bend
- Never leak (Principle 1). Every access check goes through `packages/access`; no screen or endpoint checks access its own way. Every AI feature retrieves through the one permission-enforcing retrieval layer (B.4) and never queries the index directly.
- Every record belongs to an org (ACC-11): every table has `org_id`, and every query filters by it (the only exceptions are the sign-in lookups that run before the org is known, and the worker's org list, `worker_org_ids()`, which returns org ids only; see Database).
- Recording is never hidden (Principle 6): every room and call UI shows the recording indicator.
- The personal assistant suggests and drafts; it never sends, edits, creates or deletes for a user (D16).
- Content is data, not instructions (Rule 8).
- Privileged access (Rule 9) happens only in the DPO and Compliance consoles, against a logged case with a stated reason. It is never available to any AI feature.

## Git
- Never commit directly to `main`. Create a feature branch.
- This repository is public: anything pushed, on any branch, stays public even after the branch is deleted.
- Keep PRs small and focused. Use Conventional Commit titles: `feat(scope): …`, `fix(scope): …`, `chore: …`, `docs: …`, `ci: …`. Name the migration in the title when a PR adds one, e.g. `feat(db): … (0006)`. Cite requirement, decision and technical-decision IDs (CHAT-04, D39, T5) and review IDs (RMS-01) in commit messages and test names. Squash-merge.
- Claude merges only a PR whose head branch is in this repository (not a fork) and that Claude opened or the user asked it to merge, and only once all three hold on its latest commit: CodeRabbit has approved it; Qodo has reviewed it and left no open "Action required" finding (no Qodo review on the latest commit means this isn't met); the CI checks (`check`, `migrations`) succeeded (not skipped) and no other CI job failed. If one of them doesn't hold, Claude tells the user which one and merges only if the user, told that, confirms for that PR. Hold the merge while the PR description lists unticked "Before merging" steps.
- A PR that adds or changes a file in `db/migrations/`, the privileged module's allow-list, the Owner bootstrap script, `.gitleaksignore`, or the `GITLEAKS_CONFIG_TOML` in `.github/workflows/secrets.yml` (the last two silence the secret scan) lists an unticked "Before merging: @ashtonatnormal has read it" step. Only the user's own tick, or the user saying they have read that change, clears it; a general request to merge ("merge it when green") doesn't. CodeRabbit skips migrations, and the user can't formally approve PRs opened under their own account.
- Never bypass CI or branch protection. Never merge past red CI. Don't post `@coderabbitai approve` unless the user asks: the approval must come from CodeRabbit's own review. Never resolve a CodeRabbit or Qodo thread unless the commit that fixes it is pushed; if you disagree with a finding, reply with your reason and leave the thread for the user. Resolving threads to unlock an approval counts as bypassing review.
- `main` protection lives in `.github/rulesets/protect-main.json`. A repo admin applies it with `scripts/protect-main.sh`, or imports the file under Settings → Rules → Rulesets. Change it only by PR; never loosen it in the GitHub UI. If it isn't live, say so rather than assume `main` is protected.
  - Changes land only through a PR with 1 approval (CodeRabbit's counts). A new push dismisses earlier approvals, and every review thread must be resolved. Only squash merges.
  - The required checks (`check`, `migrations`) must pass on a branch that is up to date with `main`.
  - No force-pushes, no deleting `main`, no bypass actors (admins included).
- After every Claude response, a Stop hook (`.claude/hooks/auto-push.sh`) commits the work tree and pushes the current branch as a checkpoint (`chore(auto): checkpoint after Claude Code run`), unless a rule below stops it. Opt out with `HEARTH_AUTOPUSH=0`. Before committing, it formats the staged copies of what it commits with the repo's own Biome (`node_modules/.bin/biome format --stdin-file-path`, never `npx`; only with a regular `biome.json` or `biome.jsonc`, node, and perl with its Digest::SHA module, which Fedora and RHEL package separately as `perl-Digest-SHA`; at most 300 files and about 10 s), to keep a checkpoint from going red for formatting alone. It formats only where a file on disk can take Biome's version in an atomic exchange (Linux `renameat2` `RENAME_EXCHANGE`, on x86_64 or arm64, with the work tree on the same mount as `.git`); elsewhere (macOS, NFS, most FUSE file systems) it commits files as they are and says so. It formats only a file of a type Biome formats, of at most 1 MiB, that is a regular file with one link and no symlinked folder on its path, in a folder on the git directory's mount, holds on disk exactly the bytes staged, and is written to disk by git unconverted (no CRLF line endings, `ident`, `filter` or `working-tree-encoding`); every other file is committed as it is, and so is a file Biome ignores or can't parse, or one that changes while Biome runs. If another git command holds the index when the formatted files are staged, the checkpoint is committed unformatted. If another git command stages, resets, stashes or commits anything while the hook runs, the hook commits nothing and leaves the index as that command left it (it puts back what was staged before only while HEAD hasn't moved and the index still stages exactly what the hook left there), and the next checkpoint tries again; a new file outside the allow-list that reaches the commit anyway, staged in the moment before `git commit` reads the index, takes the commit back off the branch, and no checkpoint commit that adds one is pushed. When a checkpoint commits, its message says if the formatting step was skipped or stopped early. A formatted file on disk gets Biome's version only after the commit (or when formatting leaves nothing to commit), in one atomic exchange, and only if the commit (or HEAD) holds that version and the file still holds exactly what was staged, with the mode it had. An edit or a change of mode made meanwhile is kept (the old file is read back after the exchange, its bytes and not just its size and time) and the next checkpoint commits it; only a write or a change of mode to the old file landing after the hook's last look at it (20 ms after the last exchange) can be lost. The swap step's own 10 s limit and TERM, INT or HUP wait until every exchanged file is checked. An old file whose bytes changed and can't go back, or that a stopped hook never checked (SIGKILL, or a signal it doesn't handle), is kept in `autopush.kept.*` in the git directory, and every checkpoint's message names it until it is deleted; a change of mode alone is then lost. If an exchange fails anyway, that file is left as it was, formatting stays off until `autopush.noswap` in the git directory is deleted (every committing checkpoint says so), and the next checkpoint commits the files as they are on disk. The hook never runs on `main`/`master`, never commits files or token shapes it recognises as secrets (it looks for them both before and after formatting, since Biome can move a value onto a line of its own), skips while a merge or rebase is in progress, and never force-pushes. Checkpoints aren't gated and may be red; the gates are the pre-PR check and green CI before merge. Changes to tracked files don't need the new-file allow-list, but they're committed only when the checkpoint passes its secret checks and isn't skipped or refused. A new file is committed only in a source folder (`apps/`, `packages/`, `db/`, `docs/`, `scripts/`, `infra/`, `demo/`, `spike/`, `.github/`, `.claude/`) or as a known root config file, and never if it's shaped like data (CSV, JSONL, audio, video, office files, PDFs, dumps, archives). The hook leaves other new files uncommitted and names them, and refuses the whole checkpoint if one is already staged; commit such a file by hand only when it holds no people's data. People's data goes only under `local-data/` (see Security and privacy).

## Database (PostgreSQL)
- Never modify the production schema by hand. Every schema change is a migration in `db/migrations/`, named `<NNNN>_<name>.sql`, applied in name order to an empty database in one transaction (as Kysely's migrator does on Postgres; from Kysely 0.30, set `transactionMode: 'per-run'` explicitly, since its default may change). Migrations are plain SQL: no psql meta-commands, a migration never ends its own transaction or changes role, and each file stays under 120 KB. The migration tool is Kysely (`docs/TECH-SPEC.md`, T3): `apps/server/src/db/migrations.ts` is its provider for these `.sql` files, which refuses any file Kysely would skip or not see and fails a migration that ends the transaction or leaves another role in place, naming the file. `apps/server/src/db/migrate.ts` is the pre-deploy migrate step, run from the server image, and `scripts/check-migrations.sh` applies migrations with the same code. The migrate login takes `hearth_owner` at connection, and must have no rights of its own (`hearth_owner` itself, or a NOINHERIT login whose only membership is `hearth_owner`, as CI's is), so a migration that switches role and back gains nothing. A scratch build starts empty, so it can't see a migration that sorts below one production has already applied: `scripts/check-migration-order.sh` (CI, on every PR) fails a PR whose new migration numbers at or below the highest on its base branch, or that changes, renames or deletes one the base already has, and Kysely's default `allowUnorderedMigrations: false` stays, so the pre-deploy migrate refuses such a file too. After adding a migration, run `npm run db:types` to regenerate `apps/server/src/db/schema.ts` (CI fails if it's stale). No direct production changes.
- Roles:
  - `hearth_owner` runs migrations and owns every table, view, function and schema. It is NOSUPERUSER; anything that needs more (an untrusted extension such as pgvector, a `BYPASSRLS` role) is a bootstrap step in `infra/`, mirrored in `scripts/check-migrations.sh` where CI needs it, never a migration.
  - `hearth_app` is the runtime role: NOSUPERUSER, NOBYPASSRLS, owns nothing, and is never a member of `hearth_owner` or of any role that owns tables or has `BYPASSRLS` (a member of a table's owner skips RLS just like the owner).
  - `hearth_worker` is the worker's login (`WORKER_DATABASE_URL`, TECH-SPEC T18): NOINHERIT, owns nothing, holds no privilege of its own, and holds only job roles (`hearth_queue`, `hearth_job_offboarding`, `hearth_job_partitions`, `hearth_job_purge`, `hearth_job_revocation`), by SET and never INHERIT (on RDS also the powerless `rds_iam`, as `hearth_app` may), which `withOrg()`'s `as` takes for one transaction. Job roles are NOLOGIN, own nothing, are members of no role, may be used by `hearth_worker` alone and never get BYPASSRLS; `hearth_app` is never a member of one, and the api and realtime roles never hold the worker's credential (nor the worker theirs). Every role granted anything in the database, and every role that can use one by SET or INHERIT, is held to the rule `hearth_app` is (`scripts/check-migrations.sh`); a migration that finds a role already there checks each grant's own options.
  - Migrations create roles NOLOGIN or without a password; passwords and IAM auth are set outside git (Secrets Manager). Roles belong to the whole server, so a migration that finds a role already there asserts its attributes and memberships instead of skipping it silently.
- RLS is on for every table (the migrator's own ledger, `kysely_migration` and `kysely_migration_lock`, aside: it has no `org_id`, and nobody but its owner may be granted it). Policies are org-scoped, the second line of defence behind `packages/access`. They read `nullif(current_setting('app.org_id', true), '')::uuid`, so a missing org means no rows. CI fails if any table has RLS off, and `db/tests/015_policies.sql` pins every policy's text. `/ready` fails if `DATABASE_URL` connects as a role that skips RLS or can use a job role, or if `WORKER_DATABASE_URL` connects as one that can become a role that skips RLS or can't take each of the worker's job roles.
- The server sets the org and user only inside a transaction, through one helper, `withOrg()` in `apps/server/src/db/database.ts`: `BEGIN` (READ COMMITTED), `select set_config('app.org_id', $1, true), set_config('app.user_id', $2, true), set_config('lock_timeout', '2s', true), set_config('transaction_timeout', '30s', true)` (for a job, `set_config('role', <job role>, true)` first, in the same statement), the work, then `COMMIT` or `ROLLBACK` before the client goes back to the pool. Both values come from the server-side session (opaque, revocable tokens), never from the request. Never `SET app.*` or `set_config(…, false)` on a pooled connection. Jobs and WebSocket handlers use the same helper with their own org. With `{ system: true }` it acts as the org's `hearth` system principal, which it reads in the same transaction; sign-in uses this before a session exists, and so do the worker's jobs. Only `withOrg()` and the worker's `listOrgs()` (beside it in `database.ts`) set the role. Every transaction the server opens (these and the pre-org lookups) is bounded by a 30 s `transaction_timeout`, so none can hold the outbox's horizon (TECH-SPEC T16, T18); only read-only work (`readOnly`) may raise it, to at most 5 minutes. Postgres ends the connection of a transaction that runs past it, so the caller sees a lost connection, not a SQLSTATE.
- The sign-in lookups that run before the org is known go through `apps/server/src/db/pre-org.ts` instead. Each runs in its own short READ COMMITTED transaction, because the functions are VOLATILE and read FOR SHARE, with a 2 s `lock_timeout`, a 30 s `transaction_timeout` and `synchronous_commit` off (it writes only row locks). It calls only those two functions and sets no `app.*` value. The worker's org list is the other lookup before an org is known: `listOrgs()` calls `worker_org_ids()` (org ids only, executable by `hearth_queue` alone) in its own short read-only transaction as `hearth_queue`, and everything after it runs in `withOrg()` for one org. `scripts/guards/db-entry.test.ts` keeps every other transaction in `withOrg()`, and every role change and `worker_org_ids()` call in `database.ts`.
- New tables, views and functions get no grants by default:
  - Grant `hearth_app` only the SELECT/INSERT/UPDATE/DELETE each table needs, in the same migration. Never ALL, TRUNCATE, TRIGGER or REFERENCES: TRUNCATE ignores RLS and empties every org's rows.
  - Run `revoke execute … from public` on every new function (Postgres grants it to everyone otherwise).
  - Create views `with (security_invoker = true)` so RLS still applies. Never grant a materialized view (RLS can't apply to it); precompute per-org rows into a table with RLS instead.
- `audit_events` and `data_access_events` are append-only: `hearth_app` gets INSERT only, never SELECT, UPDATE, DELETE or TRUNCATE (so no `INSERT … RETURNING`). Reads go through a `SECURITY DEFINER` function (below) that checks the reader's ACC-10 role in tables: `read_audit_events()` for the audit log, which admits only the roles on the org's `audit_log_readers` list (a setting, empty until chosen in the admin console, C0.16; never Team Admin; D45); `data_access_events` gets its readers with the features that need them (C1.11, C2.8, C6.2). DB tests prove it. `data_access_events` is partitioned by month: every partition gets RLS on and no grants, and its partitions are created ahead by `create_data_access_partitions()`, which the worker's partitions job runs daily as `hearth_job_partitions` (TECH-SPEC T15 item 16).
- The outbox (`outbox_events`, TECH-SPEC T16) is append-only for `hearth_app` (INSERT only; `id`, `tx_id` and `at` are the database's; the actor is the transaction's principal unless Hearth acts), and the roles that may append are pinned by a DB test (`db/tests/032_worker_roles.sql`); never the Rule 9 role or any role with BYPASSRLS. Rows leave the outbox and the queue only through the clean-up functions (`purge_outbox()`, `purge_jobs()`, `purge_schedule_runs()`), whose ages are fixed in SQL. A feature flag changes only through `set_feature_flag()`; every `ai.*` flag is off and locked by a table constraint until A0's migration lifts it. A transaction that makes a feature's effect visible ends with `feature_fence()` (a job's with `job_fence()` or `job_finish()`), which refuses unless the flags are on and at the revisions the server checked, so nothing commits after a flag is turned off or narrowed (TECH-SPEC T17). Flags gate features, never an access check or a privacy or safety control.
- Never let the browser reach a privileged credential (the owner or any `BYPASSRLS` role, AWS keys, provider keys). Server-only variables never get a `VITE_` prefix (Vite ships those to the browser). A guard test (`scripts/guards/vite-env.test.ts`) fails on any `VITE_` variable in source, config or any `.env` file git tracks whose name contains SECRET, TOKEN, PASSWORD, PRIVATE, KEY, DATABASE, DB_URL or PG, except names ending in `_PUBLIC_KEY` (such as the VAPID key Web Push needs), and on any Vite config that sets `envPrefix`. In AWS secrets live in Secrets Manager, never in code or plain config.
- The browser never talks to Postgres. Every read and write goes through the server, which takes the acting user and org from the server-side session, never from the request body, query or headers. That covers `*_by` columns, audit actors, the user passed to `SECURITY DEFINER` functions, and `set_config`.
- The Rule 9 module (`apps/server/src/db/privileged.ts`) is the only code with a database connection that bypasses RLS. (`SECURITY DEFINER` functions also skip RLS, because they run as `hearth_owner`, which owns the tables, so each one filters by org itself and stays narrow.) The module uses its own database role and credential, which no other job or service can assume. Only the DPO and Compliance consoles import it; every read through it is logged with its case and reason (Rule 9, ADM-06); it makes no outbox or index writes; AI code never imports it. A guard test next to it (`privileged-imports.test.ts`, added in the same PR) keeps the allow-list. Like Module One's `admin-imports.test.ts`, it catches static and dynamic imports, re-exports, `require()` and `vi.mock()`-style calls, under either spelling of the module's path (`#src/db/privileged.ts` or relative), and any other code reading the module's credential. Adding a file to the list is a reviewed change.
- Every system job (retention, indexer, recorder, calculation and conversion workers) gets its own role with only the grants it needs, and none gets `BYPASSRLS`. The worker's jobs are job roles its login takes per transaction (C0.6: `hearth_queue` claims, schedules and reads flags, `hearth_job_offboarding` runs offboarding, `hearth_job_partitions` the partitions job, `hearth_job_purge` only the clean-up functions; `hearth_job_revocation` the revocation consumer and its jobs (C0.7)); `db/tests/032_worker_roles.sql` pins each one's privileges. A service that reads sensitive data (the recorder, conversion, calculation, the Rule 9 role) gets a login of its own. Grant SELECT on transcript and recording tables only to the roles that must read them, named in the migration. Per-job roles alone don't meet PDPA-12 (P1): with one org and org-scoped RLS, `hearth_app` and the Rule 9 role can each read every transcript. PDPA-12 needs storage and encryption keys separated by team or space, designed in `infra/`; don't describe it as met until that exists.
- Admin powers are roles (ACC-10) held as rows. `packages/access` (`can()`) decides every admin action, and RLS stays org-scoped.
  - Roles are set only through ADM-02's role assignment and the roster CSV import (ACC-03), plus the Owner bootstrap below. No other endpoint, job, agent tool or migration writes roles. Both console paths run the same server-side checks on every row and write an audit event (ADM-06).
  - Nobody changes their own roles, alone or by approving a grant to themselves. Nobody can promote themselves.
  - Until the PRD decides otherwise, only an Owner grants or removes Owner, Admin, AI Admin, Leadership, DPO and Compliance Officer; Admins assign Team Admin and Member. DPO and Compliance Officer grants open Rule 9 access, so they also need a second approver (an Owner or Admin other than the granting Owner and the grantee) and alert the DPO.
  - The org's first Owner, who is also its first DPO (D35), is created once by a reviewed bootstrap script in `scripts/` or `infra/` that a person runs against the target database. It reads the name and phone number at run time from Secrets Manager or the environment; they're never committed, because the repo is public. Later DPO and Compliance Officer grants follow the rule above.
  - Every admin action needs re-authentication (§9.4), by the session's method (`reauthMethodOf` in `packages/access`, TECH-SPEC T20 item 6): the PIN for a session issued under the PIN rule, a fresh SMS code to the person's own number for any other; a PIN-rule session whose PIN was cleared, or another session whose holder now holds a PIN role, can't re-authenticate and needs a new sign-in (`sign_in`, T20 item 6).
  - Holders of a PIN role (`PIN_ROLES` and `holdsPinRole` in `packages/access`: by default the roles only an Owner grants, which `roles.test.ts` keeps equal to that list) sign in with the SMS code and then their PIN, get a 7-day session issued under the PIN rule (`PIN_RULE_SESSION`), and re-authenticate with the PIN, never by SMS. Everyone else signs in on the code alone (D46). The sign-in reads whether someone holds a PIN role in the transaction that issues the session, after their person row is read `FOR SHARE` (`holdsPinRoleNow`). The rule is code, never a flag. From C0.16, every write that gives someone a PIN role takes their person row `FOR NO KEY UPDATE`, ends their open sessions, then writes the role row, in one transaction (people → sessions → role_assignments), and the database refuses such a grant while they have a live session (T20 item 14). In this repo "privileged" means Rule 9 access only: the sign-in code says "PIN role" and "PIN rule".
- A write `hearth_app` has no grant for goes through one `SECURITY DEFINER` function declared `set search_path = ''`, with every object schema-qualified (`public.people`). A plain `search_path = public` lets a temporary table stand in for a real one. The server calls the function only after `can()` allows the action, passing the acting user; the function re-checks that user's role and org in tables and writes an audit event. Sign-in and session lookups that run before the org is known (token hash → session, phone → user) are `SECURITY DEFINER` functions with the same `search_path` and `revoke execute` rules. They take no acting user and skip `can()`, return only ids, and audit sign-ins (ADM-06), not each lookup. The worker's definer functions also take no acting user and skip `can()`, because they act for no person, only for the worker's own job roles, the only ones that may run them: `worker_org_ids()` returns only org ids; the clean-up functions write one audit event per batch; and the fences (`feature_fence()`, `job_fence()`, `job_finish()`), which are definer functions only because their row locks need UPDATE, neither re-check an ACC-10 role nor write an audit event, because they decide only whether work already admitted may still commit, change no flag and nobody's data (`job_finish()` ends the job and its run, the queue's own bookkeeping), and every flag change they compare against is checked and audited in `set_feature_flag()`.
- Rows that carry history (people, teams, channels, sessions) are archived or soft-removed (`archived_at`, `removed_at`), not deleted. Record who did what and when in `*_by` / `*_at` columns. Content the PRD says to delete (CHAT-05, FILE-02's Trash after 30 days, Rule 7, PDPA-09 retention) is deleted for real, but only through the deletion and retention code, for rows and S3 objects alike. That code checks legal holds (ADM-08) and access-request holds (PDPA-09, including at least 30 days after a refused request), cascades to derived content and logs each deletion (PDPA-09).
- Store the context a record was made in (e.g. the team or channel it belonged to). Later moves must not rewrite history.
- Compute values that depend on a tunable settings row (e.g. retention "delete after" dates, overdue flags, a session's "substantive" status) from stored raw values plus that row, never from a stored derived column, so tuning the setting re-applies to history. Fields people set (a task's status and due date, TASK-01) are raw values. Caches of derived data (computed sheet values, thumbnails, index rows) may be stored if they can be recomputed and are deleted with their source (PDPA-09), but they're never the source of truth.
- Enforce hierarchy (folders, teams, departments) and other invariants with DB triggers whose error messages the UI can show as is. Run tree changes under READ COMMITTED. A trigger or `SECURITY DEFINER` function that refuses because a row it reads has ended (archived, deactivated, signed out, revoked, removed) reads that row `FOR SHARE`, so a change to it in progress makes it wait and then see what was committed (`read_audit_events()` does this for the reader's role, person and list entry).
- Lock rows in this order: people → users → passkeys → phone_numbers → devices → sessions, then role_assignments → feature_flags → jobs → schedule_runs: a flag change takes its row `FOR NO KEY UPDATE` after the actor's rows; a job's finishing transaction locks the flags `FOR SHARE`, then the job, then its run; claims and the lease sweep lock jobs with `SKIP LOCKED`, and enqueues and outbox appends take only foreign-key `KEY SHARE` locks. Sign-in and re-authentication read the person `FOR SHARE` first. A transaction that ends some or all of a person's sessions locks the person's row first: `for no key update` when it may end more than one device's sessions (so a sign-in in progress finishes first and is then ended too), the deactivation's own `UPDATE`, or `FOR SHARE` when it ends one device's or one session's. An admin action on someone else is an exception to this order: the admin's own rows come first and that person's after. A PIN reset or device sign-out takes their row `for no key update` only once `can()` has allowed it, and `can()` then decides again, so a deactivation of them in progress is seen and a refused caller locks nothing of theirs. Two admins acting on each other at the same moment can deadlock, and one of them gets 409. Every state-changing request re-reads the acting person, device and session `FOR SHARE` in its own transaction before it decides with `can()`. A lock taken `NOWAIT` never waits. A deadlock or lock timeout answers 409 `try_again`.
- Tables that hold Rule 9 case material get no grants to `hearth_app`; only the Rule 9 module reaches them.
- File storage (S3):
  - Use private buckets per data class, each with its own KMS key; restricted sessions get their own key too. Object keys are `<org_id>/<random id>`, made by the server. The filename, owner, folder and ACL live in the database, and access decisions never read the key. Team or space separation (PDPA-12) comes from KMS keys or encryption context set in `infra/`, never from key prefixes.
  - Uploads go to a quarantine prefix through a presigned URL the server issues per upload. The URL signs `If-None-Match: *` (so it can't overwrite) and the size the server checked against the limits. The server sets the stored content type from the bytes, never from the client. A file is served only after the malware scan promotes it: promotion copies `quarantine/<org_id>/<id>` to `<org_id>/<id>` and deletes the quarantine copy, and the key never changes after that. Uploaded files are parsed only in an isolated worker with no network access, and macros never run (§9.4).
  - Downloads: the server checks access, logs the view where the PRD asks (REC-21), and issues a signed GET URL that expires within 60 s, on a separate user-content origin, never the app origin. Anything not on the preview allow-list is served as an attachment with a safe content type; HTML and SVG never render inline. Recordings and other long media play from segmented renditions (e.g. HLS) whose segments are authorised for a short time, never by lengthening one URL past 60 s.
  - S3 lifecycle rules (defined in `infra/`, never set by hand) only change storage class. Retention deletes are done by the retention engine (PDPA-09, ADM-07). It first checks legal holds (ADM-08) and access-request holds (PDPA-09), deletes every version in a versioned bucket, and logs each deletion, in the log a backup restore replays. Held recordings also get an S3 Object Lock legal hold. An age-based expiry may only be a backstop for objects the engine has released. B.6's "deleted at 120/360 days" lifecycle row predates this; PDPA-09, REC-23 and ADM-08 win.
  - Sensitive deletes go through a checked DB function that logs which files to delete. The server removes only those files and stamps the log row, and a daily job retries unstamped rows.
- DB tests live in `db/tests/` (`scripts/test-db.sh`). Each app test runs as `hearth_app` (`set local role hearth_app` plus the helper's `set_config` values), and each job-role test as the job role it tests (`set local role <job role>` plus the settings that role's work uses, as `db/tests/032_worker_roles.sql` does); a test that doesn't switch role runs as a superuser and passes trivially. Each table's tests cover no org set (no rows), another org (no rows), the same org (the rows RLS allows), for every runtime role that can read it, and every privilege `hearth_app` and each job role must not have (e.g. UPDATE or DELETE on `audit_events`, any grant on Rule 9 tables). Each `SECURITY DEFINER` function gets a case for every ACC-10 role it accepts or must refuse, set through `app.user_id`. The full per-role matrix (Member, Team Admin, Admin, Owner, AI Admin, Leadership, DPO, Compliance Officer, including the roles that must be refused) lives in `packages/access`'s tests, with Rules 1–9 as named cases. Rule 9 reads are tested in the Rule 9 module's own tests.

## Security and privacy
- Never commit secrets. `.env*` is git-ignored except `.env.example`, which documents every variable with a comment.
- Never disable auth checks or weaken RLS or access rules without explicit review.
- The session token lives only in a `__Host-` cookie marked `HttpOnly; Secure; SameSite=Lax`, never in storage JavaScript can read. Sign-in state between steps is kept in Valkey under an id in a second cookie, `__Host-hearth_attempt` (`SameSite=Strict`), never in a URL or body. Valkey key names hold a keyed hash of a phone number or IP, never the value. The local fake SMS provider (`SMS_PROVIDER=fake`, a stand-in for Twilio Verify that sends nothing and prints each code to stderr with the number masked, never to the JSON log) runs only where `DEPLOY_ENV` is `local` or `test` and `APP_ORIGIN` is a localhost origin. Twilio Verify (`SMS_PROVIDER=twilio`) is refused where `DEPLOY_ENV` is `local` or `test` or `APP_ORIGIN` is a localhost origin; config and the guarded factory each refuse both on their own (`createFakeVerify()` and `createTwilioVerify()`, which only `main.ts` calls: `scripts/guards/sms-provider.test.ts`). Twilio's credentials (`TWILIO_*`) come only from Secrets Manager, and the transfer gate sends it no number until C0.9 clears it in the transfer register (TECH-SPEC T20 items 9 and 10). The local `AUTH_SECRET` from `.env.example` is accepted only where `DEPLOY_ENV` is `local` or `test` and `APP_ORIGIN` is a localhost origin. The client's address comes from `X-Forwarded-For` only through the proxies `TRUST_PROXY` lists. State changes are never GETs or HEADs. One Fastify hook, registered at the root so no plugin scope escapes it, refuses every browser-facing request other than GET or HEAD (sign-in, OTP and passkey routes included) whose `Origin` isn't exactly the app origin; a missing or `null` Origin is refused too. The WebSocket upgrade handler makes the same check before accepting. Only provider webhooks (LiveKit, SMS) are exempt, and they verify the provider's signature instead; the Twilio Verify adapter takes no webhook, so it has no exemption. Tests prove that a cross-origin POST, a POST with no Origin, a POST from the user-content origin and a cross-origin WebSocket upgrade are all refused. Gateway frames, the gateway's Valkey streams and the revocation channels carry ids, codes and numbers only, never content or anyone's details (TECH-SPEC T19); the browser reads content over REST, which checks access, and a refused topic answers exactly as a missing one. The realtime role writes nothing to Postgres.
- Every document header the web app is served with, its Content Security Policy included, comes from one builder, `documentHeaders()` in `packages/shared/src/web-headers.ts`: Vite's dev server, the e2e preview and C0.12's CloudFront response-headers policy all use it (`scripts/guards/csp.test.ts`, TECH-SPEC T21 items 7 and 8). A new outbound host (C0.13's RUM, C2's LiveKit) joins `connect-src` there and in the guard's allow-list in the same PR. `POST /api/csp-report` logs only reduced fields (the directive, what was blocked as a keyword, origin or scheme, the page's path with every segment but the app's route words (`ROUTE_WORDS`) replaced, the disposition), stores nothing, and has no exemption from the Origin hook (T21 item 9).
- Never send a third-party API key to the browser, not even a short-lived one. The server opens the connection and passes back only what the browser needs. The one exception is the LiveKit participant token, which LiveKit requires:
  - The server mints it after `can()` allows joining, for one room and the session's identity.
  - It lasts minutes, not the SDK's 6-hour default.
  - `canPublish`, `canSubscribe` and `canPublishSources` are set from the access check, and `canPublishData` is off: room content travels over Hearth's own WebSocket, never LiveKit data messages (B.2).
  - Only the recorder bot's server-side token gets `hidden` and recorder grants. People and agent workers join visibly (Principle 3), with no `hidden`, recorder or admin grants, and agents don't publish audio (ROOM-11).
  - Expiry only gates joining, so when someone loses access the server removes them from the room within 60 s (ACC-05).
  - A unit test on the minting module checks the lifetime and the forbidden grants.
- A person (never a coding agent) writes any local output that holds people's data (exports, transcript or model comparisons, §9.5 test-set clips) only under `local-data/` at the repo root. It's git-ignored at any depth, so a `local-data/` made from `demo/` or `apps/*` is ignored too.
- Coding agents (Claude Code sessions, CI) never connect to production, never read production data, and never open or run anything on people's data, including the §9.5 test set and anything under `local-data/`; Anthropic isn't in the transfer register (PDPA-10). They never call Twilio or any real SMS provider, and neither does CI: local runs and tests use the fake provider (the `FakeVerify` class in tests) or the loopback Twilio stand-in (`apps/server/src/testing/fake-twilio.ts`), with fictional numbers only. Production access is logged (§9.4) and never uses the Rule 9 module's credential. Any analysis looks at totals and shares, never one person's rows, and leaves out groups small enough to identify someone. Don't export anything that identifies anyone. In-product people insights follow ADM-14 (D34): counts and durations only, shown only to the roles it names.
- A setting that changes which provider receives people's data, where it is processed or stored, or turns on live processing updates the processing register, the transfer register and the notice (PDPA-01, PDPA-02, PDPA-10), and everyone acknowledges the new version (PDPA-03). Switching models within the same provider and region changes neither.

  - no decorators, `accessor` fields or `.tsx` files, which Node can't strip;
  - start worker threads and child processes from `new URL('./job.ts', import.meta.url)`, never a plain path string, which resolves against the working folder.

  `scripts/guards/server-runtime.test.ts` enforces the first four (and that JSON imports carry `with { type: 'json' }`, package.json `exports` and `imports` name `.ts` files, and runtime code loads no test-only file), `scripts/guards/boundaries.test.ts` keeps `imports` targets inside the workspace, and CI's start-up check starts every role. `apps/web` keeps the `@/*` → `src/*` alias under Vite. Import workspace packages by name (`@hearth/access`). `apps/web` never imports from `apps/server`; shared code goes in `packages/`. `scripts/guards/boundaries.test.ts` enforces this: no app imports another app, `packages/` import no app and not `infra/`, and no workspace imports `demo/` (port from it instead, BUILD-PLAN 1E.5). Validate every input at the server boundary with zod.
- In `apps/web` (TECH-SPEC T21 items 1 to 3 and 13; the WS cases named are in `scripts/guards/web-source.test.ts`):
  - `src/` compiles against ES2023, so tsc refuses the library APIs and syntax Safari on iOS 16.4, the pilot's floor, lacks (`Promise.withResolvers`, `Object.groupBy`, the regex `v` flag); the DOM types aren't narrowed, so WS-08 refuses the Popover API. It imports no Node module (Biome's `noNodejsModules`) and reads no `process.env` (WS-08).
  - A session is a document: every change of person (sign-in, sign-out, a refusal that says the session has ended, another tab's sign-in or sign-out) ends in a full page load, so no state outlives the person it was loaded for.
  - Nothing user-specific goes in browser storage until C1.8: only the few `hearth:*` keys and the router's own in sessionStorage, and nothing in localStorage, IndexedDB or Cache Storage (WS-01).
  - `src/main.ts` statically imports only CSS and modules that import no package, runs `preBoot()`, then loads the app by one dynamic import (WS-10). A chunking setting (`manualChunks`, `advancedChunks`, a vendor split) or a new static import there must keep that rule.
  - `fetch` only in `api/http.ts`, and `WebSocket` only in `live/gateway-client.ts` and `session/runtime.ts`, never with an absolute URL (WS-03); one QueryClient per document, made in `session/query-client.ts` (WS-02).
  - The sign-in and session code reads no flag (WS-11), and there is no WebAuthn ceremony while passkeys are off (WS-12). `sign-in/api.ts` is the one file that knows the sign-in contract, and reads every answer with `packages/shared`'s schemas.
- When docs and code disagree, the code is what happens. Fix the doc in the same PR.

## Conventions
- British spelling in UI copy; short, active voice; no claims the app didn't do.
- Colours only through the design tokens; light and dark must both work; 44 px tap targets; 16 px inputs on phones; WCAG 2.2 AA.
- Phone-first: every flow works at 390 px (and 320 px) before desktop polish.

## Commands
Run these from the root, on Node 24.
- `npm run check`: typecheck, lint and test across every workspace. It must pass before you open a PR; the auto-push hook's checkpoints may be red.
- `npm run build`: build every workspace that has a build step (`apps/web` and `demo/`; the server has none, T2).
- `node scripts/check-web-dist.ts`: after `npm run build`, CI's check of the web bundle against `apps/web/bundle-budget.json` and its scan of `apps/web/dist`.
- `npm run test:integration`: the integration tests (sign-in by code and the PIN steps, devices, socket revocation, the code challenge, the dormant passkeys, the outbox, the job queue and scheduler, flags, the worker's roles, the realtime gateway, the web shell's GETs) against the Compose stack. Each run builds its own throwaway database and Valkey key prefix, so it needs only `docker compose up -d --wait`.
- `docker compose up -d --wait`: the local stack (`docker-compose.yml`): Postgres 17 with pgvector, Valkey 9.1 and RustFS (S3-compatible, TECH-SPEC T9), on 127.0.0.1 with the values in `.env.example`. `docker compose down -v` removes it and its data.
- `npm run dev`: the server's api role with `node --watch`, reading `.env.example` and then `.env` (git-ignored) for overrides. `ROLE=realtime npm run dev` or `ROLE=worker npm run dev` runs another role; the worker connects as `hearth_worker` through `WORKER_DATABASE_URL`, the others as `hearth_app` through `DATABASE_URL`. `curl localhost:3000/ready` answers 200 once the stack is up and `npm run db:reset` has built its database. With the fake provider (`SMS_PROVIDER=fake` in `.env.example`) the api prints each sign-in code in its terminal.
- `npm run dev -w @hearth/web`: the web app on Vite's dev server at `http://localhost:5173` (the `APP_ORIGIN` in `.env.example`), proxying `/api` to the api role on 3000 and `/ws` to the realtime role on 3001. Run the api with `npm run dev` and realtime beside it with `ROLE=realtime PORT=3001 npm run dev`, then sign in with a number from the Tembusu seed (`db/seed/tembusu.sql`), every one of them fictional.
- `npm run e2e`: the web app's end-to-end suite (Playwright, `apps/web/e2e`) against the built app, so run `npm run build` first (the preview refuses a build older than its sources), with the stack up. It rebuilds its own `hearth_e2e` database and flushes Valkey DB 9 every run, and starts the api and realtime roles itself on 3210 and 3211 (`DEPLOY_ENV=test`, the fake provider), so it leaves `hearth` and the dev ports alone. Arguments after `--` go to Playwright (`npm run e2e -- --project=chromium`); see Testing and CI for cloud sessions.
- `scripts/check-server.sh`: CI's start-up check of every role (`IMAGE=hearth-server` checks the image instead, after `docker build -f apps/server/Dockerfile -t hearth-server .`). The image check uses host networking, so it needs Docker on Linux (or Docker Desktop with host networking turned on).
- `npm run fix`: apply Biome's formatting and safe fixes.
- `npm run db:reset`: rebuild the local stack's `hearth` database (`scripts/db-local.sh`): owned by `hearth_owner`, migrated, loaded with the Tembusu seed, and with local logins for `hearth_app` and `hearth_worker`, which `npm run dev` connects as. `npm run db:migrate` applies new migrations and keeps the data.
- `scripts/check-migrations.sh && scripts/test-db.sh`: build a scratch database from `db/migrations/` and run the DB tests. They need a Postgres 17 on 127.0.0.1:5432, which `docker compose up -d --wait` provides. CI loads the seed in between; the tests don't need it.
- `npm run db:types`: regenerate `apps/server/src/db/schema.ts` from the scratch database after `scripts/check-migrations.sh` (CI fails if it differs).
- `scripts/check-migration-order.sh`: check this branch's migrations against `origin/main` (fetch it first).
- `demo/`: `npm run dev`, `npm run build`, `npm test` and `npm run shots`, run inside `demo/` or from the root with `-w demo`.
