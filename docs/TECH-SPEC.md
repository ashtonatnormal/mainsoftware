# Hearth — technical decisions

The technical decisions behind the build, numbered `T1`, `T2`, … so prompts, commits and tests can cite them the way they cite the PRD's `Dn`. T1–T12 come from the build plan (`docs/BUILD-PLAN.md` Part 1E.1) and confirm the PRD's non-binding building blocks (Appendix B.2). The rules for how the code uses them are in `CLAUDE.md`, which wins where the two disagree; fix this file in the same PR.

Each decision has a status:

- **Decided**: settled by `CLAUDE.md` (Stack, Database, Security and privacy) or the PRD. Changing it means changing those too.
- **Default**: the build plan's recommendation. It stands unless the owner changes it before the step that first builds it.
- **Open**: needs the owner's choice before the step named.

## T2: why Node runs the source

The owner chose this on 12 Oct 2026. Node 24 can run a TypeScript file directly by blanking out its type annotations as it loads it ("type stripping", Stable since Node 24.12.0). It needs every import to name the real file (`./config.ts`) and can't resolve tsconfig's `@/*` alias, so the choice was how to close that gap. Each option was built as a real server skeleton (Fastify, `ws`, Yjs, the three roles, a production-style install) on Node 24.21.0, and an independent check then tried to refute each result.

| | How production starts | Imports | Extra in the image | Startup, api role | What went wrong |
|---|---|---|---|---|---|
| **A. Node runs the source, `.ts` imports, `#src/*` map** (chosen) | `node src/main.ts` | `./x.ts`, `#src/x.ts` | nothing | about 330–390 ms, 101 MB | tsc accepts `./x.js` and decorators, which Node refuses; a guard and a CI start-up check close both |
| B. Node runs the source, plus a 33-line resolve hook | `node --import …/hooks.ts src/main.ts` | unchanged | nothing | 366 ms, 104 MB | `module.registerHooks` is a release candidate; every entry point must load the hook; a relative hook path breaks from another folder |
| C. The `tsx` runner | `node --import …/tsx/… src/main.ts` | unchanged | tsx and esbuild (12.5 MB) | 600–681 ms cold, 118 MB plus a 16 MB helper | slowest and heaviest; production depends on tsconfig files, the start folder and undocumented settings |
| D. A Vite bundle | `node --enable-source-maps dist/main.js` | unchanged | nothing (no source) | 324 ms, 95 MB | worker files and variable imports fail only in the bundle, which CI never ran |
| E. tsc output | `node --enable-source-maps dist/main.js` | `./x.ts`, `#src/x.ts` | nothing | 320–329 ms, 96 MB | eight config files; a missing project reference builds green and crashes at start; stale output lingers |

The same server as plain JavaScript started in about 300 ms and held 91 MB, and runs varied by 10–15%, so only C's gap is clearly larger than the noise.

**Decision: A.** Production runs the files developers edit, with nothing between Node and the code: no build, runner, hook or source map to keep in step, and no package in the image that exists only to run TypeScript, so a dependency update can't change how production code loads. Every entry point (the server, C0.3's migrator, the Owner bootstrap script, worker threads) is plain `node file.ts`, and stack traces name the exact `.ts` line and column. The cost is about 50 ms and 11 MB per process at start, which long-lived Fargate tasks barely notice, and a few gaps where tsc says yes and Node says no: `./x.js` imports, decorators and `accessor` fields, and package.json targets or JSON imports Node reads differently. `scripts/guards/server-runtime.test.ts` closes those, and CI's start-up check (`scripts/check-server.sh`) starts every role under plain Node. The source stays bundler-ready: Vite and Vitest read `.ts` imports and `#src/*` as they are, so if the server ever needs syntax Node can't strip, images without source, or a faster start, a bundle (option D) can be added without rewriting imports.

`#src/*` rather than `#/*`: TypeScript 5.9 doesn't resolve the bare `#/` key (TS2307), and older Node 24 releases refuse it (24.11 does). `apps/web` keeps `@/*`, which Vite resolves.

## T3: why Kysely, not Drizzle

The owner chose Kysely on 12 Oct 2026, on this comparison. Both are TypeScript libraries for talking to Postgres, and either could apply the migrations. The differences below were checked against the published packages (drizzle-orm 0.45.4 and drizzle-kit 0.31.11 with 1.0.0-rc.4, and kysely 0.29.6) in October 2026.

| | Drizzle | Kysely |
|---|---|---|
| What it is | An ORM: the schema is written in TypeScript, `drizzle-kit` generates SQL migrations from changes to it, and queries are typed from that schema. | A typed SQL query builder: no schema in TypeScript. The SQL migrations are the source of truth, and types are generated from the database (`kysely-codegen`) or written by hand. |
| What its schema covers | Tables, indexes, RLS policies, roles, views (with `security_invoker`) and sequences. Not grants, `revoke execute`, functions (`SECURITY DEFINER` included) or triggers. `CLAUDE.md`'s Database rules lean on all four, so those migrations are written by hand either way, and the TypeScript schema shows only part of the database. | Nothing. Every migration is written by hand, which is what `CLAUDE.md` already asks for. |
| How the migrator picks files | Stable (0.45): the files listed in `meta/_journal.json`, applied only if their journal timestamp is newer than the last migration applied. A migration made earlier on another branch and merged later is skipped without an error. | Sorted by name and tracked by name. By default it fails, rather than skipping, when a new migration sorts before one already applied or an applied one has gone missing. |
| Transaction and locking | The whole batch in one transaction. | The whole run in one transaction on Postgres, under an advisory lock so two deploys can't migrate at once. 0.30 (in beta) keeps that default as `transactionMode: 'per-run'` but warns it may change, so the migrator sets it explicitly once Hearth is on 0.30 or later. |
| Fit with `<NNNN>_<name>.sql` | Stable writes exactly that layout, which is where `CLAUDE.md`'s naming rule came from (until T3 was decided, `scripts/check-migrations.sh` also cross-checked Drizzle's journal). Version 1, still a release candidate, replaces the journal with a folder per migration named `<14-digit timestamp>_<name>/migration.sql` and refuses old folders until `drizzle-kit up` converts them. Adopting Drizzle means changing the naming rule and the check script at or before that upgrade. | Migrations are TypeScript modules by default, so reading the `.sql` files takes a small provider (about 30 lines). The naming rule stays, and C0.3 switches the check script to Kysely's migrator (`CLAUDE.md`, Database). |
| Day-to-day queries | `db.select().from(users).where(eq(users.orgId, id))`, plus a relational query API for nested reads. Friendly for simple reads; joins and raw SQL are possible. | `db.selectFrom('users').where('org_id', '=', id)`, close to the SQL it produces. This suits hand-tuned queries such as the access filter (`sqlReadableBy`) and keyword search. |
| Maturity | More widely used, with a larger community. Its 1.0 has been in beta since November 2025 and in release candidates since April 2026. | Smaller but steady, with a stable API for years; 0.30 is in beta. |

**Decision: Kysely.** Much of Hearth's schema is the part Drizzle can't model (grants, `revoke execute`, definer functions and triggers, all written to `CLAUDE.md`'s rules), and every migration gets a human read before merge. Generating migrations would cover only the easy part, while adding a second source of truth and a file layout that is about to change. Kysely's migrator already works the way `check-migrations.sh` assumes (name order, one transaction), and it fails loudly on an out-of-order migration where stable Drizzle skips it. The cost is writing table SQL by hand and regenerating types after each migration, which a `db:types` script run against the scratch database covers.

C0.3 built on it:
- **Migrator.** `kysely` 0.29.6 (the newest stable release; 0.30 is in beta) applies the files through a provider in `apps/server/src/db/migrations.ts`. The provider refuses any file Kysely would skip or not see. The connection takes `hearth_owner` at start-up, so a bad role fails at once and `RESET ROLE` goes back to it, and around each file the provider checks that the session is still `hearth_owner` and still in the run's one transaction, so a migration that commits or leaves another role in place fails, naming the file. A file that switches role and back is harmless only because the login has no rights of its own: CI's doesn't, and production's must not (`hearth_owner` itself, or a NOINHERIT login whose only membership is `hearth_owner`). 0.29 runs the whole batch in one transaction on one connection under an advisory lock and has no `transactionMode` setting; from 0.30 the provider's caller sets `transactionMode: 'per-run'` explicitly. `allowUnorderedMigrations` stays false.
- **Where it runs.** `apps/server/src/db/migrate.ts` is the pre-deploy migrate step, run from the server image, which carries `db/migrations/`. `scripts/check-migrations.sh` uses the same code on CI's scratch database, and `scripts/db-local.sh` on the local stack's.
- **Order against `main`.** A scratch build starts empty, so only `scripts/check-migration-order.sh` (CI, on every PR) can catch two PRs whose migrations merge out of order. It fails a new migration numbered at or below the highest on the base branch, and any change to a migration the base already has.
- **Types.** `npm run db:types` regenerates `apps/server/src/db/schema.ts` from the scratch database with a short generator in `apps/server/scripts/db-types.ts` that reads Postgres's catalogue, and CI fails if the file is stale. It replaces `kysely-codegen`: version 0.20.0 depends on `braces` 3.0.3 through `micromatch`, which has a high-severity advisory (GHSA-vfj7-8cjw-p6xm) with no fixed release, so it would fail the `audit` job. The generator adds no package, marks identity columns `GeneratedAlways`, and turns `in (…)` checks into string unions.

## T4: why Hearth's own queue, not pg-boss

The owner chose this on 14 Oct 2026, after pg-boss 12.37.0 was measured against this repository. pg-boss works on Node 24 and Postgres 17, but:

1. **Its schema breaks the rules CI enforces.** Its 13 tables have no `org_id` and no row level security, and its 6 functions are executable by PUBLIC, so every relevant check in `scripts/check-migrations.sh` fails on them. Allowing it would need a named exception to ACC-11 and to "RLS on every table" (`CLAUDE.md`). The only precedent is the migrator's own ledger, which nobody but its owner may touch, whereas a queue is read and written at run time.
2. **Its SQL commits inside itself.** Its construction and migration plans carry their own `BEGIN` and `COMMIT` and run `CREATE INDEX CONCURRENTLY` after the commit, which the one-transaction migrator refuses. Each of its schema versions (19 changes between January and October 2026) would be a hand-edited migration for the owner to read.
3. **It blocks rollback.** With `migrate: false` it refuses to start on any schema version but its own, older or newer, so an image older than the database's pg-boss schema can't start: no rollback across an upgrade (C0.11's "rollback rehearsed", INF-MIGRATE's expand and contract).
4. **What C0.6 is judged on is Hearth's to build anyway**: the outbox, the interrupted-awaiting-review state, cancellation by feature and purpose, the per-step checks, and exactly-once-in-effect inside `withOrg()`'s transaction. pg-boss provides none of them.

The cost is our own code (about 4,600 lines of TypeScript, comments included, in `apps/server/src/jobs/`, `outbox/`, `flags/` and `worker/`, and migration 0007's 900 lines of SQL) and its concurrency risk, which the race cases in `apps/server/scripts/check-concurrency.ts` and the integration suites cover (T15 to T17). There is no cron library either: the scheduler has its own five-field UTC evaluator (`apps/server/src/jobs/cron.ts`).

## T13: the access defaults for the owner to confirm or change

The PRD doesn't decide these, except items 1, 11 and 17, where C0.4 applies something stricter than the PRD's text. C0.4 applies the choice that fails closed, or the build plan's recommendation, and the Rule 1-9 suite and the role matrix pin each one. Changing one is a change to `packages/access` and its cases.

1. **Audiences (Rule 2, PRD-35, build-plan decision 9).** A space's audience is its readers now and later: a public channel or room is the whole org, a private one is its members including future ones, a session follows its stamp. PRD Rule 2's text still says "every current member"; this is stricter, so it never shows more than the PRD allows.
2. **Public channels** are readable by the whole org without joining (CHAT-01, PRD-35); joining changes membership and notifications only.
3. **Restricted rooms.** Admins and Compliance Officers restrict a room (REC-07, ADM-04: it narrows access); only the DPO or a Compliance Officer lifts it or reclassifies a past session (decision 13: it widens access). Until RMS-58 says who may join a restricted room, a restricted room on a public base can't be joined, and one on a private base only by its members.
4. **Owner includes every Admin power.** Only an Owner grants Admin, so an Owner is also an Admin for every admin action, except reading the audit log. That goes by the reader's own roles on the org's readers list (D45, as `read_audit_events()` checks), so an Owner who doesn't hold Admin reads it only while Owner is on the list (an Owner can add it).
5. **Accounts of Owner-only role holders.** Admins can't deactivate, reset the PIN of or change the phone of someone holding Owner, Admin, AI Admin, Leadership, DPO or Compliance Officer, or named in an open DPO or Compliance Officer proposal (otherwise an Admin could take over the account and then approve the grant to it, PRD-85); only an Owner can. Any Admin may still sign out anyone's devices (ACC-04), since that only removes sessions. With a single Owner, their own phone or PIN change needs a break-glass path outside the console. `can()` can't see an account an Admin took over before a proposal existed, so C0.16's approval screen should show the grantee's last phone or PIN change and who made it.
6. **Team membership** is changed by an Admin or that team's Team Admin, never by the person themselves through an admin power. Nobody joins an archived team, but an Admin can still remove its members (item 14).
7. **Default channels.** Org-wide defaults are public channels only; a team's defaults are public spaces, or private ones the team owns and the person setting them manages, never a restricted room. So a default can't pull people into a space none of them could open.
8. **Audit-log readers (D45).** An Owner changes any role on the list but Team Admin; an Admin can't add or remove Admin, Team Admin or any role they hold themselves, so no Admin gives themselves the log.
9. **Channel ownership transfer (ADM-03)** goes to an active person and, for a private channel, only to a current member, so an Admin can't take over a private channel they can't read.
10. **Managers (ACC-03, ACC-05).** An Admin sets a person's manager, in the console or a roster row, never naming themselves and never on their own record, since a leaver's items pass to their manager; another Admin or an Owner does it. The manager is an active person other than the person themselves. So a sole Owner is named someone's manager by an Admin, never in a roster row they import themselves.
11. **Drive items.** Every item has one owner, a person or a team; for a team-owned item the team's current Team Admins act as Owner (members get what an explicit grant gives them). Grants pass down from folders and add up; an item is never less shared than its folder. Owning a folder makes you an Editor of other people's items in it, never their Owner. Editors share up to Editor unless the Owner turns it off on that file or folder (FILE-03, decision 17), and never change the owner; a folder's grants still reach everything in it, whatever an item's own switch says. A team-owned item's Team Admins share it with the team itself like anyone else, and narrow or remove that grant. "Anyone can create in the current folder" (FILE-01) means Editors and up; My Drive is everyone's. The Owner is never a grant: it moves only by a transfer or ACC-05, to a person or a live team, never to the org. This narrows DOC-03, FILE-03, SHEET-27 and SLIDE-25, which list Owner among the roles granted to people, teams or the whole org (and the build plan's C0.4 prompt), because an Owner grant to a team or the org would give every member purge, transfer and restricted-editing powers. A FILE-01 org wiki folder is therefore owned by a person or a team, with a whole-org grant.
12. **Version history** is for Editors and the Owner, docs included, pending D40 (SHEET-26, SLIDE-24, Q19).
13. **The Drive's Trash.** An item in the Trash, or in a trashed folder, is readable only by its own owner and by whoever trashed it while they still hold a grant on it (DRV-01). Only the trashed item itself is restored (by its owner, or the trasher with Editor) or purged (by its owner). Legal holds are checked by the deletion code (C0.10), not by `can()`.
14. **An archived team's** Team Admins lose their powers, and grants to the team keep reaching its members. Nobody joins it, but an Admin can remove its members, so its grants stop reaching them. Its own Drive items then have no acting Owner: nobody transfers, purges, limits editing on or switches Editors' sharing on them through `can()` (Editors still share them while that switch allows), and no build step yet adds a way to move them to another owner (an open question: letting an Admin move them would let an Admin hand themselves items they can't read).
15. **Conversations.** A DM never gains members (a third person starts a group DM); only current members add people to a group DM, never an agent; anyone leaves a group DM. A chat attachment is readable by whoever reads its message (CHAT-06's "inherit the conversation's permissions", read as a floor, as folder grants are), so group-DM eras apply to it, and they hold Viewer on it. Like any Drive item, its Owner, and Editors they allow, can share it further (FILE-03); the share reaches only its grantees (people, a team or the whole org), never the conversation itself, and its index class stays its message's (Rule 4).
16. **Visibility.** A channel or standalone room can be made private by its owners; making a private one public would open its whole history and sessions, so it's refused until the owner decides who may.
17. **Tasks and events.** A task is read by its creator, assignees and team list (a private one by its owner only, Rule 5); its creator, assignees and team-list members edit it and its creator deletes it. An event is read by its organiser and invitees, and only the organiser edits or cancels it. A meeting's session stamps its invitees when it starts, so someone invited later doesn't gain an earlier recording. A task made from a restricted session stays restricted, never indexed, even after its owner shares it: sharing widens its readers only. This is a narrower reading of Rule 5's "unless the owner shares it"; lifting it would take the logged share confirmation Rule 5 describes for restricted output.
18. **Session actions.** Participants correct notes and see "viewed by" only while they can still read the session (REC-15, REC-21); nobody deletes a session or slide copy through `can()` (REC-23).
19. **What an admin request reveals.** An item someone can't read answers every content request exactly as a missing one (PRD-108). An admin request that names a room, session or channel tells the roles allowed it that the item exists, and a channel ownership transfer tells an Admin whether the new owner is in a private channel.
20. **Roster rows (ACC-03, PRD-85).** A roster add or CSV row carries the roles an Owner or Admin could grant directly, never DPO or Compliance Officer: those are granted once the person exists, as a proposal a second person approves, so an import can't skip the second approver.

## T14: the sign-in defaults for the owner to confirm or change

PRD-53 sets the code and PIN limits and `CLAUDE.md` the cookie, Origin and database rules; the owner decided item 2, and on 19 Oct 2026 the code for everyone with the PIN for PIN roles (D46), which C0.8 built: items 1 to 13 and 15 to 21 say how, and T20 has the rest. The others are C0.5's choices, and `apps/server/src/auth/sign-in.integration.test.ts` (with the unit tests, `db/tests/100_sign_in.sql` and `apps/server/scripts/check-concurrency.ts`, and from C0.8 `auth/codes.integration.test.ts` and the dormant passkey suite, `auth/passkeys.integration.test.ts`) pins each one. Changing a number is a change to `apps/server/src/auth/policy.ts` and its tests; the 90-day session cap and the PIN hash's cost are also in migration 0006, so changing those needs a migration.

1. **SMS provider.** The `SmsProvider` interface (`start`, `check` and `cancel`; T20 item 1) has three implementations: Twilio Verify, the local fake and `hearth-codes`, the AWS fallback's shape.
   - The fake runs only where `DEPLOY_ENV` is `local` or `test` **and** `APP_ORIGIN` is a localhost origin: config refuses it elsewhere, and `createFakeVerify()`, the one path `main.ts` takes, refuses the same independently. It prints each code to stderr with the number masked, never to the JSON log stream.
   - Tests use the fake's class, `FakeVerify`, which prints nothing, and the Twilio adapter's contract tests run on a loopback HTTP stand-in for Twilio (`apps/server/src/testing/fake-twilio.ts`).
   - Twilio runs only where `DEPLOY_ENV` is `nonprod` or `prod` and `APP_ORIGIN` isn't a localhost origin, and receives no number until C0.9 clears it in the transfer register (PDPA-10, T20 item 9).
   - With no provider configured, code requests answer "unavailable".
2. **Destinations: any country** (decided by the owner on 13 Oct 2026: "All numbers worldwide should be permitted, some team members live overseas").
   - A number is stored and compared in E.164 (`phone_numbers_e164`): a plus, a country code and at most 15 digits.
   - People type it with `+` and the country code, or `00` and the country code; spaces, dashes, dots and brackets are ignored. A bare 8-digit number starting 3, 6, 8 or 9 is taken as Singaporean (+65), since most of the team is there. Anything else needs the country code (`packages/shared/src/phone.ts`, which the web app uses too).
   - Codes still go only to roster numbers, every number gets the same reply, and the cap on code sends holds, so accepting any number sends nothing to strangers.
   - Before real codes are sent: C0.9 records Twilio in the transfer register (PDPA-10), since Twilio receives every number that signs in and every code, in the United States, not only texts to overseas numbers; and a person sets Twilio's Fraud Guard, its Geo Permissions and each country's sender rules (Singapore's SSIR registration covers only Singapore) from a runbook (C0.12, C0.19; T20 item 11). They take the place of the AWS spend limit and the worldwide destination list C0.5 planned.
   - The proposed Geo Permissions allow only the team's countries. That narrows this item's "any country", so it waits for the owner's confirmation (T20 items 11 and 16). Under it, a roster number from any other country gets no sign-in code, and its reply is the same as everyone's, so the person can't see why; the server logs the refused send at error (`sms_send_failed`). So the runbook adds a country before a number from it joins the roster.
3. **Numbers not on the roster.**
   - They get the same status, body, cookie and limits as a roster number, and every code is wrong.
   - Nothing touches Postgres before the reply. The roster lookup, the audit row and the send all run after it, so the reply's timing can't show whether a number is on the roster. They run even when the client hangs up before the reply, so it can't keep a request or a failed code out of the audit log.
   - No SMS is sent, no audit row is written, and the number is stored nowhere: Valkey keys and sign-in state hold a keyed hash. The log gets a line without the number.
   - A current number of someone who has left gets no SMS, and an audit row with them as the target.
   - A number current in two orgs counts as not on the roster, and the log gets an error without the number.
   - A sign-in attempt names the person only on the way to sending their code: once the number is found current, the person still at the org, the provider cleared (T20 item 9) and the global cap not reached, and just before the code's audit row is written and the provider is asked to make and send the code. If the audit row, the commit or the send then fails, the attempt still names them, but no provider reference reaches its challenge record, so there is no code to guess and every guess answers wrong. When the transfer gate or the global cap stops a send, the attempt names nobody.
   - A refused check of a roster number's code waits for the provider's round trip, and one off the roster's doesn't, so every refused check answers no sooner than 2 s after it arrived (T20 item 3).
   - Residual: the per-number windows are shared, so a 429 before your own 3rd request shows that someone asked for that number's code in the last 10 minutes. `Retry-After` is rounded to the minute so it doesn't date it.
   - Residual: a number has one code at a time, owned by the browser that asked last, so a check that answers "expired" (`code_expired`) within the code's 5 minutes and before its 5th wrong try shows that another browser has since asked for that number's code. That takes one code request and one check, and when it happens to a roster number it usually means its owner is signing in. It answers alike for every number, on the roster or not, since a request replaces the number's challenge record before the roster is read; a check already under way when the newer request lands answers from its own try instead (T20 item 2).
   - Residual (C0.8): the floor hides the provider's round trip only while Twilio answers within 2 s, so a slower check shows that a number is on the roster.
   - Residual (C0.8): while the provider fails, a roster number's check answers 503 "unavailable" (its try given back, and no sooner than the 2 s floor, as a refusal is) where one off the roster answers "wrong", until three failures within a minute open the breaker and every check answers 503 for 30 s (T20 item 3). So the reply's content tells them apart, and its timing only as the slow-check residual above says.
   - Residual (C0.8): a sign-in request for a number replaces any pending code for it, a re-authentication code included, and then texts the number a sign-in code. So anyone who knows a Member's or Team Admin's number can cancel their pending SMS re-authentication code, at most 3 times per 10 minutes and 10 a day (the per-number windows), and each time the owner gets a sign-in code they didn't ask for. It can't block re-authentication outright (the person asks again), and PIN-role holders re-authenticate with the PIN (T20 item 6).
4. **Codes.** 6 digits, made and checked by the provider (C0.8 AQ-03): Twilio Verify makes them, and `hearth-codes`, the AWS fallback's shape, would make them from `crypto.randomInt` and keep only a MAC of each in its reference. Hearth stores no code: the number's challenge record holds the provider's reference and a count of tries (T20 item 2). A code is valid 5 minutes from the request on Valkey's clock, whatever the provider's own validity; it works only for the attempt that asked for it (one residual, after a provider glitch: T20 item 2's foreign check), 5 tries kill it, and a new request for the number replaces it.
5. **Limits.**
   - Per number: 3 code requests per 10 minutes and 10 per rolling 24 hours (PRD-53), and at most 10 code checks per rolling 24 hours, counted the same for every number. A check the provider never answered counts against no day's checks: one the open breaker refuses counts in no window, and one the provider fails is given back (T20 item 3), so retrying through an outage can't lock a number out of sign-in for the day.
   - Per IP: 30 code requests per 10 minutes, and 100 sign-in requests of any kind per 10 minutes (loose, because a whole office may share one address). An IPv6 client counts by its /64.
   - All numbers together: 600 code requests per hour, refused with the same 429.
   - At most 100 code sends asked of the provider per rolling hour across the deployment (`sms-global`), re-authentication codes included. It counts each code request Hearth delivers once, so a start's one retry after a network error or a 5xx (when the provider had sent already), and a foreign reply's cancel and second start (T20 item 2), can each add a text it doesn't count. Above that, sign-in codes are silently not sent and an error is logged (an alarm in C0.13), and a re-authentication code request answers "unavailable".
   - Per session: 10 re-authentications per 10 minutes, the PIN and SMS code requests and checks alike. For the PIN it lets requests through with Valkey down, because the PIN lock in Postgres still bounds guessing; for an SMS code it fails closed (C0.8 AQ-10).
   - Per person: 20 re-authentication code requests and 20 re-authentication code checks per rolling day (T20 item 6); a check the provider never answered (the breaker open, or the provider failing) is given back. Re-authentication codes don't count against sign-in's per-number windows.
   - Every refused sign-in code check answers no sooner than 2 s after it arrived, and after 3 provider failures within a minute every check answers "unavailable" for 30 s (T20 item 3).
   - At most 2 PIN hashes run at once per process, with 16 waiting; beyond that, "unavailable".
   - All windows slide, timed by Valkey's clock, in one Lua script.
   - With Valkey down, code requests and checks answer "unavailable" (fail closed), and signed-in requests carry on.
   - Every window, code challenge, attempt and passkey challenge in Valkey expires, so the Valkey that holds them must never evict a key (`noeviction`, set in C0.12): a `volatile-*` policy evicts exactly the keys that expire, which would restart these windows. A full Valkey then refuses writes instead of dropping keys, so the counts hold, and a code request or check whose write is refused answers "unavailable".
6. **Sessions.** They last 90 days from sign-in, or 7 days for a session issued under the PIN rule (T20 item 7): a fixed lifetime, set at issue, that the schema caps at 90 days. They end after 30 days without use (computed at lookup from `last_seen_at`). `last_seen_at` is written at most once a minute, after the response. The database, not the server, writes a session's start, last-seen and re-authentication times, so no write can stretch them. There is no session cache: every request looks its session up in Postgres, so a revocation counts at once over HTTP.
7. **New devices.** Every sign-in without a live session needs the SMS code, and a PIN-role holder's needs the PIN too (passkeys are switched off, D46). There is no device cookie, and each sign-in makes a device row. The device list shows devices not signed out that hold a live session, labelled from the User-Agent ("iPhone · Safari"), which isn't stored. There is no location.
8. **The PIN.** Only PIN-role holders have one (D46, T20 item 5): they set it at their first sign-in, after the code, and enter it at every later one.
   - Exactly 6 digits. One digit repeated, ascending or descending runs, and a short list of common PINs are refused (SHL-49). Dates (DDMMYY and the like) are allowed: refusing them would remove about a tenth of all PINs, and the lock allows at most 10 guesses before an admin reset. The owner may choose otherwise.
   - argon2id through Node's built-in `crypto.argon2` (Stable from Node 24.19; a release candidate on the 24.12 floor, with the same behaviour), m=19456 KiB, t=2, p=1, a 16-byte salt and a 32-byte tag, stored as a PHC string. Only that cost is accepted; raising it is a migration.
   - A pepper derived from `AUTH_SECRET`, with its key id beside the hash. Rotation (`AUTH_SECRET_PREVIOUS`: verify under the old pepper by key id, rehash on the next correct PIN) isn't built in C0.5 or C0.8. It must exist before anyone sets a real PIN, which from C0.8 means before any PIN-role holder signs in for real; the C0.12 row carries it. Until then, changing `AUTH_SECRET` makes every PIN need an admin reset.
9. **PIN lock.**
   - Failures are counted per account in Postgres, at sign-in and re-authentication alike, and committed before the reply. The database stamps when the last one happened.
   - Each failure from the 5th locks the PIN for 15 minutes after it. The 10th locks it until an admin resets it.
   - A correct PIN resets the count.
   - With passkeys switched off (D46) nothing stands in for a locked PIN: its holder waits out the 15 minutes, or, from the 10th failure, asks an Owner for a reset. The dormant passkey code still works while the PIN is locked and leaves the count alone.
   - The check locks the account's row `NOWAIT`: a second check of the same account at the same moment answers "try again" rather than queueing.
10. **Passkeys** are kept and switched off (D46, T20 item 8): their routes aren't registered, and the step-up reply and the device list carry no passkey key. What follows holds for the dormant suite, which switches them on, and for a reviewed switch back on.
    - SimpleWebAuthn, with the RP ID the app origin's host and the expected origin the app origin; attestation none; user verification required; EdDSA, ES256 and RS256; discoverable credentials preferred.
    - Challenges are single-use and live 2 minutes in Valkey. The user handle is random.
    - A passkey is only ever the step after the SMS code, or a re-authentication.
    - Adding or removing one needs a re-authentication from the last 5 minutes.
    - Passkeys are kept, unusable, when someone leaves, and kept after a PIN reset.
    - Passkeys are bound to the app's host name, so production's must be final before anyone registers one.
11. **Re-authentication.** Decided by the session (D46, T20 item 6): one issued under the PIN rule re-authenticates with the PIN, never SMS; any other with a fresh SMS code to the person's own number; and one that neither mends (a PIN role reached a code-only session, or a PIN-rule session's PIN was cleared) only by a new sign-in. The dormant passkey route takes only a session whose method is the PIN. Each re-authentication stamps the session, and a sign-in stamps the session it issues. Admin actions, and adding or removing a passkey (item 10), need a stamp from the last 5 minutes on a session whose method is still the PIN or an SMS code: `reauthenticated()` in `packages/access` is false for one that only a new sign-in mends, however fresh its stamp.
12. **Admin PIN reset (ACC-06).** Through `can()` (T13 item 5). Only PIN-role holders have a PIN, and only an Owner acts on them, so in practice only an Owner resets a live PIN; an Admin may still clear a former holder's leftover one. Someone with no PIN answers 409 `no_pin`. It records the identity check (in person or by video call) and an optional note. It clears the PIN and its failure count, ends the person's sessions (`pin_reset`), including one from a sign-in in progress, and keeps their passkeys. A PIN-role holder then signs in with the code and sets a new PIN on the code alone, so they sign in straight away, with the Owner present or on the call (the enrolment window, T20 item 12); a former holder signs in on the code alone. A sole Owner's own reset waits for the bootstrap script's break-glass path.
13. **Deactivation (ACC-05).** A trigger ends open sessions (`deactivated`) and signs devices out in the same transaction. No session, device or passkey starts for someone who has left (read FOR SHARE), and a sign-in step for someone who left meanwhile is refused before any PIN check, a right code answered as a wrong one. So is every step for a number removed or moved since its code was asked for: no code is sent, a right code is answered as a wrong one, and a PIN or passkey step drops the attempt with nothing counted or shown (ACC-03). Their phone number stays current until C0.16 decides. The api publishes the sessions it ended after the commit, so sockets close at once; the worker's revocation consumer (T19 item 4) closes them durably, and its offboarding consumer runs every offboarding handler as a retried job (T16 item 9; C0.6). Deactivating someone already deactivated answers success with nothing ended.
14. **Sockets.**
    - `/ws` is served on the realtime role only, and the sign-in routes on the api role only.
    - At upgrade the server checks the Origin, then the session cookie. At most 8 sockets per session, and a frame over 4 KiB closes the socket.
    - Sockets close with 4401 on revocation, 1013 when their session can't be confirmed in time, and 1001 at shutdown.
    - The api publishes after its commit, and the realtime role re-checks every 15 seconds. A re-check that hasn't answered within 10 seconds counts as failed, so the next one still runs. The realtime role subscribes to its channels again itself after Valkey reconnects.
    - A failed re-check closes no socket as signed out: Postgres being down isn't a revocation. But a session's sockets close with 1013 once the next re-check, failing too, would leave the session unconfirmed for more than 60 seconds, since a revocation message may have been lost meanwhile. A single failed re-check closes nothing. The client reconnects, and the upgrade's own lookup decides.
    - Heartbeat, topics, reconnects (re-authorise and refetch) and the protocol: T19.
15. **Cookies.** Both are written by hand, with no plugin:
    - `__Host-hearth_session`: HttpOnly, Secure, SameSite=Lax, Path=/, for the session's lifetime: 7 days for one issued under the PIN rule, 90 days for any other;
    - `__Host-hearth_attempt`: HttpOnly, Secure, SameSite=Strict, Path=/, 10 minutes.
16. **Routes.** `/api/auth/*`, `/api/devices*`, `/api/admin/*`, from C0.8 `/api/session`, `/api/flags` and `/api/csp-report` (T21 item 10), and from C0.9 PR 2 `/api/notice` and `/api/notice/acknowledge` (T22 item 26) are on the api role, and `/ws` on the realtime role, all on the app's own host. Every state change is a POST, and every response under `/api` is `no-store`, an `/api` path with no route included: it answers 404 before any body is read.
17. **Audit codes.**
    - `auth.code_requested` (roster numbers only), `auth.code_failed`, `auth.sign_in`, `auth.pin_set`, `auth.pin_failed`, `auth.pin_locked`, `auth.passkey_added`, `auth.passkey_removed`, `auth.passkey_failed`, `auth.reauth`, `auth.sign_out`, `auth.device_sign_out`, `person.deactivate`, `person.reset_pin`, `person.sign_out_devices`.
    - Never `session.*`, which names voice-room sessions.
    - The details (C0.8, D46): `auth.code_requested` carries `send` (`attempted`, `skipped_left`, `skipped_number_removed`, `skipped_not_cleared`, from C0.9 PR 2 `skipped_no_notice` or `skipped_unstated` (T22 item 27), or `skipped_cap`) and, for a re-authentication code, `during: 'reauth'`; `auth.code_failed` carries `result`, and `during: 'reauth'` for one; `auth.sign_in` carries `method` (`sms` for the code alone, `sms_new_pin` and `sms_pin` for a PIN-role holder, and the dormant `sms_passkey`) and `pinRule`, whether the session was issued under the PIN rule; `auth.reauth` carries `method` (`pin` or `sms`, and the dormant `passkey`). The `auth.passkey_*` actions are written only while passkeys are switched on.
    - Each row carries the device, IP and request id where known.
    - The target is always the person whose account it is. The actor is empty when whoever held the phone wasn't yet known to be them.

19. **Access requests.** `devices.list_own`, `devices.sign_out_own` (optionally naming a device), `passkeys.add_own` and `passkeys.remove_own` (both needing a fresh re-auth; their routes are dormant while passkeys are switched off, D46), the admin `person.list_devices`, and, from C0.8, `session.read_own` (`GET /api/session` and `GET /api/flags`, T21 item 10), for any active person, without re-authentication, with role-matrix rows. The admin device list shows dates, not times; your own list shows times.
20. **Transactions and locks.**
    - Lock order: people → users → passkeys → phone_numbers → devices → sessions. C0.6 extends it with role_assignments → feature_flags → jobs → schedule_runs (`CLAUDE.md`, Database; T15, T17). A sign-in's finish reads the person's roles after their row, as its own statement with no lock on `role_assignments`, and from C0.16 a grant that gives someone a PIN role locks their person row, ends their sessions, then writes the role row (people → sessions → role_assignments; T20 items 5 and 14).
    - Sign-in and re-authentication read the person `FOR SHARE` first. Anything that ends some or all of a person's sessions locks the person's row first: `FOR NO KEY UPDATE` when it may end more than one device's sessions, so a sign-in in progress finishes first and is then ended too, and `FOR SHARE` when it ends one device's or one session's.
    - Every state change re-reads the acting person, device and session `FOR SHARE` in its own transaction before deciding with `can()`. An admin action on someone else is an exception to the lock order: the actor's own person, device and session rows come first and that person's after. A PIN reset or device sign-out locks their row `FOR NO KEY UPDATE` only once `can()` has allowed it, and `can()` then decides again, so a deactivation in progress is seen; a caller `can()` refuses never waits on or holds that row. Two admins acting on each other at the same moment can deadlock, and then one of them gets 409.
    - Every request transaction waits at most 2 s for a row lock. A deadlock or lock timeout answers 409 "try again".
    - The pre-org lookups run with `synchronous_commit` off, because they write only row locks.
    - Before a session exists, transactions act as the org's system principal, never as the person.

## T15: the queue and scheduler defaults for the owner to confirm or change

BUILD-PLAN C0.6 sets "exactly-once-in-effect", the interrupted state and the checks before each step (Part 1D, row C0.6), and AGT-10 the review of interrupted runs; the owner decided T4. The rest are C0.6's choices. `apps/server/src/jobs/jobs.integration.test.ts`, the unit tests beside each module in `apps/server/src/jobs/`, `db/tests/120_queue.sql` and `140_schedules.sql`, and the race cases in `apps/server/scripts/check-concurrency.ts` pin each one. Changing a number is a change to `apps/server/src/jobs/policy.ts` and its tests; the clean-up's ages are in migration 0007, so changing one needs a migration.

1. **Claims.**
   - Per org, in a `withOrg()` transaction as `hearth_queue`, up to the worker's free slots (`WORKER_CONCURRENCY`, default 4), oldest `run_after` first, only kinds this worker knows.
   - A job whose feature, or any flag above it, is off in Postgres isn't claimed, so a stale copy of the flags never starts one, and nothing is claimed for an org whose flags the worker hasn't confirmed (item 11).
   - A claimed job whose feature or purpose differs from its kind's registry entry is never run: it goes dead (`job_mismatch`), because the gate and the fence judge the kind, not what a producer wrote.
2. **Leases.**
   - 30 s, renewed by one heartbeat statement per org for all its running jobs, each org's in its own transaction and on its own cadence: every 10 s, start to start (so a slow renewal doesn't push the next later), the first 10 s after the org's jobs' leases were set. A job that joins an org already renewing makes the org's next renewal start no later than 10 s after that job's lease was set (its claim, or a slow claim's renewal below) or, if a renewal that began without it is still in flight then, as soon as that one ends; otherwise it could wait up to a whole interval after it started. Never two heartbeats at once for one org (a renewal still in flight when the next is due delays only that org's, which starts as soon as it ends). An org waiting on a slow or hung renewal holds up no other org's, as long as a slot is free: at most 2 heartbeat renewals run at once across all orgs (`renewalsInFlight`, so the heartbeats hold at most 2 of the control pool's connections, T18 item 8), and an org due while both are taken waits for one to end, earliest due first. Both limits count heartbeats only: a slow claim's renewal of its own jobs before they start (below) is separate, renews other jobs than the heartbeats do, and runs on the one connection the claim loop holds. So if 2 renewals hang at once (`BEGIN` or `set_config` on a silent connection waits for the pool's 31 s `query_timeout`, which `statement_timeout` doesn't cover), every other org's renewals wait too and the watchdog below stops their jobs (`lease_lost`): fail safe, never a job run twice. Renewals that are slow without hanging have a limit too, since the watchdog below stops a job once the renewal that last reached it began 25 s ago. A job's renewals can't start closer together than its org's interval or one renewal's length, whichever is longer; past two orgs the cap spreads them further, to about N·d/2 apart for N orgs whose renewals each take d seconds; and a job that joins after a slow claim can wait for the claim's renewal, then one in flight without it, then its own. Fake-timer runs of the real runner, every renewal held d seconds for 300 s, first lost a job at d = 12.75 s with one or two orgs and 8.25 s with three or four, and at about 8 s with one org once slow claims join it; a transient spike does worse. So at the default `WORKER_CONCURRENCY` of 4 (at most 4 orgs with running jobs) every lease holds while renewals stay under about 8 s; Hearth serves one org (D1). Past that, jobs are aborted as `lease_lost`, safe as below (nothing written, never run twice), and the lease sweep treats each like any expired lease: the attempt counts, so a job whose renewals stay that slow ends dead (`lease_expired`), and a review run's job is interrupted (`crash`). Renewals are matched by lease token (not job id), so a job whose lease ran out while its handler went on can be claimed again, even by the same worker, without the two attempts being confused.
   - A heartbeat that fails (an error, a busy pool) is tried again for its org 1 s after it ended (a tenth of the interval), not at the next tick; each heartbeat statement is bounded to 10 s (`statement_timeout`: a third of the lease at most, and short enough that a heartbeat begun on time ends before the watchdog below would stop the job). One that renews no row for a job aborts that job (`lease_lost`), unless its finishing commit is in flight, which then reports for itself, or has committed (item 3).
   - The runner keeps, per running attempt, when the statement that last renewed its lease began (its claim, or the last heartbeat that succeeded for it). A claim whose transaction took longer than 5 s (the lease less the margin below, a heartbeat interval and a heartbeat's bound) would leave its jobs too little lease before their first heartbeat, so it renews their leases first and each job counts from that renewal; a job the renewal doesn't renew (the sweep took it) or can't (it failed) never starts, and its lease is left to run out. The database set the lease from its own `now()`, which is no earlier, so the lease lasts at least 30 s from then. Once that is 25 s ago (the lease less a margin of half a heartbeat, which leaves several watchdog ticks for the abort to land before the lease runs out and the sweep, every 5 s, can requeue the job), whether the heartbeats fail or hang, the watchdog (every second) aborts the attempt (`lease_lost`, nothing written), so two workers never run one job at once; `job_finish()`'s fence still stops a double commit from a process frozen past its lease. An attempt whose finishing commit is in flight or has committed is never aborted for this (item 3).
   - The scheduler sweeps leases every 5 s (`FOR NO KEY UPDATE OF j SKIP LOCKED`, so it passes by any job a finishing transaction holds). A job whose lease ran out goes back to the queue (the attempt counts), or dead with no attempts left (`lease_expired`). A review run's job isn't retried: its run becomes interrupted (`crash`).
   - Claims, heartbeats and outcomes pass the lease in milliseconds.
3. **Exactly once in effect.**
   - Delivery is at least once. A job's effects in Postgres commit exactly once when it makes them in its finishing transaction (`job_finish()`), and every transaction a job commits in ends with its fence (`job_fence()` or `job_finish()`), so a worker whose lease went elsewhere (`HF002`), or whose flags changed (`HF001`), commits nothing.
   - A kind that commits in several transactions makes each commit idempotent, because a retry starts it again from the top, and says so (`idempotentCommits: true`). Any other kind's non-finishing commit is a permanent error (`commit_not_idempotent`), so the job goes dead rather than retrying a bug, and a commit after `job_finish()` is refused (`commit_after_finish`).
   - Effects outside Postgres (a Valkey publish today, a push or a model call later) happen after a commit and must be idempotent, as offboarding handlers are.
   - Once `job_finish()` has committed the job has succeeded: nothing aborts it after that (no lease loss, watchdog, flag change, timeout or shutdown), and nothing retries it. So an effect after the finishing commit happens at most once (a crash loses it), and an effect that must happen goes before the finish and is idempotent, as the revocation handlers' publishes are (T19 item 4).
4. **Retries.**
   - Per kind: at most 5 attempts unless it says otherwise (1 to 100), back-off from 5 s doubling to a cap of 10 minutes, ±20% jitter, and 5 minutes an attempt.
   - A deadlock (`40P01`), lock timeout (`55P03`), transaction timeout, lost connection or any unexpected error retries (`error`, or `timeout` for the attempt's own limit). A transaction timeout reaches the server as a lost connection with no SQLSTATE, because Postgres ends the connection, so a lost connection counts as retryable.
   - A constraint failure (`23xxx`, `constraint_failed`), a `PermanentJobError` (its own code) or a payload its schema refuses (`payload_invalid`) goes straight to dead.
   - A1's "retry for up to 24 hours" (B.5) is A1's choice of attempts and cap.
5. **Dead letters.** A dead job keeps a reason code, never an error message (no personal data in job rows), is logged at error level (`job_dead`, plus a second line naming the case where there is one: `job_mismatch`, `job_give_back_limit`, `job_kind_unknown`, or the kind's own, such as `offboarding_handler_dead`) with its failure's diagnostic fields, counted in every `queue_depth` line, and kept 30 days. There is no re-run in C0.6; C0.16's console should add an audited one before any destructive handler ships.
6. **Given back, uncounted.**
   - A job aborted because its org's flags went unconfirmed or the worker is stopping goes back at once without counting the attempt, and `give_backs` counts it. At 20 give-backs it goes dead (`give_back_limit`), so a job that blocks the event loop past the flag watchdog, or that every deploy cuts short, can't cycle forever.
   - A job given back because a flag changed but its feature is still on for it (`flag_changed`), or because an essential feature was switched off (`flag_off`), doesn't count: a person's action caused it, and each is bounded by those actions. Nor does an optional job waiting under its spend cap (`over_cap`, 5 minutes): the cap resets, and A0, which builds caps, may bound the wait.
   - Every abort (a flag change, the watchdog, a timeout, shutdown, a lost lease) decides and writes the job's outcome at once, under the lease, without waiting for the handler, which can no longer commit (its fence finds the lease gone).
7. **Idempotency.** An optional key per (org, kind): adding the same key again adds nothing (`ON CONFLICT DO NOTHING`, which needs only INSERT). A key lasts as long as its row (14 days after the job finishes, 30 if dead). A key is codes (a lower-case letter, then letters, digits and `_`) and uuids joined by `:` (`run:<uuid>`, `<uuid>:sockets`), never content: `enqueue()` and the column's CHECK both refuse anything else.
8. **Payloads** hold ids only. The guarantee is each kind's payload schema, whose every field is a uuid, an enum, a boolean or a bounded whole number (a unit test walks them); the database's `is_ids_only()` check is the backstop. Offboarding's handler names are therefore a fixed list (`OFFBOARDING_HANDLERS`), which each later handler joins.
9. **Cancellation when a flag changes.** PRD-65 sets "≤10 s" and "zero posts afterwards"; the split is C0.6's.
   - The worker hears a change within 10 s and re-evaluates each running job of the feature for its person. An optional feature's running and queued jobs are cancelled (`flag_off`). An essential feature's running jobs are given back, uncounted, and with its queued jobs wait unclaimed until the flag returns, so a backlog drains then (A1: "killed and the backlog drains"). The flag's class sets the default; a kind may override it (`onFlagOff`).
   - A job whose person a narrowed cohort leaves out is cancelled (`not_in_cohort`) whatever the class: the claim can't evaluate cohorts, so a job given back would only be claimed and refused again.
   - No effect commits after the change whatever the propagation, because every fence locks the flags `FOR SHARE` and compares their revisions with the ones the worker checked, and every change bumps a revision (off, a narrowed cohort and a lock all count). A fence refused only because a flag changed while the feature is still on for the job's person (a widened cohort, say) gives the job back at once, uncounted, so a commit in flight across a change starts again in a new claim.
   - The fence covers flag changes only. A running attempt keeps the cohort membership read when it was claimed (its person's org-wide roles and whether they're still at the org), re-read at every claim, so a role revoked or a person deactivated while it runs applies from the next claim, within the kind's `timeoutMs` (T17 item 3). The first cohort-gated job kind that touches personal data (A0) re-reads its subject inside each commit.
10. **The gate.** BUILD-PLAN asks for the checks; where they run is C0.6's, and what fills them C0.9's.
    - The runner admits a job before `run()`, and `ctx.step(name)`, `ctx.read()` and `ctx.commit()` admit it again (a read touches personal data). Each admission takes the kind's registry entry, never the job row, and checks in order: the job isn't aborted; its feature is confirmed on for its person; the purpose gate allows its purpose; every provider it names is cleared (PDPA-10); its person's processing switch allows its purpose; its optional feature isn't over its spend cap. Outbox consumers pass the same gate each round (T16 item 3).
    - `validateRegistries()` refuses, until A0, any kind or consumer whose purpose is an AI purpose or whose feature is under `ai.`.
    - C0.9 replaced C0.6's stand-ins (`C06_GATE`, now gone) with the gate over the registers: `registerGate()` (`apps/server/src/compliance/gate.ts`), the worker's default, over the copy its flag cache reads (T22 items 6, 7 and 9). AI purposes are refused; a purpose passes as T22 item 6 says, which until a published notice lists another purpose at its current version means only the pinned ones; a provider counts as cleared only while its entry has an open clearance and, from C0.9 PR 2, the published notice states it or no generated version exists yet (T22 item 27); a person's processing switch is T22 item 7's; nothing is over a cap until A0 builds caps. The cap check can only ever pause an optional feature, in code (`CLAUDE.md`, AI).
    - What a refusal does is unchanged: `purpose_refused`, `provider_not_cleared` and `processing_not_allowed` cancel the job whatever its class, so `cancelled` covers more than migration 0007's comment on `jobs` says; `over_cap` gives it back for 5 minutes; and a consumer's refused round keeps its place. G3 in `validateRegistries()` keeps that safe until the runner waits on a refusal: a kind whose work waits while its flag is off serves only a pinned purpose, and names no provider, nor does any kind under a locked-on or essential flag (T22 item 10).
11. **Unconfirmed flags.** A worker that hasn't confirmed an org's flags for 8 s treats every flag not locked on as off: it claims nothing for that org, no step starts, and a watchdog (every second) aborts its running jobs and gives them back uncounted (item 6).
12. **Shutdown.** On SIGTERM the worker stops claiming and firing, gives running jobs 3 s to finish, aborts the rest (`shutdown`) and gives them back within 1 s more: uncounted (item 6), or for a review run, interrupted. `stop()` races all of this against a hard 5 s deadline and leaves whatever is still in flight to lease expiry, so a handler that ignores its signal, or a statement stuck on a lock, can't hold the process. It fits inside the server's 10 s; C0.11 can lengthen the drain within ECS's 30 s stop timeout.
13. **Schedules.**
    - Five-field cron in UTC (minute, hour, day of month, month, day of week; lists, ranges and steps; no names or `L`, `W`, `#`), read by the server's own evaluator (`apps/server/src/jobs/cron.ts`), so no dependency.
    - Occurrences come from the database's clock (`now()` read in the firing transaction), never the worker's. One run per occurrence (`unique (org_id, schedule_id, scheduled_for, attempt)`), and a firing whose run already exists queues no job.
    - A firing takes the later of `next_run_at` and the latest occurrence at or before now, so occurrences missed while no worker ran fire once, as the latest, with the count logged (`schedule_missed`, counted up to 1,000).
    - A review schedule whose org's flags are unconfirmed waits for the next tick rather than firing or being skipped.
    - The registry writes its schedules to every org (at start, every 10 minutes and for a new org): it inserts missing ones and retires the keys it lists as retired, and never updates or un-retires a row (`schedules.origin` is `registry` only until A5 widens it). A row that differs from the registry is logged once (`schedule_differs`), never changed; payloads are compared whatever order their keys are in.
    - A due row that can't fire (a cron the evaluator can't read or that never matches, or a payload its kind's schema refuses, as after a rollback to a version with a stricter schema) is logged once at error level by key, never with its payload (`schedule_unreadable`), and passed over by that process from then on, so it neither rolls back the org's other firings nor takes a place in the batch.
14. **Local time.** PRD-61's "09:00 local on the day" and quiet hours are delayed jobs whose `run_after` is computed in UTC from the person's IANA zone when queued and recomputed when the zone changes, not schedules (C2.1, C3.1 and C0.14 build them); C2.1's `task.overdue` is such a job, which appends the event when it runs. A local time that doesn't exist (spring forward) runs at the next minute that does; one that happens twice runs once, the first. Recurring local-time schedules (A4's digests, A5's "Mondays 9:00") add a time zone column and a zone-aware evaluator then.
15. **Interrupted runs.** AGT-10 sets the state; who and which are C0.6's.
    - Only a `review` schedule's runs wait for a person. Every non-success end of one (a crash, shutdown, a flag turned off or changed, a timeout, a failure, unconfirmed flags, an unknown kind) makes its run interrupted with that reason, logged at error level (`schedule_run_interrupted`) and counted in `queue_depth`. A `rerun` schedule's runs are retried like any job.
    - Both C0.6 schedules are idempotent maintenance, so `rerun`; A4's and A5's will be `review`.
    - C0.6 builds the state, its columns and constraints, and the clean-up's handling of every run state (an interrupted run is never purged; nor is a resumed one whose next attempt doesn't exist yet). Deciding a run (resume or dismiss) and the scheduler's queueing of a resumed run's next attempt come together with the first review schedule (A4 or A5.4), with the checked, audited `review_schedule_run()`, its access action and its console screen, because before then no run can wait. Until then `hearth_queue` can't insert a run's `attempt` or `resumed_from`.
16. **Partitions.** `CLAUDE.md` gives the job its own role; the schedule is C0.6's. Daily at 03:17 UTC, `create_data_access_partitions(12)` as `hearth_job_partitions`, in one transaction that waits at most 1 s for a lock, takes a database-wide advisory lock (with several orgs one run creates and the rest find nothing to do), calls the function and ends with `job_finish()`. Creating a partition takes an ACCESS EXCLUSIVE lock on `data_access_events`, so the job gives up after a second and retries (30 s doubling to 10 minutes, 20 attempts) rather than stall the busiest log. Daily rather than monthly (BUILD-PLAN C0.6 said monthly): the function is idempotent, creates at most one partition a month, and a missed run heals the next day. (Migration 0005's comment still says monthly; a migration on `main` never changes.)
17. **Clean-up.** Daily at 03:47 UTC as `hearth_job_purge`, acting as the org's Hearth system principal (the functions refuse anyone else, so the audit row names Hearth), only through `purge_outbox()`, `purge_jobs()` and `purge_schedule_runs()`, `SECURITY DEFINER` functions that fix the ages in SQL so no worker bug can delete early: outbox events after 14 days (by position, T16 item 6), succeeded and cancelled jobs 14 days after they finished, dead jobs after 30, finished schedule runs after 90, decided ones 90 days after the decision, and never a run waiting for review or a resumed run whose next attempt doesn't exist yet. Each call deletes one batch of at most 5,000 rows and writes one `maintenance.purge` audit row in the same transaction, never one per row. C0.10 registers these as retention classes.
18. **Producers.** Only the worker's own roles queue jobs: `hearth_queue` for scheduled runs, `hearth_job_offboarding` for offboarding (C0.6) and `hearth_job_revocation` for revocation (C0.7). `jobs.created_by` is the acting principal, which no producer chooses. `hearth_app` gets no INSERT on `jobs` until a step gives the api a producer (C0.14's notifications), and that step adds, in the same migration, a database check of which role may queue which kind, so the api's credential can't queue a maintenance, offboarding or revocation job or take another kind's idempotency keys. The same kind→role check then binds `job_fence()` and `job_finish()` to the kind's role too: until then any job role holding a job's lease could finish another kind's job, which only the runner, holding every lease, can do.
19. **Polling.** The runner and the consumers poll every 500 ms when idle (each poll is one short transaction per org); the scheduler ticks every 5 s ±10%. With one org (D1) that is a few trivial queries a second. A LISTEN or Valkey nudge can be added if latency or the number of orgs needs it.
20. **Two versions at once.** During a rolling deploy or after a rollback, two worker versions share the database. Each claims and fires only kinds it knows. A queued job of a kind no running version knows waits; after 7 days the scheduler makes it dead (`kind_unknown`) at error level. Schedules never change per key and are never un-retired (item 13), so versions can't undo each other. Consumers stay one instance per (consumer, org) whichever version runs them. Migrations stay expand-only (INF-MIGRATE), so an older image runs on the newer schema.

## T16: the outbox defaults for the owner to confirm or change

BUILD-PLAN C0.6 sets "ids-only, 14 days", the envelope (Part 2, the notes for C0.6) and "retrofitted onto every write"; the rest are C0.6's choices. `apps/server/src/outbox/outbox.integration.test.ts` (with the unit tests in `apps/server/src/outbox/`, `db/tests/110_outbox.sql`, `apps/server/scripts/check-catalogues.ts` and the race cases) pins each one.

1. **Order.** Per org, by `(tx_id, id)`, where `tx_id` is the writer's top-level `xid8` (`pg_current_xact_id()`, the column default, which no producer may set). There is no order across orgs. It isn't commit order, nor per-entity order: a consumer re-reads the entity's current state (`ordering: 'reread'`, the default), or compares `acl_epoch` for ACL rows (`ordering: 'epoch'`). A commit-time sequencer stays in reserve as a migration-only change if a consumer ever needs commit order.
2. **The horizon.** A consumer reads only rows with `tx_id < pg_snapshot_xmin(pg_current_snapshot())`, in the same statement as the rows. Any transaction holding an xid anywhere on the cluster holds every consumer back: events are delayed, never lost. So every transaction the server opens is bounded (T18 item 7), and the worker logs how long consumers are held back (item 19).
3. **Checkpoints.**
   - One per (org, consumer), moved only by the role the consumer runs as: a trigger (`outbox_checkpoints_own_row()`) refuses any other role, a role name that doesn't exist and a renamed row (`42501`). From 0008 it also binds each consumer the server runs to that role (`offboarding` to `hearth_job_offboarding`, `revocation` to `hearth_job_revocation`), so one consumer's role can't start another's checkpoint in an org where it has none yet, and nobody, the superuser included, can pair the name with another role. A migration that adds a consumer binds its name in the same function, and `apps/server/scripts/check-catalogues.ts` fails until it does: every consumer the worker runs (`productionRegistries`) must be bound to exactly its role, and every bound name must be one of them. Names it doesn't bind (the tests' own consumers) may name any role their writer can use.
   - It moves in the transaction that applies the batch's effects, by compare-and-set from the position the round read. A consumer takes `pg_try_advisory_xact_lock` per (consumer, org), so one instance runs at a time, and reads its batch (at most 500 events) before it writes, so its own xid never lowers its horizon.
   - A new consumer starts at the oldest kept event (`start: 'oldest'`: the floor, or the beginning when nothing has been purged), or at the current horizon (`'now'`) when it bootstraps from enumerators (C1.7) or a re-check covers anything before it (C0.7's revocation consumer, T19 item 4).
   - Each round passes the job gate (T15 item 10) for the consumer's purpose and providers, and withholds an event whose subjects' processing switch refuses that purpose (`outbox_event_withheld`). A protective consumer (T19 item 4), which only takes access away, is never withheld an event for a subject's processing switch, and its purpose gate still applies. A round for an org whose flags the process hasn't read yet is refused, and the flags reloaded, rather than fenced with nothing to compare.
   - Each round ends with `feature_fence()` for the consumer's feature, so no effect commits after its flag changes.
4. **Exactly once in effect.** Effects in Postgres commit with the checkpoint; effects elsewhere go through jobs keyed by what they do, whose own effects are idempotent. Re-delivery and replay change nothing.
5. **Replay.** Moving a consumer's checkpoint back, never below the floor, by the consumer's own role (`ConsumerRunner.reset`, which waits up to 30 s for a round in progress; C0.16 may expose it as an audited ops action). Older than the floor: rebuild from the base tables by enumerators (INF-ENUM, C1.7), then start from the horizon read when the rebuild began. A replay queues jobs again where their keys have gone with their rows (jobs are purged 14 days after they finish), so jobs' effects must be idempotent, as they are.
6. **14 days.** BUILD-PLAN sets the length; the meaning is C0.6's.
   - Both a minimum and a maximum: deletion doesn't wait for a slow consumer, because `subject_ids` are personal data.
   - `purge_outbox()` finds the furthest position of an event older than 14 days whose transaction has ended (the edge), deletes every event at or below it from the lowest position up, and records how far it went (`outbox_floors`) in the same transaction. So everything at or below the floor is gone and nothing can appear there again, and a consumer at or above the floor has missed nothing. An event whose transaction took its xid early can go up to that transaction's length (at most 30 s) before its 14 days are up.
   - A consumer whose checkpoint is below the floor stops and logs an error (`outbox_consumer_fell_behind`, once each time it falls behind), and must be rebuilt. It stays blocked, and the worker unready (T18 item 9), until a round reads again after the rebuild or a reset (`outbox_consumer_unblocked`).
   - The outbox and the queue hold only ids of facts the base tables and the audit log keep, so C0.6 treats their rows as transient operational records outside legal holds and access-request holds (PDPA-09), and the clean-up's audit rows as their deletion record; a restore that brings back old rows is cleaned again within a day. That reading is for the DPO to confirm, and C0.10, which builds `isHeld()` and the deletion log, either routes the clean-up through them or records the exemption.
7. **"Every write" (D41) and "every content write" (`CLAUDE.md`).** Every write is covered.
   - Content writes always append their event with an ACL snapshot; no exemption is allowed for a content table.
   - Other writes append their catalogue event where a consumer may act on them (sign-ins, credentials, people added, profiles, deactivation, flags). Bookkeeping (last-seen and re-authentication stamps, a device's display name), security counters, the audit and access logs themselves, the clean-up and the queue's own machinery are exempt, each with its reason.
   - `apps/server/src/outbox/coverage.ts` decides every write grant of every runtime role (INSERT and DELETE by table, UPDATE by column, keyed `'<role> <table>:<operation>'`), every function a runtime role can run and every `SECURITY DEFINER` and trigger function, each mapped to event types or an exemption. `hearth_app`'s `principals` INSERT is `person.added`, `working_hours` INSERT and DELETE `profile.updated`, `devices.label` UPDATE and `data_access_events` INSERT exempt. Two checks enforce it both ways: CI's `check-catalogues.ts` fails on a grant or function the table doesn't decide (and on an exempt content table), and every integration suite but the roles one sweeps its committed writes (a trigger copy of each write and each outbox insert) and fails on one without its event naming the same subject, or on a write by any role but the runtime roles (`hearth_app` and `JOB_ROLES`) and the harness's own superuser.
8. **One event per business event.** The server appends events beside the change, never in triggers: a deactivation that ends N sessions and M devices appends `person.deactivated`, `signin.ended` (with their ids) and `acl.changed`. The trigger cascades (`people_end_sessions`, `devices_end_sessions`) are covered by their transaction's events. The actor is the one the audit log records, and the ACL snapshot comes from `@hearth/access`, never from SQL that duplicates it.
9. **Events are claims.** An event says what a transaction did, but a consumer that does something it can't undo re-reads the base row before acting. Offboarding is the first: the worker's offboarding consumer reads `person.deactivated`, checks that the person has left (an event for someone still at the org is logged at error level, `offboarding_not_deactivated`, and passed over), and queues one `offboarding.handler` job per handler, keyed `<person>:<handler>` so a repeated event adds nothing while the job's row lasts. Each job re-reads the person and takes the actor from `people.deactivated_by`, never the payload, then runs its handler with retries (60 s an attempt). Offboarding's handlers are a fixed list that later steps join; its C0.5 `sockets` handler is retired, and closing a leaver's sockets is now the revocation registry's (T19 items 2 and 4), which hears the deactivation's `signin.ended` and `acl.changed`. The api still publishes the sessions it ended at once, so sockets close as fast as before.
10. **The actor.** The database binds an event's actor to the principal the transaction acts as (`app.user_id`, from the session), unless that principal is Hearth's system principal: before a session exists the person signing in is the actor, as the audit row has it, and a job names whoever its work is for.
11. **Names.** `<noun>.<past-tense verb>` (`person.deactivated`), apart from audit codes' imperative `person.deactivate`. Sign-in sessions are `signin.*`, never `session.*`, which C2.4 reserves for recorded room sessions (T14 item 17). `packages/shared` reserves a namespace per later stage (`message.*` C1.1, `task.*` C2.1, `session.*` C2.4, `file.*` and `folder.*` C4.1, `transcript.*` A1, `agent.*` A5, and so on), and a unit test refuses a name outside its namespace's stage.
12. **ACL snapshot and `index_class`.** A content event carries `aclOf`'s row (`acl_tokens`, `acl_more`, `index_class`) and the container's `acl_epoch`; any other event carries none (the four columns are null together, by a constraint), and an indexing consumer never indexes one.
13. **`acl_epoch`.** A counter per ACL holder (the container: a channel, a space, a Drive item), stored on the holder's row by the step that makes it (C1.1, C4.1) and bumped in the transaction of every change that rewrites its stored ACL rows (a grant, visibility, a move, trash, restore). Never by a membership, team, role or deactivation change: those change people's keys, not stored rows (T13). Consumers keep the highest epoch per holder and drop an older snapshot.
14. **`acl.changed`.** One type, with `ids.change`: `keys` (people's keys changed: a team membership, a role, a deactivation; `subject_ids` names them; nothing stored is rewritten; consumers drop live state such as sockets, topics, room participation, Hocuspocus, previews and AI caches) or `rows` (an item's stored ACL was rewritten; the snapshot and new epoch come with it). C0.6 emits `keys` on deactivation (its `reason` is `deactivated`); C0.16 adds team and role changes and their reasons; C1.1 and C4.1 `rows`. C0.7's revocation consumer handles `keys` for any reason and passes over `rows` until C1.1 (T19 item 4).
15. **The envelope.** The actor's id and kind (the kind checked against the principal by a foreign key). `subject_ids`: the people whose personal data the event concerns (the person for account events; for content, the author and the people it names, as each type's catalogue entry says), at most 100. `purpose`: a key from `packages/shared` `PURPOSES`, one of those the catalogue allows for the type. `tombstone`: the entity is gone for every reader, so everything made from it goes too; not an edit, a correction or a partial redaction. `ids`: the other ids consumers need, under `is_ids_only()`, with each type's zod schema as the guarantee (uuids, enums, booleans, bounded whole numbers). `flag.changed` carries only `{ enabled }`: its entity is the flag's row, and consumers re-read the row for its key, cohort and revision. `on_behalf_of` isn't carried; A4 or A5 add it if a consumer needs it.
16. **Purpose keys.** A code vocabulary in `packages/shared` (`PURPOSES`) mirroring PDPA-01's pre-filled purposes, plus `service_operation` for Hearth's own maintenance (for the DPO to confirm or fold into hosting). C0.6 marked each key for whether it may rest on consent; C0.9 built the processing register on the same keys, and the basis the DPO records there now decides, so that mark is gone (`PurposeSpec.consent`, C0.9 PD-28). Check 6 in `apps/server/scripts/check-catalogues.ts` requires `PURPOSES` and `PROVIDERS` to equal the registers' defaults both ways, and every org to have exactly their rows (T22 item 18).
17. **Events with no write.** `task.overdue` (C2.1) and LiveKit webhooks (C2.2) are appended by a job or webhook handler in its own transaction, with the system principal acting; the job's idempotency key or a marker row stops doubles.
18. **Restore.** A point-in-time restore rolls the outbox, checkpoints, jobs and projections back together, and consumers re-deliver idempotently. Deletion-log replay (C0.17) goes through the deletion code, which appends tombstones as any delete does. A logical restore or a Blue/Green major-version upgrade (logical replication) leaves stored positions that the new cluster's xids don't follow, so when the worker starts, each org's consumers first compare the highest stored position (events, checkpoints and the floor, so a fully purged outbox still counts) with `pg_snapshot_xmax(pg_current_snapshot())`, as `hearth_queue`, read only; one at or above it stops that org's consumers with an `outbox_future_rows` error (and `outbox_consumer_blocked` for each, which leaves the worker unready, T18 item 9), and the runbook (C0.17; C0.11 for Blue/Green) purges the outbox and rebuilds consumers. A check that fails is tried again at the next round. It runs at start only: a restore or an upgrade restarts the worker. `pg_upgrade` and snapshot restores keep xids.
19. **The lag metric before C0.13.** JSON log lines from the worker every 30 s: `outbox_lag` per consumer and org (seconds behind, events behind up to 100,000, checkpoint age, and events and seconds held back by the horizon), at warning level above the consumer's own budget (`lagBudgetMs`), and `queue_depth` per org (queued, running, dead, interrupted, oldest queued age). C0.13 turns them into CloudWatch metrics. No dependency.
20. **Who may append.** The roles that may insert into the outbox are an explicit list a DB test pins (`db/tests/032_worker_roles.sql`), `hearth_app` alone in C0.6; each later step that adds one (C2.1's overdue job, A1's transcript jobs) extends the list in its own migration and test. No role with BYPASSRLS, and never the Rule 9 role (C1.11), may hold INSERT.
21. **Who validates.** `appendOutbox()` (`apps/server/src/outbox/append.ts`) validates against the catalogue (the ids by zod, the purpose, the snapshot's presence) and splits a long list of ids; the database checks the type list, the ids shape, the snapshot's shape, the actor and its kind.

## T17: the flag defaults for the owner to confirm or change

BUILD-PLAN C0.6 sets "≤10 s propagation", job cancellation and "ai.* registered off and locked" (PRD-65), and ADM-10 the AI levels; the rest are C0.6's choices. `apps/server/src/flags/flags.integration.test.ts` (with the unit tests in `apps/server/src/flags/`, `db/tests/130_flags.sql`, `packages/shared/src/catalogues.test.ts`, the role matrix and the race cases) pins each one.

1. **Registry in code, state in the database.** Keys, class, purposes, client visibility and stage live in `packages/shared` `FLAGS`. Rows exist for every org from the migrations: `feature_flag_defaults()` lists each key's default value and lock, a trigger on `orgs` gives a new org its rows, and a migration that adds a flag replaces the function and inserts rows for existing orgs. CI's `check-catalogues.ts` compares the function with `FLAGS`.
2. **Hierarchy.** By dotted prefix: a flag is on only if every registered flag above it is too. ADM-10's three levels are `ai` (all AI), `ai.agents` (all agents) and `ai.agents.<id>` (one agent, rows made by A5).
3. **Cohorts.** People and org-wide roles (`owner`, `admin`, `ai_admin`, `leadership`, `dpo`, `compliance_officer`), any of which matches, at most 1,000 entries in all: enough for BUILD-PLAN A0's "the founder, DPO and AI team" and INF-RELEASE's testers. A role counts while its assignment is unrevoked and its holder still at the org, and a person the cohort names counts only while still at the org, so a leaver is in no cohort. A kind whose subject is a leaver by design (offboarding, deletion) therefore sits under a whole-org flag, as offboarding does under `core.system`. `set_feature_flag()` refuses a change that adds someone who has already left (HF004), reading them FOR SHARE. Someone the cohort already names who leaves later stays named and matches nothing, so they never stop the flag being switched off, resent or narrowed; if another change moves the cohort while the people added are checked, the call answers 409 `try_again` (40001). Teams, departments and Team Admin come with the first step that needs them (C6.8's department waves): Team Admin's powers end when its team is archived (T13 item 14), so telling who holds it needs team reads the worker doesn't have yet. Places (STU-05's pilot channels) come with A5, percentages with whatever first needs them. A job is checked against the person it's for (`jobs.subject_id`); a job for nobody runs only under a whole-org flag. Cohorts are evaluated in the server alone (`apps/server/src/flags/evaluate.ts`); the database fences by revision, so it never needs a second copy of the rule. The fence therefore covers flag changes only: a running attempt keeps the cohort membership read when it was claimed (its person's roles and whether they're still at the org), re-read at every claim, so a role revoked or a person deactivated while it runs applies from the next claim (within the kind's `timeoutMs`). The first cohort-gated job kind that touches personal data (A0) re-reads its subject inside each commit. `set_feature_flag()` keeps a cohort sorted and without repeats, so the same cohort sent in another order changes nothing.
4. **Classes.** Every flag is essential or optional (ADM-05 and D10 for AI). Optional: a spend cap may pause it (A0), and its work is dropped when it's switched off. Essential: no cap ever pauses it (D10), and its work waits while it's off. Core flags default to essential. The class lives in code only (`CLAUDE.md`, AI: how caps are enforced stays in code).
5. **Locked.** A locked row keeps its value: every `ai.*` row off, by a CHECK constraint even the owner can't get past, and `core.system` on. `set_feature_flag()` refuses any locked row (`HF003`, 409 `flag_locked`) before it locks the row, `can()` refuses `flag.set` for any `ai.*` key, and the purpose gate refuses AI purposes. C0.9 put the second, compliance lock in the register tables: an AI purpose stays planned with nothing recorded, and an AI provider can't be cleared, by a constraint and a trigger that A0's migration replaces (T22 items 2 and 3). Only A0's reviewed migration lifts the `ai.*` lock, bumping the revision of each row it changes. Nobody turns one on before, the Owner and the DPO included.
6. **Propagation.** Postgres holds the truth. After a change commits, the api publishes `{ v: 1, org, key, revision, at }` on `h:<DEPLOY_ENV>:flags` (best effort, like the api's publish on `revoked`). Every process (api, realtime, worker) reloads that org's flags on the message, and polls every 2 s (±10%), so the worst case is about 5 s with Valkey down. Each read's statements are bounded to 2 s by Postgres (`statement_timeout`), and the process stops waiting for a whole read after 2.5 s whatever happens (a connection whose peer went silent never hears Postgres's error): that read counts as failed (`flags_poll_failed`, and `flags_unconfirmed` at 8 s), the next poll is scheduled, and the stuck read changes nothing when it ends. A stuck read keeps its pool connection until the pool's `query_timeout` ends it (31 s), so a process has at most 3 flag reads in flight at once (`FLAG_READS_IN_FLIGHT`, stuck ones included; the worker's control pool has 8 connections, the api's 10 and realtime's 12, T19 item 11): a poll due past that waits until one ends, its org going unconfirmed once its last read is 8 s old (logged once, `flags_unconfirmed`, as for a read that fails), and a `reload()` of it resolves at once, as after a failed read. `flags_reads_limited` is logged once an episode, which starts at the first poll that waits and ends only when fewer than 3 reads are in flight and no poll waits. The limit's accepted cost: after a blip that leaves 3 reads stuck on silent connections, no org confirms until one of them ends at the pool's `query_timeout` (about 31 s), even if fresh connections would work. Meanwhile each org's flags read as off once its last read is 8 s old (fail closed, item 7), apart from flags locked on (`core.system`), which still read on; from then the worker claims nothing for that org, and the watchdog of T15 item 11 gives back its running jobs whose feature isn't locked on. A change pushed meanwhile is seen once a read runs, and the fences (item 8) still stop any effect a change should stop. A process starts loading an org's flags the moment it first needs them (`track()`): the api for each signed-in request's org, realtime for each socket's, the worker every org (as `hearth_queue`). The worker stops keeping an org's flags (`untrack()`) when the org leaves its org list, and a later `reload()` (a job's fence refusal, a gate's second look) leaves an org it doesn't keep alone, so only `track()` keeps one again; the api and realtime keep theirs, since they serve one org (D1). A caller that serves values to someone (C0.8's `GET /api/flags`) waits for that first load.
7. **Fail closed when unconfirmed.** A process that hasn't confirmed an org's flags for 8 s reads every flag not locked on as off (`FlagCache.verdict()` says `unconfirmed`, which the job runner tells apart from `off` and `not_in_cohort`).
8. **Zero effects after a change.** PRD-65 asks for it; the mechanism is C0.6's.
   - Every transaction that makes a feature's effect visible ends with `feature_fence(feature, seen)` (a job's with `job_fence()` or `job_finish()`), which reads the flag and those above it `FOR SHARE` and refuses (`HF001`) unless all are enabled and still at the revisions the server evaluated (`seen`). A change in progress makes it wait and then refuse, and one that starts later waits for it.
   - A flag change takes its row `FOR NO KEY UPDATE`, which waits for fences but not for the jobs being queued for the feature, whose foreign keys hold the row `FOR KEY SHARE`.
   - Work outside Postgres before such a commit (A0's model calls) checks the cache just before and passes the job's `AbortSignal`, so an in-flight call is cut off.
   - The fences cover flag changes, never register changes (C0.9 PD-17): running work sees a register change at its next admission, within about 2.2 s, and no C0.9 work can be refused by one (T22 item 12). An outbound send holds its provider's clearance `FOR SHARE` in the transaction that decides it, with the bound T22 item 8 states.
9. **Who changes a flag, and how.** `CLAUDE.md` asks for re-authentication and the audit log; the roles are C0.6's.
   - An Owner or Admin, for a flag that isn't locked and isn't `ai.*` (A0 decides who turns AI on and off: ADM-05, ADM-10), through `POST /api/admin/flags/set` with a re-authentication from the last 5 minutes.
   - The route validates first: a key that isn't flag-shaped is 400 `invalid_request`; a bad cohort (over 1,000 entries, a cohort naming nobody, names given for the whole org, a role outside the six) is 400 `invalid_cohort`, before any database work.
   - Then `can()` decides `flag.set` (403 `forbidden`); a key the process's registry doesn't know, or the org has no row for (`22023`), is 404; a change that lets the feature reach anyone it doesn't reach now (turning it on, or, while it is on, widening its cohort or giving it to the whole org) is 409 `purpose_refused` when the purpose gate, reading the registers in the same transaction, refuses any of the flag's own purposes. Turning a flag off, narrowing it and a change that reaches nobody new are never refused, and no register change is refused because a flag is on (C0.9's interlock, T22 item 11).
   - `set_feature_flag()` re-checks the person and their role `FOR SHARE` (`42501`), refuses a locked row (`HF003`) and a cohort that adds anyone who isn't a person still at this org (`HF004`, 400 `invalid_cohort`), bumps the revision and writes `flag.set` to the audit log with who joined and left the cohort and the value before and after. A no-op writes nothing and returns the current revision.
   - On a real change (the route reads the revision first in the same transaction and compares), the server appends `flag.changed` and publishes after the commit.
   - No production flag can change in C0.6 (`core.system` on and `ai.*` off are both locked). Tests drive test flags (`it.*`) through the real route, whose registry is injectable (`FLAGS` in production); C0.14 and C0.15 add the first changeable flags, and C0.8 adds none (C0.8 OD-13).
10. **Flags and settings.** Flags switch features on or off for a cohort: rollouts, kill switches, and org-wide on/off toggles such as ADM-13's read receipts. A flag never gates an access check (`can()` still decides every one), nor a privacy or safety control (the recording indicator, Principle 6; the notice acknowledgement gate; the access filter). Settings hold values with ranges in code (numbers, lists, choices) in their own typed tables, read at use (`CLAUDE.md`: compute from raw values and the settings row), as `audit_log_readers` does.
11. **Flags in the browser.** `GET /api/flags` (C0.8, `apps/server/src/web/flags.ts`, T21 item 10) answers `{ flags }`: the signed-in person's own value of each flag marked `client: true`, as a boolean, never a cohort, a revision or anyone else's values. `not_in_cohort` reads false, as `off` does, so the answer never says which. It waits at most 2.5 s (`FLAG_READ_WAIT_MS`) for the org's first read, and while the org's flags are unconfirmed it answers 503 `unavailable`, never a guess, and the client keeps the values it last had. It doesn't touch the session (C0.8 OD-14), so a polling tab can't keep an idle session alive. The client asks while a screen shows a flag slot (Today's and Chats' in C0.8): when it mounts, every 60 s while the page is visible, on focus and on the gateway's nudge (T19 item 10: only for `client: true` flags, carrying no values, and refetched within the reconnect spread). No production flag is `client: true` yet (C0.8 OD-13), so in production it answers `{ flags: {} }` at once, with no wait and no flag read. The 10 s budget is for server processes ("every process"); the server re-checks every action, so a stale client at worst shows a slot whose action the server refuses. The answer doesn't ask the purpose gate: G1 (C0.9, T22 item 11) keeps every flag outside `ai.*` on the pinned purposes, which the gate always allows, so it can't say on for a purpose the gate refuses, and the step that adds the first flag naming another purpose makes `verdict()` and this answer ask the gate.
12. **The `ai.*` flags registered.** `ai` (essential), `ai.transcription`, `ai.transcription.sessions`, `ai.transcription.voice_messages` and `ai.notes` (essential: caps never stop them), and optional: `ai.brain`, `ai.ask`, `ai.catch_up`, `ai.summaries`, `ai.docs`, `ai.sheets`, `ai.slides`, `ai.quick_replies` (BUILD-PLAN A3), `ai.people_inference`, `ai.assistant`, `ai.agents` and `ai.onboarding_buddy` (C0.15's step "registered, off"). A catalogue test requires every flag with an AI purpose to sit under `ai.`, so no flag outside the `ai.*` lock can carry one.

## T18: the worker's roles, defaults for the owner to confirm or change

PRD-112 asks for scoped credentials per service and `CLAUDE.md` for a role per system job; the shape is C0.6's. `db/tests/032_worker_roles.sql`, `apps/server/src/db/roles.integration.test.ts`, `scripts/check-migrations.sh` and `scripts/guards/db-entry.test.ts` pin each one.

1. **One login per service, a role per job per transaction.** `hearth_worker` holds nothing itself and takes one job role per transaction through `withOrg()`'s `as`, in its first statement (`set_config('role', …, true)`, so the role ends with the transaction). The job roles are `hearth_queue` (claims, heartbeats, outcomes, the scheduler, the flag cache, metrics and the org list), `hearth_job_offboarding` (the offboarding consumer and its jobs), `hearth_job_partitions`, `hearth_job_purge` and, from C0.7, `hearth_job_revocation` (the revocation consumer and its jobs, which read only sessions' ends: T19 item 4), as `apps/server/src/db/roles.ts` lists them. Job roles limit what a buggy handler can touch: a consumer can't start or move another's checkpoint (T16 item 3), a maintenance job can't read sessions, the clean-up can delete only what its functions allow. They don't separate jobs from a compromised worker process, which can take any of its roles. Services that read sensitive data (the recorder in C2.6, conversion in C4, calculation in C5, the Rule 9 role in C1.11) get logins of their own when they arrive.
2. **The worker's org list.** `worker_org_ids()`, ids only, executable by `hearth_queue` only, called by `listOrgs()` in `database.ts` in its own short read-only transaction, at start and every 60 s: a second, named exception to "every query filters by org", beside the sign-in lookups. Everything after it runs in `withOrg()` for one org, under row level security.
3. **Who runs the partition function.** `hearth_job_partitions`; `hearth_app` still can't (T15 item 16).
4. **Every runtime role is held to `hearth_app`'s rule.** Any role granted anything in the database, and any role that can use one by SET or INHERIT, is never a superuser, BYPASSRLS, an owner or a member of one (`scripts/check-migrations.sh`). 0007 itself checks, grant by grant, that `hearth_worker` holds only job roles, by SET and never INHERIT or ADMIN (and, on RDS, the powerless `rds_iam` that IAM sign-in needs), telling a job role by its shape rather than a list of names, so one a later migration adds still passes on a server that has it: `hearth_queue` or a `hearth_job_` name, with no power (login, superuser, BYPASSRLS, CREATEROLE, CREATEDB, replication), a member of no role and owning nothing, that only `hearth_worker` may act as a job role, and that nobody may act as `hearth_worker`. The api's and realtime's `/ready` refuse a login that skips RLS or can use any job role; the worker's refuses one that can become a role that skips RLS, is a member of `hearth_app` or of any `pg_*` predefined role, or holds anything but `rds_iam` and roles of that shape by SET, and its `worker_roles` check refuses one that can't take each of its job roles (`apps/server/src/db/pool.ts`).
5. **Roles are made by migrations**, NOLOGIN, and checked by property when they already exist (0001's pattern). `infra/` never makes a job role; it gives `hearth_worker` its login (IAM on RDS) exactly as it does `hearth_app` (C0.12). Locally it gets the password `hearth-local` from `scripts/db-local.sh` and the integration harness.
6. **`WORKER_DATABASE_URL` reaches the worker only**, and `DATABASE_URL` the api and realtime roles only (C0.11's task definitions), so no task holds another service's credential. Each role reads only its own variable and ignores the other, valid or not.
7. **Every transaction is bounded.** `transaction_timeout` 30 s in the first statement of every `withOrg()` transaction, every pre-org lookup and the worker's org list, to bound how long one transaction can hold the outbox's horizon (T16 item 2). Only read-only work (`readOnly`, which takes no xid) may raise it, to at most 5 minutes. It is set per transaction rather than as a connection default because a running timer can't then be raised. Postgres ends the connection of a transaction that runs past it, so the caller sees a lost connection, not a SQLSTATE (T15 item 4). Every pool also bounds each statement on the client, at 31 s (`query_timeout`), because a connection whose peer has gone silent (a failover, a dropped network path) never hears Postgres's error. pg on its own only fails the statement's call and keeps the connection waiting on it, so the pool's client ends itself when a statement times out, and the pool drops it and opens a fresh connection for the next transaction (`BoundedClient`, `apps/server/src/db/pool.ts`; `pool.integration.test.ts` proves it on a frozen connection). That doesn't stop the statement on the server, which runs until its transaction's own timeout. TCP keepalive, also on, frees only an idle connection whose peer has gone: Linux sends no probes while a statement's bytes go unacknowledged. A raised read-only transaction must therefore keep each statement under 31 s, or the client gives up on it.
8. **Two pools.** The worker opens two pools on its login: a control pool (8 connections) for claims, heartbeats, outcomes, sweeps, the scheduler, the flag poll, metrics and the org list, each loop holding at most one connection at a time, except the flag reads, at most 3 (`FLAG_READS_IN_FLIGHT`, T17 item 6), the heartbeats, one per org renewing and at most 2 at once (`renewalsInFlight`, T15 item 2; a slow claim's renewal of its own jobs is the claim loop's one), and outcomes: each job's outcome is its own short transaction, so up to `WORKER_CONCURRENCY` (4 by default) can be written at once (the give-backs at shutdown, say). Each waits for a free connection like any other. Its worst case is every flag read and heartbeat renewal stuck on a silent connection until the 31 s `query_timeout` (item 7): 3 + 2 = 5 of the 8 connections, leaving 3 that claims (a slow claim's renewal included), the scheduler, the org list and metrics (one at a time each) and outcomes (up to `WORKER_CONCURRENCY` at once) share, each a short transaction that waits up to 2 s to connect; an outcome that can't connect in that time is left to the lease sweep, which treats the job like any whose lease ran out (T15 item 2: requeued with the attempt counted, dead with none left, a review run's job interrupted). `apps/server/src/worker/index.test.ts` keeps those 3 free; and a work pool (`WORKER_CONCURRENCY` plus one per consumer) for handlers' transactions and consumer rounds, each holding at most one at a time. Neither can starve the other, so heartbeats and the flag poll never wait behind work. Each pool names itself in `pg_stat_activity` (`hearth-worker-control`, `hearth-worker-work`, as the others are `hearth-api` and `hearth-realtime`), so an operator can see whose transaction holds the horizon. From C0.9 each flag read also reads the registers, in the same read-only transaction and under the same cap, so these counts stand (T22 item 9).
9. **Readiness.** The worker reads the org list first and starts its other loops once it has, and its `/ready` `worker` check passes while every loop's last good round is within three of its intervals (never less than 5 s), every listed org's flags are confirmed (T17 item 6: it claims nothing for an org whose flags it hasn't), and no outbox consumer is blocked in a listed org (behind the floor, T16 item 6, or positions from the future, T16 item 18); an org that leaves the list takes its consumers' blocks with it. Its error, which goes to the log, names each loop, org or consumer that fails and why (`behind_floor`, `future_rows`). A loop that fails logs `worker_loop_failed`, at error level from the third failure in a row.
10. **The fences.** `feature_fence()`, `job_fence()` and `job_finish()` are `SECURITY DEFINER` (their locks need UPDATE, which none of the job roles that run them holds on flags or jobs) but, unlike other definer functions, neither re-check an ACC-10 role nor write an audit event: they act for no person, only for the worker's own roles, the only ones that may run them; they decide only whether work already admitted may still commit; they change no flag and nobody's data (`job_finish()` ends the job and its run, the queue's own bookkeeping); and every flag change they compare against is checked and audited in `set_feature_flag()`.

1. **Rule 6 covers live connections (OD-01, owner).**
   - A person's sockets close, and a topic they hold is dropped, within 60 seconds of losing access. This applies to deactivation, sign-out, a PIN reset, a device sign-out, leaving a team, and from C1.1 leaving a space.
   - The 60 s is a hard bound (p100), not a percentile: ACC-05 says "within 60 seconds".
   - Rooms (C2.2), docs (C4.3) and presentations (C5.6) join the same bound through the registry.
   - *Why:* the C0.7 Done line cites Rule 6, and Rule 6 now carries review finding PRD-80's clause. The PRD cites no review ids, so PRD-80 is cited here and in the PR. The PRD promises only what C0.7 and the later steps deliver: the live updates of whatever was lost stop, and a sign-out or offboarding closes every live connection.

2. **Two registries (OD-10).** The offboarding registry (C0.5) does what a departure does to someone's things. The revocation registry (`apps/server/src/revocation/registry.ts`) drops live access, for anyone, for any reason.
   - Closing a leaver's sockets moves from offboarding to revocation.
   - Offboarding's `sockets` handler is retired. Its name stays in `OFFBOARDING_HANDLERS`, so a job queued before C0.7 still parses and finishes as `offboarding_handler_unregistered`, the path C0.6 built for a removed handler.
   - Its role keeps its `sessions` read until a later migration contracts it (T3), at the latest C0.16's. A C0.6 worker may still run the old handler while C0.7 deploys, and a revoked grant would make that job fail with 42501.
   - Every deactivation appends `signin.ended {deactivated}` and `acl.changed {keys, deactivated}` in its own transaction (T16 item 8). So the revocation registry hears it without consuming `person.deactivated`.
   - *Why:* one durable path per effect. Later handlers (LiveKit, Hocuspocus, AI caches) then hear every loss of access, deactivation included, as a session end or a keys change.

3. **Handler names are a closed list (T15 item 8).**
   - `REVOCATION_HANDLERS = ['sockets', 'topics']`. `register()` refuses an unlisted or duplicate name, a handler that acts on no cause and a cause not in `REVOCATION_CAUSES`.
   - Each handler declares the causes it acts on:
     - `sessions_ended`, from `signin.ended`;
     - `keys_changed`, from `acl.changed` `keys`, with `subject_ids` naming the people.
   - A later handler adds its name to the list and registers itself, with the grants its reads need in its own migration. A later cause (C1.1's and C4.1's `rows_changed`) adds itself to `REVOCATION_CAUSES` and to `revocationOf()`.
   - *Why:* job payloads hold codes, never free text.

4. **The revocation consumer and its jobs (OD-08, owner; OD-09, OD-28, OD-39, OD-40).**
   - **The consumer.** `revocation` runs as `hearth_job_revocation` (0008), under `core.system`, with purpose `accounts`. `core.system` is locked on, so no flag gates it (T17 item 5). 0008 binds the name to that role, so the offboarding role can't start the revocation checkpoint before the consumer does, or the reverse (T16 item 3).
     - It reads `signin.ended` (any reason) and `acl.changed` (`keys`, any reason). It passes over `rows` with a debug line until C1.1.
     - It starts at `'now'`, and has a lag budget of 10 s.
   - **It is protective** (`OutboxConsumer.protective`). It only takes access away, so the consumer runner never withholds one of its events because of a subject's processing switch (PDPA-04). The purpose gate still applies.
     - Only a consumer under `core.system` with purpose `accounts` may be protective (`validateRegistries()`).
     - Its jobs name no subject, so `admit()`'s per-person check doesn't apply to them either.
     - A person's processing restriction therefore can't hold back the revocation of their access, or of anyone named in the same event. A later handler without a re-check, such as C2.2's LiveKit, would otherwise depend on it.
   - **What it reads.** `revocationOf()` checks what the round depends on: sessions and people must be the database's lower-case uuids (`LowerUuid`), at most 100 of them, and a session event's person must be one too. Anything else is passed over with `revocation_event_unreadable` at error level (an `acl.changed` naming nobody at warn), and the checkpoint moves on. A round that throws is rolled back and repeated at every poll, so an event that `enqueue()` or the database would refuse must never reach them. A `signin.ended` naming no session (a device signed out with none live) is passed over at debug.
   - **The jobs.** For each event, and each handler that acts on its cause, the consumer queues one `revocation.handler` job.
     - The payload is ids only: `{ handler, cause, person?, people?, sessions? }`. It names no subject (`subject_id` unset): the job runs under a whole-org flag, the role can't read `people` to check a subject, and a subject would bring a foreign key that could fail inside the round.
     - A `sockets` job is keyed `sockets:<first session id>`. The key is unique because a session ends once.
     - A `topics` job has no key. A repeated re-check is harmless, and the only id unique to the event is its bigint, which no key may hold.
     - Jobs try up to 20 times, with a back-off from 1 s doubling to 15 s (±20%). About seven tries start inside the first minute, and the last about 4 minutes after the first. Each try may run for 30 s. A job that dies logs `revocation_handler_dead` at error level.
     - The `sockets` job re-reads which of its sessions have ended, and the `signin.ended` event that ended them, and publishes only those, with that event's `at` as `at` (item 13; with no such event, no `at`). The event is found by its session within a minute either side of the session's `revoked_at`, which only bounds the scan of the outbox's `(org_id, at)` index, since a session ends once. If none has ended, the claim was forged: the job logs `revocation_not_ended` at error level and dies (`not_ended`). If only some have, it logs the same line with the count and publishes those.
     - The `topics` job publishes the people as they are, with no `at`, because a re-check can only drop what Postgres says is lost.
     - A publish that fails fails the job, which is tried again.
   - **C0.9.** `accounts` is pinned, with `service_operation` (T22 item 5): the register keeps both active and never consent-based, and the purpose gate allows them in every state, so a register never read or gone stale never stops this consumer or its jobs. Tests pin two things:
     - the gate `startWorker` wires by default (`worker.gate`, `registerGate()` over the worker's copy of the registers) allows `accounts` before any read;
     - a gate that refuses every subject's switch withholds nothing from this consumer.
   - **Tests.** Integration suites wait until the consumer's checkpoint exists in their org before their first durable revocation (`waitForCheckpoint`), because a `'now'` start skips anything committed before it.
   - *Why:*
     - T16 item 4 sends effects outside Postgres through jobs.
     - Starting at `'now'` loses no safety, since the re-check covers anything before it, and avoids replaying 14 days of events.
     - The short back-off matches the 60 s goal.

5. **The Valkey signals (OD-11, OD-12).**
   - `h:<env>:revoked` keeps its v1 message and its one publisher, the api after its commit. Its `at` is the api's clock just after the commit. From C0.7 every reader ignores unknown fields, so a later step can add one.
   - `h:<env>:access` (v1) is new. The worker's revocation jobs publish on it now, and from C0.16 so does the api's push for team and role changes.
     - Its message is `{ v: 1, org, path: 'push' | 'durable', cause, at?, sessions?, people? }`, with at most 500 sessions and 500 people, and at least one of either.
     - Its readers ignore unknown fields, ignore a message whose `v` isn't 1 (at debug), and treat an unknown cause as a re-check.
   - Sessions named on either channel close at once, with 4401 and no database read. That is safe because publishers name only sessions that have ended: the api after its commit, the worker after its re-read.
   - People named on `access` are re-checked against Postgres before anything is dropped.
   - *Why:* old realtime processes keep the fast path through a rolling deploy, and no strict old reader can drop something new.

6. **Session re-check on revoke, and the races (OD-12).**
   - **On a message.** A revocation message closes the named sessions' sockets. Then one targeted check re-checks the other sessions and the topics of each person who still has a socket open on the process. Targeted re-checks coalesce for 100 ms and run in the decision lane (item 8).
   - **The upgrade race.**
     - A session id named on either channel, or found ended by a check, is kept for 60 s in a recently-revoked set (at most 100,000 ids).
     - Every gate after the session lookup runs in one synchronous block that ends in `handleUpgrade`, with nothing awaited in between: stopping, the recently-revoked set, and the process, session and person caps.
     - So an upgrade whose lookup confirmed a revoked session is refused 401, even when the revocation arrived during the lookup.
   - **The subscribe race.** A person named on `access` is kept for 60 s with the time the signal arrived. A topic decision or an accept that started before that time is followed by a targeted re-check of that person.
   - **Ended sessions.** Every subscribe batch first re-reads its subscribers' sessions, with the periodic check's statement. An ended session is closed with 4401 and is never granted a topic, just as every api request re-reads its acting session.
   - *Why:* the push needs no Postgres, and every race closes without locks.

7. **Topics (OD-02, OD-04, OD-05 deferred, OD-06, OD-18, OD-19, OD-29).**
   - A topic is `<kind>:<uuid>`, of three kinds:
     - `person`: the subscriber themselves (C0.14's inbox);
     - `org`: their org (C0.18's banner);
     - `team`: a team they belong to, an archived team's included (T13 item 14; C0.16's team events).
   - `packages/access` decides each one as `{ action: 'topic.subscribe', topic }`, routed before content requests. A topic is allowed when its token (`p:`, `o:`, `t:`) is among the subject's keys.
   - Only people may subscribe. Assistants, agents and the system principal are refused, as with every self-service request (R9-03).
   - A refused topic answers exactly as one that doesn't exist: `refused`, with no reason (PRD-108). A topic lost later gets `dropped` with reason `access`, and the socket stays open.
   - Each kind declares `perItem` (`apps/server/src/realtime/topics.ts`). C0.7's kinds need no per-item check, because subscription is at reader-set granularity. C1.1's group-DM and space kinds will need one.
   - Whether a public space's topic needs membership or only read access (OD-05) is the owner's decision at C1.1. The kind registry allows either.
   - *Why:* tokens are already the access model (T13), so a token topic needs no new fact.

8. **One check for sessions, admission and topics (OD-36).**
   - **The periodic check.** Every 15 s, each realtime process checks every open socket's session, its admission (from C0.9 PR 2: whether its person has acknowledged the org's latest notice, item 10 and T22 item 30), and every topic it holds, in any state.
     - Each org gets one transaction: read only, with a 10 s `transaction_timeout`, acting as the org's system principal, with no row locks. The whole check, every org included, has 10 s to answer.
     - The topic part loads only the subscribers' person rows, their active team memberships and role rows, and the org's teams (`loadTopicWorld`). It decides each distinct (person, topic) pair once through `@hearth/access`'s `canTopics`, which is `can()` for a list.
     - A lost topic's start time is the earliest time its base rows give for the change that took its token (item 13).
     - What a check finds applies only to the topics it asked about, in the generation it asked about, and confirms them as of the check's start.
   - **When checks fail.** A check that hasn't answered within 10 s has failed, and one failed check closes nothing. A socket closes with 1013 only when its session, or one of its granted topics, would go unconfirmed past 60 s if the next check failed too. The arithmetic is T14 item 14's: 2 × (15 + 10) s < 60 s.
   - **The lane.** Subscribe decisions, accept-time checks and targeted re-checks share one lane per process.
     - It batches every 20 ms, at most 500 sessions a batch (a single larger ask runs alone), one transaction at a time, with the same transaction shape, and first confirms the batch's sessions. A batch that hasn't answered within 10 s has failed.
     - It acts as the org's system principal, not as each subscriber. One transaction serves up to 500 sessions of the org. RLS is org-scoped, so the rows read are the same either way. `can()` decides in memory with the subscriber as its subject. The subscriber's org and id come from the socket's server-side session, never from a frame.
     - A lane that fails closes nothing. The ack lists its undecided topics in `retry`, and the client sends them again after a jittered back-off. Only `closeUnconfirmed` closes sockets for failed checks.
   - **Generations.** Several steps continue after an await: a lane result, the reader's first read of the org's stream (item 9). Each acts only if the socket is still open and the topic still has the generation and state it started with. Unsub, drop and close end a generation. An ack is built from the state after its last await, so a topic dropped meanwhile is in none of its lists.
   - **Repeated subs.** A sub of a topic the socket already holds decides nothing. Its ack lists the topic `ok` if it is live in the generation the sub found. Otherwise it lists it in `retry`: an earlier sub is still deciding it, or answered it `refused` or `retry` meanwhile. A topic dropped or unsubscribed meanwhile is in none of the lists, since the client heard of its end.
   - **Locks.** Teams and memberships are never locked, so the lock order (`CLAUDE.md`) is unchanged.
   - *Why:* the realtime pool's lanes are fixed (item 11), and plain reads take no xid, so the outbox horizon is never held.

9. **Fan-out, and reconnects by re-authorise and refetch (OD-13, OD-14, OD-15; resume decided by the owner, 17 Oct 2026).**
   - **The owner's decision.** C0.7 resumes by re-authorising and refetching. There is no event replay in C0.7.
     - A reconnecting client resubscribes its topics, every topic is decided again by `can()`, and the client refetches each topic acked `ok` over REST.
     - No stream position, epoch, grain or anything else derived from the org's stream is ever sent to a client. So no frame describes events on topics the client doesn't hold. What a member can still infer is listed under What's left, below: `reset`s while a burst big enough to outrun a reader lasts, and the coarse signals of sharing a server.
     - The per-org stream stays only for fan-out between realtime processes, with its own gap and loss detection, on which the gateway sends the affected sockets a `reset` telling them to refetch (Gaps, below).
     - Finer resume belongs to C1.1: its per-conversation sequences in Postgres make catch-up cheap over REST, behind the same access checks.
     - *Why.* C0.7 first replayed missed entries from the org's stream, with positions in every frame. The positions were rounded to a 25 s grain and kept fresh by a tick per grain so that they wouldn't say when other topics' events happened, but a member could still learn something about them: the replay's trim test reset once the org's stream overflowed its cap, a resume took longer the more entries the org had, and a missing tick showed one bit a grain. Re-authorise and refetch has none of these channels, and the replay's 2-minute window saved little, since a client away longer refetched anyway. Its gap resets, which the owner kept, are narrower: no client can cause one by reconnecting or probe for one, and trimming by age makes a trim past a reader a fact about the server (What's left, below).
   - **The stream.** Topic events go into `h:<env>:rt:{<org>}`, a Valkey Stream with entries of at most 2 KiB. Each append trims the entries older than 60 s by Valkey's clock (`MINID ~`), and then caps the stream at about 100,000 entries (`MAXLEN ~`) only as a memory backstop.
     - A Lua script (`SET NX`, `EXISTS`, `XINFO STREAM`, `TIME`, `XADD`, `XTRIM`, `PEXPIRE`) writes it and its epoch key `h:<env>:rt:{<org>}:epoch` together (`publishTopicEvent()`). C0.7 has no production caller: C0.14's inbox, C0.16's team events and C0.18's banner are the first. Realtime appends nothing and runs no script.
     - The script numbers each entry (its `n` field) with the stream's own count of entries ever added (`XINFO STREAM`'s `entries-added`) once the entry is in. So each entry is numbered one more than the one before it for as long as the stream lasts, and a replica numbers as its primary did. Neither the number nor the entry's id ever reaches a client.
     - *Why by age:* a count cap trims past a reader whenever an org's events outrun it by the cap, which says something about the org's volume (a burst of 12,000 events in 334 ms on another member's topic reset a member holding only their own under the old `MAXLEN ~ 10000`). The age limit is longer than a reader may go without reading before readiness fails (`gatewayPolicy()` refuses it otherwise), so a trim by age past a reader means the reader stalled or was cut off (readiness has then failed), or kept reading but fell more than a minute behind a burst (the volume backstop under What's left). Readiness measures time since the reader's last read, not how old its position is.
     - Both keys expire 24 h after their last write. While realtime has sockets in the org, it refreshes both keys every 60 s with `PEXPIRE`, and makes the epoch if it is missing. So a quiet org's stream doesn't vanish under its readers.
   - **The reader.** Every realtime process reads the streams of the orgs it has sockets in, with `XREAD BLOCK 2000 COUNT 500`. It uses its own connection, whose timeouts can't cut a block. It checks every entry a read returns against the number of the entry before it, and checks each org's epoch and tail before a read: every 2 s, and after a reconnect, a failure or a read that found a lost tail. A check reads the epoch, then the stream's first entry, its last entry and the entry at the reader's position in one `MULTI`. When an org's last socket on the process closes, the reader forgets that org's position and epoch. Neither ever leaves the reader.
   - **Frames.** Every frame and entry holds ids, codes and whole numbers only. Clients read content over REST, which checks access. An `ev` carries its entry's topic, type and ids, never its stream id or number. `ack`, `pong` and `reset` carry nothing read from the stream.
   - **Subscribing without a gap.** A topic goes live, and into the reader's index, as soon as its decision allows it. Its ack waits until the reader follows the org's stream (it has read the stream's tail: `StreamReader.ready()`).
     - So every entry appended after the ack reaches the socket, and the client's fetch, which starts after the ack, covers everything before it. An `ev` that arrives during the fetch means fetch again.
     - If Valkey can't be reached, the ack goes anyway, after waiting no longer than the command client's 1 s timeout. The reader resets the org once it reads the stream's tail (Gaps, below).
   - **Reconnects.** A new socket holds nothing.
     - The client sends `sub` with topics only. A `sub` naming a `since`, a position or an epoch is a bad frame (1008).
     - Every topic is decided again: one lost while away is `refused`, and one left and rejoined is `ok` again, decided now.
     - Nothing is replayed. What changed while the client was away it reads over REST, whatever the time away, so there is no resume window and no membership-era test in the gateway. REST applies whatever the access rules say about history (C1.1's eras, PRD-79).
   - **Gaps.** The reader never moves past a gap it can detect without resetting the org. Where it can't be sure every entry of an org reached the sockets holding its topics, it tells every socket of the org that holds a topic live to refetch: one `reset` frame each, naming that socket's own live topics, with reason `gap`. A topic still being decided isn't named: its client fetches it after its ack, which comes later.
     - Trims are found by the read itself. Valkey trims only from a stream's head, so an entry numbered more than one past the last one read means entries after the reader's position were trimmed before it read them (`trimmed`). The test holds whenever the trim landed: before the read, or while an `XREAD` was in flight, when Valkey answers from the trimmed head past the position it was asked for, which no check before the read can see. The reader resets the org before it dispatches that entry, and goes on from it. Its own last entry trimmed by age is no gap, so a quiet org's next event resets nothing.
     - An entry numbered at or below the last one read means the stream lost entries the reader had read and was written again: by a new primary after a failover, or as a new key (`tail_lost`). The org is reset the same way.
     - The checks find the rest: the epoch changed (`epoch`), or the tail the reader read gone (`tail_lost`), either because the stream's last entry is below the reader's position or because the entry at its position is missing although the stream's head is at or below it. The second test finds a failover's lost tail even when a producer appended on the new primary before the check, at ids at or below the reader's position, which a read from it never returns. A reader that finds one continues from the stream's last entry and resets the org.
     - The check reads the head, the last entry and the entry at the position in one `MULTI`, so they describe one moment's stream, in which a trim takes only a prefix. Read one after another, they could make an ordinary append look like a lost tail. After a minute of quiet, the next append trims by age past the reader's own last entry. If it landed after the head was read at or below the position and before the entry there was read, the entry would seem lost from the middle, and every socket of the org would be reset, at a time set by an event on a topic it may not hold. A test lands such an append after each of the check's commands in turn.
     - A lost tail is lost for every reader, so the reader that finds it, at a check or a read, also replaces the epoch (a read's find at the check that follows it, before its next read). Every other reader of the org, including one whose numbers still run on because it hadn't read the lost entries, then finds the change and resets its own sockets.
     - A stream that was absent when the reader started (realtime writes nothing, so a quiet org's stream often is; an empty one that still exists keeps XINFO's entries-added and is numbered from it) is read from its start, so its first entry must be numbered 1.
     - An entry with no number isn't the producer's. It isn't dispatched, and since the reader can't tell what it hid, the next numbered entry resets the org (`unnumbered`), as does the first after a tail with none.
     - A read of an org's tail that succeeds after one failed resets the org (`late_start`), since a sub may have been acked meanwhile while the reader followed nothing.
     - An org whose due check fails isn't read until a check passes, so no read carries the reader's position past a lost tail a check could see.
     - Entries lost before any reader read them can't be found, for example in a failover that keeps the epoch and drops entries no reader had read.
     - An absent stream under an unchanged epoch is no gap: nothing has been written since the reader's position.
     - Every socket of the org that holds a topic gets its `reset` at the same moment, naming only its own topics, so a `reset` says nothing about any one topic's events. The reader logs `stream_reset` with the cause (`epoch`, `trimmed`, `tail_lost`, `unnumbered` or `late_start`), which no client sees.
     - The gateway coalesces an org's resets on the trailing edge, as it does the flags nudge (item 10), over 5 s, the reconnect spread's minimum (`resetCoalesceMs`). The first goes at once, before the entries after the gap the reader found. Any the reader asks for in the next 5 s go as one at the window's end, after the entries dispatched meanwhile, and the client's refetch after it covers them all. So a reader that finds a gap at every read, as an outrun one does, gives the org's sockets one `reset` for each 5 s it goes on, not one a read. A client asked to refetch again before it has refetched from the last `reset` has nothing more to do, so no `reset` asks for refetches sooner than the shortest spread a client waits within.
   - **What's left.** What a member holding only some topics can still infer about the others, none of which a client can probe for by reconnecting:
     - `reset`s that follow from volume. A trim by age past a reader takes the reader stalling for a minute (readiness has failed long before), a fact about the server. The count backstop trims past a live reader only when an org appends more than about 100,000 entries faster than a reader drains them, 500 a read. Measured through the Compose stack's realtime app with the production numbers, for a member holding only their own topic while another member's took every event: bursts of 20,000, 60,000 and 150,000 at about 46,000 a second gave no reset, and one of 300,000 at the same rate found a gap at 111 reads in about 6 s. An outrun reader finds a gap at every read for as long as the overload lasts, so before coalescing the member got 111 resets, whose count and spacing followed how long and how hard the overload ran. Coalesced (Gaps, above), every socket of the org gets one `reset` at once and then one for each 5 s the overload goes on. So they learn that the org had such a burst, roughly when, and roughly how long it lasted, to within 5 s, but not how many events or on which topic.
     - Timing. All of an org's events share its stream, so an `ev` waits behind the entries before it: a member's own `ev` arrived in about 2 ms (p90 2 ms) when the org was quiet and 22 ms (p90 46 ms) right after 3,000 entries on another topic. That is a coarse signal of other topics' volume, like the load on any shared server.
     - Presence. `welcome` and `pong` carry `reconnectSpreadMs`, 1 ms for each socket on the process between 5 s and 30 s (item 11). Above 5,000 sockets it shows how many sockets the process holds, across every org on it, which is presence and not topic events.
   - *Why:*
     - Streams don't lose entries across a Valkey reconnect, and any task can serve any client.
     - Nothing a client is sent can bring back deleted or era-hidden content, because frames hold none, and a reconnect is decided as a first subscribe is.

10. **The protocol (OD-35, OD-44, OD-27, OD-43, OD-42).** `packages/shared/src/gateway.ts` holds the frames and, in its header, the client's side of the contract for C0.8.
    - **One socket per tab.** A tab opens one socket and multiplexes every topic on it. Writes go over REST, so the protocol has no write frame, and inbound frames stay small enough for the 4 KiB cap. Each tab keeps its own per-user state, which a sign-in as someone else replaces (CHT-60).
    - **Versions.** Frames are JSON text, and each carries `v`, the protocol version.
      - A client's first frame is `hello`, sent within 10 s, naming every version the client speaks (`versions`).
      - The server answers `welcome` in the highest version both speak, and every later frame uses it.
      - A client with no version in common whose newest is older than the server's newest is closed with 4426 `client_outdated`, and reloads. With versions that run without gaps, that is a client older than every version the server speaks.
      - Any other client with none in common is newer than every version the server speaks. It is closed with 1013, reconnects within the spread, and reaches a newer task once the deploy moves on.
      - `hello` has the same shape in every version, so any server can read any client's.
    - **Validation.** The server validates every client frame strictly with zod. Clients read server frames with the lenient schemas `packages/shared` exports (`readServerFrame`):
      - unknown fields and frame types are skipped;
      - an unknown `dropped` reason reads as `access`, and an unknown `reset` reason as `gap`;
      - an `ev`'s ids may be any record.

      So the server may add to v1 without a stale client missing a drop or a reset.
    - **The flags nudge.** When `FlagCache.onChange` reports a change to a `client: true` flag, every socket of the org gets a nudge.
      - The nudge carries no values.
      - It is coalesced per org on its trailing edge: at most one a second, and always one after the last change.
      - The client refetches after a random delay within the reconnect spread, so 25,000 clients don't call `GET /api/flags` at once.
    - **Admission.** An admission hook decides who may hold a socket; it admitted everyone until C0.9 PR 2. It is asked inside the gateway's own read-only transactions: at accept (as a targeted check), in each subscribe batch and in each periodic check.
      - Since C0.9 PR 2 it is `NOTICE_ADMISSION` (`apps/server/src/realtime/admission.ts`, T22 item 30): only someone who has acknowledged the org's latest notice, over the REST gate's own plain read, so while no version exists it admits nobody. `registerRealtime` always wires it in production. Only a test sets `RealtimeDeps.admissionForTests`, to another hook or to `'none'`, which turns admission off and queries nothing, as in C0.7; the integration harness defaults to `'none'`, and the notice suite runs production's hook. `scripts/guards/api-test-overrides.test.ts` keeps `admissionForTests` out of `main.ts` and every file but `realtime/index.ts`, the server's `testing/` folder and tests.
      - Someone it no longer admits has every socket closed with 4403 `notice_required`. That happens within one check (25 s) of a new notice version, and the client shows the notice.
      - Only the sockets open when the check or the subscribe decision read admission are closed. A socket opened after that read, as one in a tab where the person has just acknowledged, is left to its own accept-time check.
      - It isn't a sign-out, so nothing local is wiped.
    - **4401.** `signed_out` means signed out on that session, for any reason.
      - Whether the close should say which reason (PRD-74 against NFR-04) is C1.8's decision for the owner (OD-42).
      - Whatever C1.8 decides must keep NFR-04: `dropped` and 4401 wipe cached server data, but unsynced local edits are kept, shown, and offered as a copy, never dropped silently.
    - **Every close** is in `GATEWAY_CLOSE`: 4401 `signed_out`, 4403 `notice_required`, 4426 `client_outdated`, 1013 `try again later`, 1001 `server stopping`, 4408 `too_slow`, 1008 `hello_timeout`, `bad_frame`, `too_many_frames` or `too_many_topics`, and 1011 `internal_error`; 1009 for a frame over 4 KiB, and 1002 or 1007, are ws's own.
    - *Why:*
      - The frame schemas live where C0.8's web app can import them.
      - Version negotiation lets one server speak to old and new clients during the PWA's update window, and stops a new bundle reloading in a loop against a task not yet replaced.

11. **Limits, the pool and the connection budget (OD-21, owner; OD-23, OD-24, OD-25, OD-26).**
    - **The budget.** It is designed for 5,000 people × up to 5 devices: 25,000 sockets across at least two realtime tasks. Each task accepts up to 25,000, so one task can carry the org while another restarts. C1.12's load test checks the numbers, including a task kill and a drain at 12,500 sockets.
    - **Upgrade limits.**
      - A session holds at most 8 sockets (429).
      - A person holds at most 40 sockets, five devices' worth (429), so no one person can fill a task.
      - A process holds at most 25,000 sockets (503). The cap is checked before the lookup, as a fast path, and again in the same tick as `handleUpgrade`.
      - A process runs at most 5 session lookups at once, and queues at most 1,000 (503 beyond that). A lookup still waiting 5 s after the upgrade arrived is refused 503. Its slot is freed only when its transaction ends, so lookups abandoned on a slow database never take more than 5 connections.
      - An upgrade waits for a slot only until 1 s before that limit (`lookupReserveMs`), and is then refused 503 without a lookup (as is one handed a slot later than that, which a busy event loop can do: the slot goes straight back), so every lookup that runs has at least a second to answer. Without the reserve, under sustained overload the queue's oldest waiter would get each freed slot with almost no time left, run its lookup anyway, and still be refused: no upgrade would get through while the database stayed slow. The reserve doesn't cover a database slower than itself: under overload a lookup may start with only the reserve left, and if it takes longer it is still thrown away after it ran, so while lookups take more than a second, upgrades can still all be refused.
    - **Frame limits.**
      - A client frame is at most 4 KiB (1009) and names at most 50 topics.
      - A socket holds at most 100 topics. A topic counts from the moment it is asked for, deciding included. More closes the socket with 1008 `too_many_topics`.
      - Each socket gets a token bucket of 20 frames, full when it opens, which refills at 5 a second. An empty bucket closes the socket with 1008 `too_many_frames`.
      - Every frame takes a token, protocol pings and unasked-for pongs included; only the pong answering the server's own ping is free. ws's automatic pong is off, and the gateway answers a ping itself, through the bucket and the backpressure marks. So a client that floods pings and never reads can't grow the send buffer.
      - A malformed frame, a binary one, or one in another version than `welcome` chose closes it with 1008 `bad_frame`.
    - **Backpressure.** Above 256 KiB buffered, droppable frames (`nudge` now; C1.3's typing and presence) are shed. Above 1 MiB, or above 256 KiB for 10 s, the socket closes with 4408 `too_slow`, and the client reconnects, resubscribes and refetches (item 9). The marks apply to every frame the server sends, protocol pings and pongs included (both droppable), and the heartbeat sweep applies them to every socket every 5 s, whether or not anything is sent to it.
    - **The pool.** Realtime's pool grows from 10 to 12 connections:
      - up to 5 lookups;
      - 1 lane;
      - 1 periodic check;
      - up to 3 flag reads (`FLAG_READS_IN_FLIGHT`);
      - 1 for `/ready`'s role check;
      - 1 spare.

      So neither `/ready` nor the check waits behind a storm of lookups. C0.9's admission read runs inside the lane's and the check's transactions, so it adds no connection. This is recorded as T18 item 8 records the worker's control pool.
    - **The reconnect spread.**
      - `welcome` and every `pong` carry `reconnectSpreadMs`, from the process's socket count: 1 ms a socket, at least 5 s and at most 30 s.
      - Suppose a client's open socket closes for any reason but 4401, 4403, 4426 and an abuse 1008. It waits a random time within the spread before its first retry, then backs off from 1 s to 30 s.
      - A lost task's sockets therefore arrive at no more than about 1,000 a second at each task they move to. Five lookups of a few milliseconds each serve well over that.
      - The rule to keep: lookups per second per task × spread ≥ sockets moved. C1.12 measures both sides.
    - **Upgrade refusals.** The browser can't see why an upgrade was refused: every refusal is close 1006. So the HTTP refusals stay. After 30 s of failed reconnects, jittered, the client asks the api whether it is still signed in. Every api route answers 401 `signed_out` once the session has ended, so C0.8's `GET /api/flags` serves; `GET /api/session` exists too, and the probe stays on flags (T21 item 4). A 4401 that was lost behind a full buffer is learned the same way. A client that 4403 or 4426 has paused asks too, at a random point in the first 30 s and every 30 s after until it resumes, since no socket of its can hear a 4401 (T21 item 4).

12. **Heartbeat (OD-16, OD-30).**
    - The server sends a protocol ping to each socket 25 s after its last one, looking every 5 s. It terminates a socket after 55 s with nothing heard: no pong and no frame. A socket that hasn't said `hello` within 10 s closes with 1008 `hello_timeout`.
    - The client sends `{ t: 'ping' }` every 25 s, and whenever it becomes visible or comes online. It treats 10 s without any frame after its ping as a dead socket.
    - Every Valkey subscriber connection sends `PING` every 5 s, so a dead one is found within about 7 s (its 2 s socket timeout).
    - The heartbeat isn't a revocation path.
    - *Why:* browsers can neither send nor see protocol pings. With 25 s of traffic each way, an ALB with the default 60 s idle timeout and most mobile NATs stay open.
    - **Readiness (OD-22).** There are two endpoints:
      - **The full `/ready`**, for deploy gating and monitoring. Its `gateway` check fails until realtime listens on `revoked` and `access`, while either subscription is down, while the stream reader is stuck (it has orgs and hasn't read for 7 s), while the last two periodic checks that had sockets to check have both failed (the point after which `closeUnconfirmed` starts closing with 1013), and while the process stops. It no longer checks object storage, which realtime never uses.
      - **`/ready/local`**, for the load balancer's health check. It fails only for reasons local to the process: before its first subscription to both channels, and while it stops.

      A Valkey, Postgres or S3 outage then fails every task's `/ready` but replaces no task, and sockets ride it out. With Valkey down, revoked sessions' sockets close at the re-checks instead; with Postgres down, a socket whose session or topics would go unconfirmed past 60 s closes with 1013.
    - **Drain.** At SIGTERM the process refuses upgrades, then closes every socket with 1001 within 1 s, and clients reconnect within the spread. On ECS the target is deregistered before SIGTERM, so the load balancer usually closes the sockets first and clients see 1006. The 1001 is the fallback, and both take the same spread.

13. **The latency metric (OD-20).** `apps/server/src/revocation/latency.ts`.
    - **When.** Each time the gateway applies a revocation (closes sockets, or drops granted topics), it logs `revocation_applied` with:
      - `handler` (`sockets` or `topics`);
      - `path` (`push`, `durable` or `recheck`);
      - `cause`, `org` and `count`;
      - `latencyMs`, measured from the change's own time;
      - `startSource`: `publisher`, `outbox`, `database`, or `unknown` (then `latencyMs` is null, and the summary counts it as `unknownStart`).

      A revocation message's session closes are one line per org. A check's closes and drops (targeted ones included, so a people signal's) are one line per person, from the earliest known start among them.
    - **Labels.** A check's session closes carry cause `ended`, whatever brought the check: an expiry or another session's end is no keys change. Its drops carry the cause of the trigger that asked for it (`keys_changed` for a periodic check).
      - A people signal's re-check takes the signal's path, since the signal is what brought in promptly what the change did (a deactivation's session ends included).
      - The re-check a session message queues for the person's other sessions is labelled `recheck`, since what it finds is by construction what the message didn't name. When it coalesces with a people signal for the same person, the signal's path wins.
      - So `closedRevoked` counts the push's own closes and those a re-check of the people it named finds, never an expiry that happened to sit next to a push.
    - **Start times.** Access is lost when the revoking transaction commits (or when an expiry passes), and each start names where it came from (`startSource`):
      - `publisher`: the push uses the api's `Date.now()` just after its commit.
      - `outbox`: the durable path's sessions message uses the `at` of the `signin.ended` event the revoking transaction appended (item 4). That is Postgres's `clock_timestamp()` when it was appended, after the writes that ended the sessions and every lock they waited for, so just before the commit. Neither start counts how long the revoking transaction ran, so the push's and the durable path's latencies can be compared.
      - `database`: a re-check uses Postgres's base rows for what ended:
        - a session's `revoked_at`, its device's `signed_out_at`, its person's `deactivated_at`, `expires_at` or the idle limit;
        - for a lost topic, the earliest time the base rows give for the change that took its token. A team topic's is the earlier of the person's deactivation and, when no membership of the team is active, the last removal. A person or org topic's is the deactivation.

        Realtime reads no outbox (item 14), so a re-check has no commit-side time. `revoked_at`, `signed_out_at`, `deactivated_at` and `removed_at` are each the revoking transaction's `now()`, its start, which comes before its commit by however long it ran: usually milliseconds, each lock wait at most 2 s (`lock_timeout`), the whole at most 30 s (`transaction_timeout`). A `database` latency can therefore read high by that much, never low: it may report a Rule 6 breach that didn't happen, never hide one. The stamps stay `now()`, because the deactivation, device sign-out and PIN reset find the rows they ended by `revoked_at = now()` and `signed_out_at = now()`. An expiry's and the idle limit's times are exact.
      - A people signal is measured from the base rows the re-check reads (`database`), whichever path brought it.
    - **Clamping.** The end time is realtime's `Date.now()` when the close or `dropped` frame is sent. Values are clamped to 1 ms–1 h. A latency below −1 s is counted (`skewed`), with its `skewMs`.
    - **Summaries and gauges.** Every 30 s the gateway logs:
      - `revocation_latency` per (handler, path, startSource), so no summary mixes starts from different points, with `count`, `p50`, `p95`, `p99`, `max`, `unknownStart`, `skewed` and `windowMs`. `max` is exact, and the percentiles (from `node:perf_hooks` `createHistogram`, to 3 significant figures) never exceed it;
      - `gateway_gauges`, with `oldestUnconfirmedMs`, socket, topic and org counts, the reader's lag, the spread, lookups running and waiting, decisions waiting, the recently-revoked set's size, refusals and closes by cause, `reset` frames sent, topics dropped by path, shed frames, topics answered `retry`, and `longestLatencyMs`, the longest revocation latency since the last gauges line (read before the summary starts a new window; null when none had a known start). It is written every 30 s while there are sockets, and once a minute otherwise.
    - **Levels.** Info up to 30 s, warn above 30 s, and error above 60 s (a Rule 6 breach). The gauges warn when `oldestUnconfirmedMs` is above 40 s, and are an error above 60 s.
    - No latency or gauges line carries a person's or session's id, a topic, a token, a phone number or content; the counts are per org.
    - C0.13 turns these into the "revocation latency" dashboard and its alarms.

14. **What realtime never does (OD-17, OD-41).**
    - Apart from C0.5's pre-org session lookup, every transaction it opens is read only. That lookup is a short read-write transaction whose `FOR SHARE` takes an xid for milliseconds, and it writes no row.
    - It writes nothing to Postgres. `scripts/guards/realtime-readonly.test.ts` enforces this, and its header names the lookup as the one exception.
    - It stamps no `last_seen_at`, keeps its `hearth_app` login (T18), reads no outbox, and imports no privileged module.
    - The per-socket lines (open, error, dead) are at debug, and the lines at info and above carry counts and org ids, never a person's or session's id, so its logs are no presence history (D34).

15. **An org with no system principal (OD-37).**
    - Its sockets close with 1013 `try again later`, never 4401, and the periodic check logs `ws_recheck_no_system_principal` at error level. The session may be live, and a 4401 would make C1.8's client wipe its cached data.
    - In a subscribe lane it is a lane failure: `retry`, and nothing closes.
    - Any other error fails the whole check, as before.

16. **Hosting (OD-31, OD-45; for C0.11 and C0.12).** These hold on C0a's minimal non-prod deploy too:
    - `/ws` is routed by path on the app's own host, never a subdomain. The `__Host-` cookie and the exact Origin check need it, and so does C0.8's CSP.
    - At least two realtime tasks, each sized for 25,000 sockets.
    - No stickiness.
    - An idle timeout of at least 60 s on the load balancer, and on CloudFront if it fronts `/ws`. The PRD's hour is fine.
    - A target-group deregistration delay of 10 s or less. ECS deregisters a task's target before SIGTERM, so clients usually see 1006 rather than the drain's 1001. The reconnect spread covers both (item 11).
    - Target-group health checks on `/ready/local`, never the full `/ready`. An outage of a shared dependency must not get every realtime task replaced at once.
    - A Valkey with `maxmemory-policy noeviction`, whose ACLs BUILD-PLAN C0.12 lists. Every service's user may run `CLIENT|SETNAME`, `CLIENT|SETINFO` and `INFO`, which ioredis 6 sends on every connect (the connection's name, its library's name and version, and its ready check), and `PING`, which Hearth sends itself (`/ready`'s check and the subscribers' keep-alive, item 12).
      - A refused `CLIENT` doesn't fail the connection: ioredis ignores it. A refused `CLIENT|SETNAME` leaves the connection unnamed; if only `CLIENT|SETINFO` is refused, it keeps its name and only its library's name and version (`lib-name`, `lib-ver` in `CLIENT LIST`) stay blank. Either way Valkey's ACL log gains a `NOPERM` entry for each refusal on every connect.
      - A refused `INFO` makes ioredis write a plain-text warning on every connect, outside the JSON logs.
      - `HELLO`, `AUTH` and `QUIT` need no grant: Valkey runs its no-auth commands whatever the ACL says.

17. **How the Done line is proved (OD-03, OD-38).**
    - Integration tests on the Compose stack prove it, with two realtime processes:
      - a deactivation closes every socket of the person within 60 s on each path: the push, the durable path alone (with the api's publish off), and the re-check alone;
      - a sign-out and a device sign-out close their sockets by the push and by the durable path alone, leaving the person's other sockets open;
      - a PIN reset and an admin's sign-out of someone's devices close their sockets by the push. Each appends `signin.ended` and ends the same session rows, so the durable path and the re-check treat them as they treat a sign-out.
      - The durable tests first wait for the consumer's checkpoint. They run on a realtime process whose periodic check can't fire during the test, so its per-path counters show that the durable path closed each socket or dropped each topic, not a check that read the change first.
    - Removal from a team drops the `team` topic within 60 s on each path, and keeps the socket and its other topics. The tests write the removal as the harness superuser, because C0.16 adds the first runtime producer.
      - The push path uses `publishAccess`, as C0.16's api will.
      - The durable path uses an appended `acl.changed` with C0.16's future reason.
      - The re-check runs alone.
    - Unit tests with fake timers prove the bound at production timings, with re-checks failing.
    - R6-10 is a c0 case for the decisions `can()` makes. The integration tests that prove the timing cite R6-10 in their names. R6-10b, a C1.1 todo, covers spaces.
    - **On a deployed stack** (C0a's minimal non-prod deploy, then prod for C0.19's exit), the proof is a drill. With sockets open on two realtime tasks, deactivate a test person and remove another from a team. Then read `revocation_applied` and `revocation_latency` for each path from C0.13's dashboard: every value is under 60 s. A person runs it, never a coding agent (`CLAUDE.md`: coding agents never connect to production), with synthetic test people, so no one's data is read.

    - **C5.6's slide snapshots.** The 4 KiB cap binds client frames only (ws `maxPayload`), so a server frame may be larger. But a snapshot is content, and content in a frame is OD-14 (b), the owner's and the DPO's decision, at C5.6.
    - **C1.3's presence** (PRD-58: changes reach others within 5 s) can't rest on the 25 s heartbeat, because a socket that dies silently is seen only at the dead limit. It uses explicit closes and visibility changes, and the heartbeat's numbers don't bind it.

1. **The provider interface** (`apps/server/src/auth/sms/provider.ts`; the name `SmsProvider` stays, AQ-15).
   - `start(to)` sends a code and answers the provider's opaque reference, which never holds the number or the code, and whether the provider handed back a verification this call didn't make (`foreign`, item 2).
   - `check(ref, code)` answers `approved`, `wrong` or `gone` (expired, cancelled, used or past the provider's own cap), and is never retried, since a check may have landed when its reply was lost.
   - `cancel(ref)` is best effort; an unknown or finished reference counts as done.
   - Each provider names the transfer-register entry it needs (`transfer`; none for the fake). A failure is an `SmsProviderError` with a kind, the provider's numeric code and the HTTP status, never the number, the code or the provider's message, which can quote the number. The provider is called only outside transactions.
   - The implementations: `sms/twilio.ts`, Twilio Verify (item 10); `sms/fake.ts`, Verify's semantics in memory, sending nothing (a second start for a number with a pending code hands back the same reference and code with one more send listed, so it reads as foreign, and a 6th send or check is refused); and `sms/hearth-codes.ts`, built now (AQ-16), where Hearth makes the code, a `TextSender` only delivers it, the reference is `h1.<nonce>.<MAC>`, and `check` recomputes the MAC in constant time. That is the shape the AWS End User Messaging fallback takes (T7), which takes over from Twilio only by a reviewed config change, never an automatic failover (AQ-14); no sender exists yet.
   - `createFakeVerify()`, the only path `main.ts` takes to the fake, refuses anywhere but this machine (T14 item 1) and prints `[local only, not a log line] Hearth code for <masked number>: <code>` to stderr, the same line for sign-in and re-authentication codes, which the e2e suite reads. The `FakeVerify` class prints nothing and is for tests.
2. **The challenge record** (`apps/server/src/auth/codes.ts`). One per number, `otp:{numberTag}`: a hash of the owner (the sign-in attempt's key, or `r:<session id>` for a re-authentication), the provider's reference, the tries counted and when it was made, on Valkey's clock. It never holds a code or a number. It lives 10 minutes, and checks are refused from 5 minutes after the request (PRD-53). Four Lua scripts compare and act, so a script that finds another owner's record, or none, changes nothing:
   - `OPEN` replaces any record for the number with the caller's, and answers the replaced reference, which the caller cancels before it starts its own code;
   - `ATTACH` sets the reference, only on the caller's record and only once;
   - `RESERVE` counts a try before the provider is asked, so parallel guesses stop at 5; past the 5 minutes it deletes the caller's own record and answers its reference, the only one a caller may cancel;
   - `SETTLE` applies the provider's verdict only while the record still holds the caller's owner and reference. A provider failure (no verdict) is settled first: it answers `failed` whatever the record, giving the try back only on the caller's own live record, so the caller gives the day's check back (item 3) even when a newer request replaced the record or another check used it meanwhile. Otherwise another owner's record, or another reference, answers `displaced` with the check's own try, and a record that is gone (another check killed or used it) answers `wrong`, or `dead` at the 5th, from the check's own try, whatever the provider answered. Neither changes anything.
   - A `gone` verdict marks the record gone instead of deleting it, and answers expired. The provider also answers gone to a check of a code it has just approved, so when two checks of the right code race on one attempt (two tabs, a double submit), the approval may settle after the gone one. A marked record answers every script as a deleted one would (`OPEN` no reference to cancel, `RESERVE` expired, `ATTACH` lost, `SETTLE` the check's own count, or `failed` with no try given back), except an approval of its own owner and reference, which still uses it up and signs in.

   A refusal depends only on the tries counted and the owner, never on whether a reference is attached, so a roster number (which has one) answers exactly as one off the roster (which never has one). So a stale attempt can't delete or cancel the newest owner's code, spend or refund one of its tries, or kill a signed-in person's pending re-authentication code.
   - **A displaced check (changed in A3's review, Q27).** A check that a newer request for the number overtook during the provider's round trip signs nobody in, even when the provider approved it. On sign-in it answers from its own try, `code_wrong {triesLeft}` or at the 5th `code_dead`, and the attempt's next check answers `code_expired` for every number alike. The design first answered it `code_expired`, which told a roster number apart: off the roster `RESERVE` fixes the reply at once, before any newer request can land. Re-authentication, signed-in traffic with nothing to hide, answers it `code_expired`.
   - **The foreign check.** Twilio reuses a pending verification for the same number on the same Service (same reference, same code). After every start the deliverer asks the record whether its owner still holds it. A request that has lost the record leaves the verification alone, so it never cancels a newer owner's. One that still holds it and got a foreign verification cancels it and starts once more; a second foreign reply is cancelled too and nothing is attached (logged as `provider_foreign_verification` at warn), so the attempt answers as after a lost text. If that first cancel fails, nothing more is started or attached, and the failure is handled as a failed send (`sms_send_failed`; re-authentication answers 503): the verification is most likely still pending, so a second start would only hand it back and text its code again. The next request tries the cancel again. This defends against a verification planted with a stolen key (item 10). Residual, kept on review (Qodo): a start whose first try is counted as a send that Twilio hadn't recorded when it answered the retry (a dropped connection, a timeout Twilio handles after the retry, or a 5xx that sent nothing) can read a pending verification this call didn't start, listing exactly one send, as its own and attach it. Its code was made by Twilio and texted to the same number (custom codes stay off, item 10), so a code first texted a few minutes earlier, within Twilio's validity, finishes the new attempt; every check is still bounded by this record's 5 minutes and 5 tries and by Twilio's own 5 checks. Reading every reply after an uncertain try as foreign would instead cancel and restart on each provider glitch: an extra paid text, the code already sent dead, and nothing attached after two glitches in a row. The owner kept it as it is on 21 Oct 2026.
3. **The floor and the breaker** (`api.otp`, built per `registerApi` from `OTP`, so each api process has its own).
   - A refused sign-in check (`code_wrong`, `code_dead`, `code_expired`), and one the provider failed (503 `unavailable`), answers no sooner than 2 s (`OTP.verifyFloorMs`, AQ-04) after it arrived, so a roster number's round trip to the provider can't be timed against the instant answer for a number off the roster. Successes aren't padded, nor is the open breaker's 503, which answers every number alike without asking the provider.
   - After 3 provider failures within 60 s, every check, for any number, answers 503 `unavailable` for 30 s without asking the provider (`OTP.breaker`, AQ-20). A failure gives the try back on the caller's own live record (item 2), and the day's check in every case, even when a newer request replaced the record or another check used it meanwhile (`otp-v24h`, or `reauth-check-p24h` for re-authentication; the per-IP and per-session windows still count the request), and a sign-in check the open breaker refuses counts in no window, since it is refused before them. So a person who presses again through a provider incident spends none of the day's checks (T14 item 5).
   - Every provider cancel on `/otp/verify` runs after the reply, so a roster number's check costs one round trip before it, whatever the try.
   - Tests may shorten the floor and set a breaker of their own through `ApiDeps.otpForTests`, which `scripts/guards/api-test-overrides.test.ts` keeps out of production code; integration tests on the real timing pin the 2 s.
4. **The `verified` step** (`apps/server/src/auth/attempts.ts`: `code_sent`, `verified`, `set_pin`, `step_up`). Once the provider approves a code the attempt is `verified`, its record is used up, and the finish follows in the same request. If the finish fails before it uses the attempt up (409 `try_again`, Valkey or Postgres down), a retry with any 6 digits finishes it with no second check, counted only in the per-IP window, until the attempt's 10 minutes end. The code-only finish uses the attempt up as its last statement before `COMMIT`, so only one request turns it into a session. A finish that finds the person has left or the number has moved answers as a wrong guess at that count and puts the attempt back at the code, whose record is gone, so its next check answers `code_expired`; on a `verified` retry it drops the attempt (401 `attempt_expired`).
   - Residual: using the attempt up is a Valkey delete that runs before Postgres's `COMMIT`. A `COMMIT` that then fails (a lost connection, or the 30 s `transaction_timeout`), or a delete whose reply was lost, leaves no attempt and nothing committed, so the person asks for a new code. It fails safe: no session is issued twice.
5. **The PIN rule** (`packages/access/src/model.ts` `PIN_ROLES`, `reauth.ts` `holdsPinRole`).
   - `PIN_ROLES` equals `OWNER_ONLY_ROLES`: Owner, Admin, AI Admin, Leadership, DPO and Compliance Officer. `roles.test.ts` pins the two lists equal, so splitting them is a reviewed change. It is a code constant, never a flag (`CLAUDE.md`, Database). Team Admin and Member sign in on the code alone.
   - Whether someone holds a PIN role is read in the transaction that acts on it (`holdsPinRoleNow`, `apps/server/src/access/world.ts`): after their person row is read `FOR SHARE`, as its own statement, with no lock on `role_assignments`. The person's row is where a sign-in and a grant meet: a grant that holds that row, as C0.16's will (item 14), makes the finish wait and then see the role (the race case in `check-concurrency.ts`).
   - The code-only finish reads the roles, makes the person's `users` row on their first sign-in (beside `signin.started`) and issues the session in one transaction. `/pin/set`, `/pin/verify` and the dormant `/passkey/verify` read the roles again where they issue the session, which is then issued under the PIN rule. A role removed between the code and the PIN step still finishes with the PIN (stricter), with a normal lifetime.
   - Three invariants hold the rule. I1 (C0.8): a sign-in issues a session only after reading the roles so, and to a PIN-role holder only through the PIN step. I2 (C0.8): each re-authentication route refuses a session whose method isn't its own, deciding in the transaction that stamps (item 6). I3 (C0.16): any write that gives someone a PIN role first takes their person row `FOR NO KEY UPDATE`, then ends their open sessions, then writes the role row, in one transaction (item 14).
   - The names: the design called them `PRIVILEGED_ROLES` and `isPrivileged`. In this repo "privileged" means Rule 9 access, and R9-02 refuses any `packages/access` export whose name says it, so they became `PIN_ROLES` and `holdsPinRole`, and the owner kept them (third round). The sign-in code says "PIN role" and "PIN rule" throughout (`PIN_RULE_SESSION`, `holdsPinRoleNow`, `issuedUnderPinRule`, `pin_rule` on `signin.started`, `pinRule` on `auth.sign_in`); every Rule 9 use of "privileged" stays.
6. **Re-authentication by method** (`reauthMethodOf`, `packages/access/src/reauth.ts`; `apps/server/src/auth/account.ts`). Decided by the session first:
   - a session issued under the PIN rule re-authenticates with the PIN (`pin`), whatever its holder's roles are now, so no SMS stamp ever lands on it; if its PIN has been cleared, only a new sign-in mends it (`sign_in`);
   - any other session uses a fresh SMS code to the person's own number (`code`), unless its holder holds a PIN role now, which a grant that didn't end their sessions would cause and C0.16 must never do: then only a new sign-in, through the PIN step, mends it (`sign_in`).

   The server reads the session's raw facts in the deciding transaction (`actingSession`: a stamp from the last 5 minutes, whether the person has a PIN, and whether the session was issued under the PIN rule), and `can()` still receives one boolean, `reauthenticated()`, false for `sign_in` even with a fresh stamp. "Issued under the PIN rule" is read as `expires_at - created_at` shorter than `SESSION.lifetime`: only `issueSession` writes `expires_at`, from the same `now()` as `created_at`, and `policy.test.ts` keeps `PIN_RULE_SESSION` shorter. It is defence in depth behind I1 and I3, not the primary control.
   - A stale admin request answers 403 `reauth_required {method}`. A re-authentication route that isn't the session's own answers 409 `reauth_method {method}` before anything is checked or sent, and writes nothing (it counts only in the route's windows); it is logged as `reauth_wrong_method` at warn, since the web app only calls the route the method names, and reaches no audit row (Q5). A `sign_in` method also logs `pin_rule_session_mismatch` at warn. Both lines hold the person's id, and the wrong-method line the route, never the method, a number or a code.
   - From C0.9 PR 2 every re-authentication route asks the acknowledgement gate first (`actingBy()`, with the use `'reauth'`; T22 item 28): a session whose person hasn't acknowledged the current notice answers 403 `notice_required` before the method guard, so it can't make the provider send a code. Before any version is published only the DPO passes, by PIN (T22 item 29).
   - `POST /api/auth/reauth/pin`: the per-session window, which lets requests through with Valkey down, then the PIN check and its lock, as at sign-in (T14 item 9).
   - `POST /api/auth/reauth/code/request`: the per-session window, failing closed (AQ-10); one request per session at a time, under a send lock (`reauth-send:<session id>`, `SET NX` for at most 15 s, `REAUTH.sendLockMs`, freed only by its holder), since every request from one session owns the record as `r:<session id>` and two at once would both pass the start's owner check, so a double tap answers 409 `try_again` before anything is opened or sent (a request slower than the lock no longer holds it); the method guard; the person's current number, read with no lock, since `phone_numbers` comes before devices and sessions in the lock order (none: 409 `no_number`, AQ-23); the transfer gate and the global SMS cap, each audited and answered 503; 20 code requests per person a rolling day that pass the transfer gate and the SMS cap, failing closed (AQ-09), so a request either holds back spends none of the person's day (from C0.9 PR 2, T22 item 27), and a full day answers 429 and gives the cap's count back; then the record, owned by `r:<session id>`, and the text, sent before the reply (signed-in traffic, nothing to hide), so a failed send answers 503.
   - `POST /api/auth/reauth/code/verify`: the per-session window and 20 code checks per person a rolling day, failing closed (AQ-09); the method guard before any provider check is spent; the breaker; no floor. A check the provider never answered (the breaker open, or the provider failing) gives the day's check back, and so does one refused before any check (from C0.9 PR 2: the acknowledgement gate's 403 `notice_required`, the method guard, or a session that ended). An approved code whose stamp fails before it commits (409 `try_again`, Postgres lost) is kept for 2 minutes (`REAUTH.approvedMs`) under `reauth-ok:<session id>`, holding the number's id, so a retry with any 6 digits stamps the session with no second check, as sign-in's `verified` step does (item 4); it counts only in the per-session window, reads the method and the number again, and uses the approval up as its last statement before `COMMIT`. A new code request from the session deletes the approval before it opens the record, so from then on only the new code stamps it. Residual, as item 4's: a `COMMIT` that fails after the approval is used up asks for a new code. An approved code stamps the session in a second transaction, which reads the method again (a grant committed since refuses, and the spent code stamps nothing) and the number, with no lock: `actingSession` has already taken the person, device and session `FOR SHARE`, and the person's row serialises this against a phone change (C0.16), which takes it `FOR NO KEY UPDATE` first and ends every session.
   - Re-authentication codes don't count against sign-in's per-number windows, so a working hour of re-authentication can't lock someone out of signing in. They share the number's one record, as Twilio holds one pending verification per number per Service: a re-authentication code replaces a pending sign-in code, and the reverse (T14 item 3's residual).
   - Outages: Valkey down stops SMS re-authentication but not the PIN's; Twilio down stops SMS re-authentication and every sign-in, but not a live PIN-rule session's PIN re-authentication. So PIN-role holders keep their admin powers through either.
   - C0.8's web app holds the contract only: `ReauthMethod` (`packages/shared/src/auth.ts`, its one definition), the `method` on both refusals, read by `apps/web/src/api/reauth.ts` (a method it doesn't know reads as `sign_in`), and the code and PIN fields (`ui/CodeField.tsx`, `ui/PinField.tsx`). C0.9's DPO pages are the first admin actions in the UI, and they re-authenticate inline with the PIN, then send the refused request once more (T22 item 15); C0.16's re-authentication sheet replaces that step.

12. **The enrolment window** (an accepted risk, Q24). A PIN-role holder's first PIN is set on the SMS code alone: after a grant to someone with no PIN, an Owner's reset, the bootstrap's first Owner and DPO, or a phone change (C0.16). Between that and the holder's own first sign-in, whoever holds the number (a SIM swap, a port-out) can sign in, set the PIN and get a PIN-rule session, and the holder is locked out (`pin_already_set`, then a PIN they don't know); they notice, but only afterwards. What limits it: procedure (the holder signs in at once, with the granting or resetting Owner present or on the call), C0.16's console ("PIN not set yet"), keeping a former holder's PIN on removal so a re-grant needs it (Q3), and C0.14's alert, which treats `sms_new_pin` as urgent but fires only once the session exists: it detects a takeover, it doesn't prevent one.
13. **Residuals.**
    - Members and Team Admins rest on one SMS: whoever receives their texts (a SIM swap, a port-out, interception, a linked device) can sign in as them on a new device, for up to 90 days. From C0.16 a Team Admin's team powers need only a fresh code, which is why leaving Team Admin out of the PIN roles is the owner's to confirm (Q2).
    - There is no phishing-resistant factor while passkeys are off: a relayed code and a phished PIN still work against a PIN-role holder.
    - Twilio joins the trust base. It makes and checks the code, and a stolen key can send texts at Hearth's cost (with any sender name), read Verify's logs (numbers), cancel pending codes and mark a verification approved. Hearth trusts only `approved` from its own check, and an approval by update answers 404 to a later check (item 11, gate 1).
    - The floor's slow-check leak, the outage's 503 before the breaker opens, and a sign-in request replacing a pending re-authentication code (T14 item 3).
    - A role removed between `/otp/verify` and the PIN step leaves a PIN hash nothing asks for until a re-grant.
    - A PIN-role power that needs no fresh stamp rests on I1 and I3 alone: today one, an Admin creating public channels or standalone rooms (of any visibility, ROOM-01) while the setting is `admins` (`packages/access/src/can.ts` `publicCreation`).
    - The success reply (`signed_in` or `code_verified`) shows whether someone holds a PIN role, but only to the holder of the right code; refusals are padded to the floor.
    - A PIN-role holder whose PIN is locked until a reset can't sign in until an Owner resets it, with no passkey to fall back on, and a sole Owner needs the bootstrap's break-glass path, so at least two Owners are recommended (Q6).
    - Cost: each sign-in without a live session and each SMS re-authentication is a paid verification. `sms-global` caps the code sends Hearth asks of the provider at 100 an hour, counting each code request once, so a start's one retry after a network error or a 5xx (when Twilio had sent already), and a foreign reply's cancel and second start (item 2), can each add a text it doesn't count.
14. **What C0.16 inherits.**
    1. I3 in the lock order. Every write that gives someone a PIN role (a grant; the approval of a DPO or Compliance Officer proposal, which inserts the role row; a roster row; the bootstrap) takes their person row `FOR NO KEY UPDATE` after the actor's rows, then ends all their open sessions (`role_changed`), then inserts the role row: people → sessions → role_assignments. 2. **A session is a document** (D-01, D-02; `apps/web/src/session/document.ts`, `session/runtime.ts`).
   - Every change of person ends in a full page load: sign-in, sign-out, a 401 `signed_out`, the gateway's 4401, a session answer (or, from C0.9 PR 2, a notice answer) naming someone else, or another tab's sign-in or sign-out (a `BroadcastChannel` message carrying no id and no data). A page restored from the back-forward cache reloads. So the QueryClient, the gateway client, the router and every module's state live exactly as long as one person's document.
   - Acknowledging the notice (C0.9 PR 2, T22 item 31) changes no person, so nothing reloads: the runtime's notice store starts or resumes the gateway and refetches every query, and the same channel's `{t:'notice'}`, which carries no id and no data, tells the browser's other tabs to check; older tabs ignore it. The path a tab was sent from to `/notice` stays in the runtime's memory, never in storage.
   - The runtime's `end()` runs once: it marks itself ended, halts every request (`api/http.ts`), stops the live connection, cancels and clears Query, then leaves the document. C1.8 inserts its unsynced-edits step before the halt.
   - Nothing user-specific is kept in browser storage until C1.8. sessionStorage holds only four `hearth:*` keys (why the last document left, a return path from `APP_PATHS`, a reload stamp and a focus flag), the router's scroll offsets keyed by path, and the router's own one-shot reload marker. WS-01 keeps every other file off sessionStorage, and the app off localStorage, IndexedDB and Cache Storage.
   - **The boot order.** `index.html` loads one module, `src/main.ts`, whose static import graph holds only CSS and modules that import no package. It runs `preBoot()`, which removes the router's scroll cache unconditionally, reloads a page restored from the back-forward cache, turns a failed chunk into a reload at most once a minute, and sets zod's `jitless` before zod loads, so zod never probes `new Function` under the CSP. Then one dynamic import loads the app. By ES module semantics nothing in that import's graph, router-core included, evaluates before the call, whatever the bundler does with chunks. **A chunking change (`manualChunks`, `advancedChunks`, a vendor split) or a new static import in `main.ts` must keep that rule**: WS-10 checks the source and SH-12 the built bundle.

3. **Data.** One QueryClient per signed-in document (`session/query-client.ts`; WS-02 keeps `new QueryClient(` there).
   - A query retries once on 409 `try_again` and up to twice on a 5xx or no answer; a mutation retries once on `try_again` only, since any other failed write may have landed. Each wait is full jitter, doubling from 1 s to at most 30 s. A `signed_out` refusal from any query or mutation ends the session. From C0.9 PR 2, a 403 `notice_required` from any query or mutation is never retried: it sends the tab to `/notice`, whose own read decides (T22 item 31).

4. **Gateway client policy** (`apps/web/src/live/gateway-client.ts`, `CLIENT_POLICY`; the client's side of `packages/shared/src/gateway.ts` items 1 to 7).
   - Limits come from each `welcome`, capped by `GATEWAY_LIMITS`: a welcome can lower them, never raise them. Until the first welcome the client keeps a 25 s heartbeat and a 30 s spread.
   - No welcome within 15 s of opening, or no open within 30 s of connecting, is a failed try.
   - Its own token bucket (18 frames, refilling 4 a second) stays under the server's 20 and 5, so the server's never empties.
   - "Reconnecting…" shows once the client has failed to reconnect for 30 s, and from then it asks `GET /api/flags` whether the session still holds (T19 item 11). A probe unanswered after 20 s is let go and its request ended, so a request that hangs can't hold back the next one or stay open until it, and a late answer counts for nothing. 4401 ends the session; 4426 reloads at most once a minute, after which the banner offers Reload; 4403 pauses the connection for the notice. 8. **The transfer gate at outbound clients** (PD-15).

But the provider is called after that transaction commits, so a withdrawal committing in that moment doesn't stop the one send already decided: at most its starts, each of 4 s a try with the adapter's one retry (T20 item 10), and one more start after a foreign verification (T20 item 2), all for that one code request. A provider counts as cleared for sends only while it has an open clearance and the latest version is a stand-in or states that clearance's seven notice facts (PD-41), so a "Save and keep cleared" that changes a stated fact suspends its sends until a new version is published. Before any version, `transfer_cleared()` keeps clearance alone. Sign-in and re-authentication codes ask `transfer_send_state()` instead, and go to the DPO alone before any version and while the published one doesn't state the clearance (PD-59), so OD-04's Twilio transfer before v0 is the DPO's own number.

Something that only shows whether a provider is cleared (C0.13's RUM capability) reads it plainly, with no lock, in its own read-only transaction: `transfer_cleared()` takes row locks, which a read-only transaction refuses, and is only for deciding a send.

11. **The interlock** (PD-18, PD-19; T17 item 9).

22. **What a version is (PD-33).**
    - **The words.** `body` is the exact text people acknowledge, in a fixed line format: `## ` a section, `### ` an entry, `- ` an item, any other line a paragraph, with blank lines between blocks. It holds no version number and no date; the screens show both from the row, and render the body as React text, never HTML (WS-07). The DPO's text and the org's name are flattened to one line and never start one, so stored text can't forge a heading or an item.
    - **The generator.** `generator` names the code that wrote it (`NOTICE_GENERATOR`). It is null on a stand-in (the seed's v0, the DB fixtures', the integration harness's), which only ever comes before the first generated version (`notice_versions_generated()`). Production never gets a stand-in.
    - **Never changed.** A trigger refuses an UPDATE of a version or of either link table for every writer, the superuser included (`notice_unchanged()`). No role holds INSERT, UPDATE or DELETE on any of them.
    - **Numbering** continues from the latest version: production's first generated version is v0, and the seed's org gets v1.

      - *Who else receives your data*: one entry per cleared provider, saying what it does, what it receives, where it processes and stores the data, how long it keeps it, who it passes it to, and whether it trains models on it;
      - *Your first sign-in code* (OD-04): only when Twilio is listed, naming Twilio Verify's countries;
      - *Access to production systems* (PRD-101): the separate emergency role, each use logged and every use reviewed by a second person each quarter;
      - *Your rights*: until PR 3, through the DPO contact in the org's employee data-protection policy.
    - **What Hearth doesn't do (PD-58).** Built from the register being published, never a fixed sentence. `DOES_NOT` (`packages/shared/src/notice-text.ts`) holds three clauses, each with the purposes that would make it false:
      - "record calls, meetings or drop-in rooms": `recording_meetings`, `recording_drop_in`;
      - "transcribe anything": `transcription`, `voice_message_transcription`, `transcription_test_set`;
      - "summarise what you write or draft text from it": `meeting_notes`, `org_brain`, `ai_writing`, `people_inference`, `assistant`, `agents`.

      A clause is left out once any of its purposes is active, and the section once none is left. Each clause left is an item ("Hearth doesn't transcribe anything."), followed by "None of these happens unless a new version of this notice says so and you have acknowledged it." So no clause contradicts a purpose the same notice lists, and the sentence stays true beside a retired entry. Every purpose is in exactly one clause or in `DOES_NOT_EXEMPT`, with its reason (NTG-10), so a new purpose forces a decision; sensitive-data detection is exempt, being listed as a purpose once active (PDPA-17). Until A0 the last two clauses' purposes are all AI and never active, so both always print: decision 5's line, written without the word "AI" (decision 8).
24. **The generator and its copy (PD-36, PD-53, PD-62).**
    - **Where it runs.** `generateNotice()` is pure and deterministic. It runs on the server, and on the web only in tests. Country names come from `Intl.DisplayNames('en-GB')`, falling back to the code.
    - **Its id.** `NOTICE_GENERATOR` (`c09.1` in PR 2) changes with any change to the output, which NTG pins with a digest.
    - **Preview is publish.** The DPO's preview is the server's own draft. A sha-256 digest of its body, generator id and sources ties the preview to the publish (item 25).
    - **The copy.** British and short; never "ask", "I agree" or an AI word; the verb is "acknowledge". NTW-10 holds every branch of the generator and every copy constant to `AI_COPY`, which now lives in `packages/shared/src/ai-copy.ts`; `apps/web/src/strings/ai-copy.ts` re-exports it, so ST-02 and the e2e `noAiCopy` check are unchanged. Each basis has its own wording: employment, the employment exception, with no consent needed; legitimate interests, PDPA-02's statement with the assessment's reference and "contact the Data Protection Officer to learn more"; business improvement, data already held; another exception, the provision cited.
    - **The DPO's free text (PD-62).** Publishing refuses a draft whose basis reference, retention or a provider's stated text facts match `AI_COPY` (`free_text_ai_copy`). The problem names the purpose or provider and the field, never the matched word, so the Notice tab stays clean under `noAiCopy`. Only the publish route checks it: the route always regenerates the draft and is `publish_notice()`'s only caller (a guard in `scripts/guards/api-test-overrides.test.ts` keeps it so), and `AI_COPY` is code that changes with the copy, which SQL doesn't repeat. The org's name isn't checked at publish, since the DPO can't change it: a unit test holds the seed's name to `AI_COPY` (`apps/server/src/compliance/notice.test.ts`), and the bootstrap PR and C0.16's org settings refuse a matching name (item 37). Until they do, the generator prints "your organisation" for a name that matches (NTG-13).
    - **For the DPO to confirm:** OD-04's paragraph, the production-access paragraph, the three "doesn't do" clauses and every basis wording.
25. **Publishing (PD-37, PD-38, PD-39).**
    - **The routes.** `GET /api/admin/notice` (`notice.read`, read only) answers the draft with its problems, warnings, changes, digest and `upToDate`; the latest version, with how many people have acknowledged it (a count, never names); and up to 100 versions of history. `POST /api/admin/notice/publish {seen, digest}` (`notice.publish`, the DPO with a fresh PIN) reads and regenerates the draft in the same transaction, then refuses, in this order: a `seen` that isn't the latest version's number (null while none exists), 409 `notice_changed`; any problem, 400 `notice_invalid`; a digest other than the draft's, 409 `notice_changed`. Then it calls `publish_notice()`, appends `notice.published` and answers `{notice, version}`.
    - **The function.** `publish_notice()`:
      - re-checks the DPO (`notice_check_dpo()`: the person, then their `dpo` role, `FOR SHARE`);
      - locks every non-AI purpose's latest version `FOR SHARE`, again until the row held is still the latest, and every non-AI transfer entry `FOR SHARE`, so no purpose changes and no clearance starts or ends while it runs;
      - locks the org's own `orgs` row, then the latest version, `FOR NO KEY UPDATE`, so two publishes, the first two included, take turns;
      - refuses a `seen` that isn't the latest version, or sources other than those it locked (HF007);
      - applies the rules (HF008);
      - inserts the version, numbered after the latest, and the links from the locked rows;
      - writes `notice.publish`, with ids and numbers only.
    - **The rules, which block,** in this order: an active purpose has a basis and a retention (item 4's four included); no active purpose rests on a consent-type basis (consent until C1.3's consent items, deemed consent by conduct until PR 3 publishes how to withdraw, s15A until per-person opt-out windows are tracked: PD-38); every provider an active purpose lists has an open clearance; the DPO's free text holds no AI wording (the route alone, item 24); the body is there and at most 100,000 characters, and the generator id is well formed; and a draft identical to the latest version (the same words, generator and sources) isn't published again. A retired purpose is listed, but no rule applies to it: 0009 already requires its basis and retention.
    - **Warnings, which never block:** a cleared provider no active purpose lists; a passed review date; `sends_waiting`, a cleared provider whose stated facts the latest generated version doesn't state; `same_text`, the words unchanged but the sources moved, so everyone would acknowledge the same words again; `dpo_contact_pending`, until PR 3; and `production_access_pending`, until C0.19 (PD-57).
    - **Two first publishes at once.** The second waits on the org's row, then finds the first's version and gets HF007 (409 `notice_changed`), never a 23514 or a 500.
    - **Nothing publishes by itself (PD-39).** A register change or a withdrawn clearance never creates or forces a version, and every version is acknowledged again by everyone. The DPO's pages say the notice is out of date and what changed (item 31). Meanwhile the gates hold: a changed purpose is no longer notified, and a withdrawn clearance stops sends at once (item 27).
26. **Acknowledging (PD-42).**
    - **The routes.** `GET /api/notice` (`notice.read_own`, read only, `touch: false`, since `/notice` polls it) answers whose answer it is (`person`), the standing, the current version, what changed since the last generated version you acknowledged before it (null when there is none, or the current version is a stand-in), and up to 50 of your own acknowledgements, newest version first. It is registered through `keepCookie`, as `/api/session` and `/api/flags` are, so a poll's 401 never clears a newer session's cookie, and the runtime ends the document when `person` isn't the session's. `POST /api/notice/acknowledge {notice}` (`notice.acknowledge_own`) calls `acknowledge_notice()` with the session's own device, appends `notice.acknowledged` when something changed, and answers `{version, changed}`.
    - **The function.** `acknowledge_notice()`:
      - re-reads the person (still at the org) and the session's own device (theirs, not signed out) `FOR SHARE`, never a device the request names;
      - refuses an id that isn't one of the org's versions (22023);
      - takes the latest version `FOR SHARE`, again until it is still the latest, and refuses any other version (HF007);
      - writes `in_app` once (`on conflict do nothing`), with one audit row, `notice.acknowledge`; a second call writes nothing and answers `changed: false`.
    - **No direct writes.** `hearth_app` no longer holds INSERT on either notice table (0003's grants are revoked). There is no acknowledgement trigger: there is one writer, 070's superuser fixtures acknowledge older versions, and a data-only restore needs nothing turned off. `recorded_by_dpo` has no writer until PR 3.
27. **"Notified" and the provider-notice rule (PD-40, PD-41, PD-59, PD-61; A-01).**
    - **"Notified."** A non-pinned purpose is notified only while it is active and the latest version links it at its current register version, so any edit after publishing stops it until the next publish (PGT-12). Pinned purposes are unaffected (PD-07), and `purposeAllowed()` doesn't change.
    - **The stated facts.** Seven: services, data types, processing countries, storage countries, training, the provider's retention and onward recipients (`notice_facts()`, which `NOTICE_TRANSFER_FACTS` mirrors and check 6 compares). No role may run `notice_facts()`: only definer functions owned by `hearth_owner` call it.
    - **The send state.** `transfer_send_state(provider)` reads the open clearance `FOR SHARE`, a second time when the first read finds none, as PR 1's `transfer_cleared()` did (item 8), then the latest version with no lock, and answers:
      - `not_cleared`: no open clearance;
      - `no_notice`: an open clearance, and no version at all;
      - `cleared`: an open clearance, and the latest version is a stand-in or links a clearance of this provider whose notice facts equal the open one's;
      - `unstated`: an open clearance that the latest generated version doesn't state.
    - **Who gets a code** (`codeMaySend()`, `apps/server/src/compliance/transfers.ts`; PD-59). On `cleared` everyone; on `no_notice` or `unstated` a holder of `dpo` alone; on `not_cleared` nobody.
      - Sign-in reads whether the person holds `dpo` after `stillHere()` has read their row `FOR SHARE`, with no lock on `role_assignments` (`holdsRoleNow()`, `apps/server/src/access/world.ts`, which lets `packages/access` decide). `hearth_app` can't lock that table, and a `dpo` grant, like every PIN-role grant, takes the person's row `FOR NO KEY UPDATE`, so the person's row is where the two meet. Re-authentication reads it from `actingBy()`'s World.
      - A code held back is audited `skipped_no_notice` or `skipped_unstated`, beside `skipped_not_cleared`, and sign-in's reply is the same as for any other number. `no_notice` is logged `sms_provider_no_notice` at info, since it is expected before v0, and `unstated` `sms_provider_unstated` at error: sign-in codes have stopped for everyone but the DPO until a new notice is published.
      - A DPO re-authenticates with the PIN, so a code re-authentication in either state is skipped and answers 503. A request held back spends none of the person's day of code requests (T20 item 6).
    - **Why.** Before v0 only the DPO can use Hearth (OD-01), so nobody else's number goes to Twilio for nothing. After a stated Twilio fact changes, the DPO can still sign in and publish, so the change can't lock the org out.
    - **`transfer_cleared(provider)`** keeps its signature and grants, and answers true for `cleared` and `no_notice`: PR 1's meaning before v0, for every other sender (C0.14's push, C2.2's LiveKit). The worker's `providerCleared()` agrees: an open clearance, and no version, a stand-in as the latest, or the clearance stated (`notice_provider_states()`, item 9). No job names a provider yet (G3).
    - **What stops sends.** Re-clearing on the same facts, or changing only a review date, a safeguard or a confirmation, keeps them going. Changing a stated fact stops them, the DPO's codes aside, until the next publish.
    - **The bound.** A version that commits during a send lists every clearance open when it was made, the one the send holds `FOR SHARE` among them, so either answer agrees with a version the send could see. A change of facts waits for the send (PD-15).
    - **Stand-ins.** Production never gets one, so there the rule applies from v0. The seed's stand-in v0 keeps e2e sign-in working for every persona.
    - **Pinned purposes after publishing (PD-61).** A pinned purpose never stops, so once its entry changes after a publish, the published notice is out of date for everyone until the next one. `readRegisterState()` marks it `stale` when the latest version is generated and doesn't link it at its current version; with no version, or a stand-in as the latest, nothing is stale. The DPO's pages say so (item 31), and the worker logs `notice_pinned_out_of_date {org, purposes}` at warn, at most once a UTC day per org while any are stale and at once again when the set changes, until a new notice is published (PGT-16).
28. **The acknowledgement gate on REST (PD-43, PD-56).**
    - **The rule.** `noticeAdmits(world, me, use, standing)` (`packages/access/src/notice.ts`) decides, from one plain read of the latest version and whether the person has acknowledged it (`noticeStandings()`, `apps/server/src/compliance/notice-standing.ts`): `unpublished` while no version exists, else `acknowledged` or `required`. The read takes no lock and calls no function, runs in the request's own transaction, and is skipped for the exempt actions.
    - **Where it is asked.** In `consider()`, after the World loads and before `can()` and any target lock, for the request's action (`requireNotice()`, `apps/server/src/access/world.ts`); and in `actingBy()` with the use `'reauth'`, before the method guard, so an unacknowledged session can't make the provider send a code. A refusal is 403 `notice_required`. Only `access/world.ts` and `auth/account.ts` call `actingSession()` (NTS-05).
    - **Exempt in every standing** (`NOTICE_FREE`): `session.read_own` (both shell GETs), `devices.list_own`, `devices.sign_out_own`, `notice.read_own` and `notice.acknowledge_own`. None reaches anyone else's data, and a lost phone can always be signed out.
    - **The bound.** The read is plain, at READ COMMITTED: a request decided before a publish commits finishes within its 30 s, and the next one is refused.
    - **Never a flag.** The gate is a rule, and no flag reads it.
    - **The capability.** `capabilities.registers` stays `decide()`'s, which applies no gate, so the DPO keeps the register pages before v0: `/notice` offers their links and the shell's guard lets `/dpo/*` through. `GET /api/session` answers the standing as `notice` (T21 item 10).
    - **Background work (PD-56)** isn't gated per person by acknowledgement until A0.2 and A2.2 exclude by it. Purposes are gated per org, by "notified".

While no version exists, a holder of `dpo` also passes `register.read`, `register.purpose.set`, `register.transfer.set`, `notice.read`, `notice.publish` and PIN re-authentication. 33. **Writes, refusals, events and the lock order (PD-50, PD-52).**
    - **Writers.** `publish_notice()` and `acknowledge_notice()` are the notice tables' only writers, called after `can()` allows `notice.publish` or `notice.acknowledge_own`; each re-checks its actor in tables and writes its audit row (ADM-06). `notice_facts()` reads only its argument.
    - **Definer functions that take no acting user.** `transfer_send_state()` and `notice_provider_states()` skip `can()`: they answer only about the org's own registers and write nothing. `notice_provider_states()` answers, for the org the server set (none: no rows), each open non-AI clearance's provider and id and whether the latest version, whatever wrote it, links a clearance of that provider with equal notice facts (`stated`, false while no version exists), with no lock and never a clearance's facts. Whether a stand-in or no version makes that moot is the reader's to decide (item 27's `providerCleared()`), as `transfer_send_state()` decides it for a send. Coverage exempts it as a read, and `transfer_send_state()` beside `transfer_cleared()` as a check.

No role may run `notice_facts()` or `notice_check_dpo()`.
    - **Refusals.** HF007 is 409 `notice_changed`: a newer version, the registers moved since the draft, two publishes at once, or an acknowledgement of a version that is no longer the latest. HF008 is 400 `notice_invalid`: a rule refused publishing. 42501 is 403 (to publish) or 401 `signed_out` (to acknowledge); 22023 is 404. The SQLSTATEs are in `apps/server/src/db/sqlstate.ts`, and the three codes, with `notice_required`, in `packages/shared/src/api-errors.ts`, none of them saying "ask".
    - **Events.** `notice.published` (entity the version, ids `{version}`) and `notice.acknowledged` (entity and subject the person, ids `{notice, version}`), both `accounts`, owned by the new `notice` suite. 0009's outbox type check already names both, so 0010 leaves the outbox alone. The audit actions are `notice.publish` and `notice.acknowledge`.
    - **The lock order:** … `transfer_register` → `transfer_clearances` → `orgs` (publishing only) → `notice_versions` → `notice_acknowledgments` → `feature_flags` …. Publishing reads the DPO's rows `FOR SHARE`, locks the registers `FOR SHARE`, then the org's own row and the latest version `FOR NO KEY UPDATE`. Nothing else takes a row lock on `orgs`, and a foreign key's KEY SHARE doesn't wait for it. Acknowledging takes the person and the device, then the latest version, `FOR SHARE`. A code's send reads the person `FOR SHARE` (at sign-in through `stillHere()`, at re-authentication as the acting session), whether they hold `dpo` with no lock, then the clearance `FOR SHARE` and the notice with no lock.

Each respect the digest was widened for makes the digests differ, in a line the probe names: partitions' row level security, grants, owners, policies, indexes, rules, triggers, bounds and attachment, a month lacking what the others have, a rule literal or list bound that reads like the folded name or month, an index predicate holding text like the index's name, an invalid partitioned index, partition keys, options, persistence, sequences, identity and generated columns, column storage, collations, default privileges, schemas, NOT VALID, rewrite rules and aggregates (their grants, definitions and declared arguments). Equivalent builds compare equal: partitions for other months (including months whose index names Postgres shortened, months with their own indexes whose names it shortened and numbered, months with policies named for them, months whose rules or column defaults name their own month, and a foreign key into months held in different numbers), a database in New York or with other date, interval, float, bytea, string-escape, identifier-quoting or `search_path` settings, a domain made in New York, and, in copies of the fresh build, an older month's partition made by 0005's function with its clock set back, the months taken from the build's own partitions.
